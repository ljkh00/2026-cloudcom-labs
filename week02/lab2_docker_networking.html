Overview
Lab Overview & Scenario

In Lab 2.1 you ran one container — the menu. But real applications are never one container. CloudEats needs a web server and a cache, and eventually a database too. This lab answers the question: how do containers talk to each other?

You'll discover that Docker containers are isolated by default — they can't reach each other just because they're on the same machine. Then you'll create a custom bridge network and connect both containers to it. Once on the same network, any container can reach any other using just its container name as a hostname. No IP addresses needed.

⚠️ Prerequisite: Lab 2.1 complete — you should have the cloudeats-menu:v1.0 image on your machine. Confirm with docker images | grep cloudeats.
🌱 Beginner tip: The big idea today is simple: containers on the same Docker network can find each other by name. Like houses on the same street — you can visit your neighbour by name, not by memorising their GPS coordinates.
⚡ Average tip: Focus on the difference between the default bridge (legacy, no DNS) and custom bridge (has DNS). This distinction is why Docker Compose always creates a custom network automatically — it's not optional for modern multi-service apps.
🚀 Advanced tip: Docker uses embedded DNS (127.0.0.11) for service discovery on custom networks. Container names resolve to their internal IP addresses. Try docker exec menu cat /etc/resolv.conf after connecting to a custom network — you'll see the DNS server entry.

Default bridge: containers are isolated (IP addresses only). Custom bridge: containers find each other by name via Docker's built-in DNS.

Docker Network Types
⏱ 10 min
10 steps across 4 parts
1
Explore Existing Networks
See what Docker created automatically
›

Start by checking what networks Docker has created on your VM:

🐧 bash · docker network ls
docker network ls

# Expected output:
# NETWORK ID     NAME      DRIVER    SCOPE
# a1b2c3d4e5f6   bridge    bridge    local
# b2c3d4e5f6a1   host      host      local
# c3d4e5f6a1b2   none      null      local
📸
Screenshot · docker network ls
Terminal showing 3-row table: bridge (DRIVER: bridge), host (DRIVER: host), none (DRIVER: null) — all SCOPE: local

Docker creates these three networks automatically on every installation:

🌉 bridge
The default. Containers get a private IP but cannot find each other by name. Used when you run docker run without a --network flag.
🖥️ host
Container shares the host's network directly — no isolation, no port mapping. Rarely used in production. Not available on Mac/Windows.
🚫 none
Completely isolated — no network at all. For security-sensitive batch jobs that must never touch the network.
🌱 Bridge = private street where every house (container) has a number (IP), but neighbours can only visit using the exact number — not a name. We'll fix that with a custom network.
🚀 Run docker network inspect bridge — subnet is typically 172.17.0.0/16, bridged via Linux device docker0. Verify with ip link show docker0.
2
Why Default Bridge Breaks Name Resolution
The core problem we're about to solve
›

Let's prove the problem first. Start two containers on the default bridge and try to ping one from the other:

🐧 bash · Demonstrate the Problem
# First, stop any container named 'menu' from Lab 2.1
docker stop menu 2>/dev/null; docker rm menu 2>/dev/null

# Start menu on the DEFAULT bridge (no --network flag)
docker run -d -p 3000:80 --name menu cloudeats-menu:v1.0

# Start a simple alpine container to test from
docker run -d --name tester alpine sleep 600

# Try to ping 'menu' from tester by NAME
docker exec tester ping -c 2 menu
# Result: ping: bad address 'menu'  ← NAME RESOLUTION FAILS!

# Clean up the tester
docker stop tester && docker rm tester
📸
Screenshot · DNS Failure on Default Bridge
Terminal output of docker exec tester ping -c 2 menu — showing error message ping: bad address 'menu'
❌
Expected failure! The default bridge has no DNS. Containers can only communicate via raw IP addresses (e.g. 172.17.0.2), which change every time a container restarts.
💡 The fix: A custom bridge network includes Docker's built-in DNS — container names automatically become hostnames. This is the same model Docker Compose uses, which is why we're learning it by hand first.
🌱 Default bridge is a legacy feature. Always use a custom network for any multi-container application.
🚀 The legacy --link flag was Docker's workaround — injecting hostname entries into /etc/hosts. It's deprecated and one-way only. Custom networks with embedded DNS (added in Docker 1.9, 2015) replaced it. Never use --link.
🐧 bash · Clean Up
# Remove the menu container — we'll recreate it on our custom network
docker stop menu 2>/dev/null; docker rm menu 2>/dev/null
docker ps  # Should show: no containers running
Part 2
Create a Custom Network
⏱ 15 min
3
Create cloudeats-net
A private network for CloudEats containers
›
🐧 bash · Create Network
# Create a custom bridge network named cloudeats-net
docker network create cloudeats-net

# Output: a long ID like: 7d3a9c8f1b2e... (that's your network ID)

# Verify it was created
docker network ls
# Now you'll see cloudeats-net listed with DRIVER: bridge

# Inspect the new network
docker network inspect cloudeats-net
# Look for: "Subnet": "172.18.0.0/16" (or similar)
# and "Containers": {}  ← empty for now
🌱 What you just created: A virtual private network that only Docker containers can join. Think of it like creating a new private group chat — no one is in it yet, but anyone you invite can talk to everyone else in the group.
⚡ Notice the subnet is 172.18.0.0/16 — different from the default bridge at 172.17.0.0/16. Docker automatically assigns the next available subnet. You can specify a custom subnet with --subnet 192.168.100.0/24 if needed for specific IP planning.
🚀 You can also specify the driver: docker network create --driver bridge cloudeats-net. Other drivers include overlay (Docker Swarm, multi-host networking) and macvlan (each container gets a real MAC address on the physical network). For this course we always use bridge.
4
Run the Menu Container on the Network
Connect your first service
›

Run the menu container and attach it to cloudeats-net with the --network flag:

🐧 bash · Run on Custom Network
docker run \
  -d \
  -p 3000:80 \
  --name menu \
  --network cloudeats-net \
  cloudeats-menu:v1.0

# Verify it's running on the right network
docker inspect menu | grep -A 5 "Networks"
# Should show: "cloudeats-net": { ... }
  • -d
    Detached — runs in background
  • -p
    3000:80 — still maps host port 3000 to container port 80 for browser access
  • --name
    menu — this name becomes the container's DNS hostname on the network
  • --network
    cloudeats-net — join our custom network (DNS enabled)
🌱 Key insight: the container name you give with --name becomes its hostname on the Docker network. Other containers will reach it by typing menu — like a domain name but only inside your private network.
⏱
Checkpoint · 25 min mark Network created, menu container running. Browser still shows the menu at http://[VM-IP]:3000/html/index.html — confirm this.
Part 3
Add Redis to the Network
⏱ 15 min
5
Run the Redis Container
Add a second service to the CloudEats stack
›
🔴
What is Redis? Redis is an in-memory key-value store — an extremely fast database used for caching (temporarily storing data to speed up responses). CloudEats will use it in Week 4 for the shopping cart. Today you just need to know it's a second service that needs to talk to the web server.
🐧 bash · Run Redis
# Run Redis on the same network
# redis:alpine is only ~30MB — tiny!
docker run \
  -d \
  --name redis \
  --network cloudeats-net \
  redis:alpine

# Note: NO -p flag — we don't need Redis on the host
# It's only needed internally by other containers

# Confirm both containers are running
docker ps
# Should show: menu (port 3000) and redis (no host ports)
🌱 Notice: no -p flag for Redis. We don't want Redis accessible from outside — only from within the Docker network. This is good security practice. The browser needs to reach menu (so it needs -p). But only menu talks to redis, and they're both inside the same private network.
⚡ Redis defaults to port 6379. Without -p 6379:6379, this port is only reachable from within cloudeats-net. This is the principle of least exposure — only expose what needs to be publicly accessible. In cloud terms, this is like putting Redis in a private subnet with no public IP.
🚀 Redis's official image includes a health check that runs redis-cli ping every 30 seconds. You can see it with docker inspect redis | grep -A 10 Health. In Week 7 we'll add our own HEALTHCHECK instructions to Dockerfiles and use them in Docker Compose to control start-up order.

# menu:  172.18.0.2/16
# redis: 172.18.0.3/16
📸
Screenshot · Network Inspect Output
docker network inspect cloudeats-net showing the "Containers" section with both menu (172.18.0.2) and redis (172.18.0.3) listed
🌱 Both containers have IPs, but you'll never need to type them. On a custom network, menu and redis are the hostnames — Docker handles the rest.
🚀 IPs in 172.18.0.0/16 change on container recreation — never hardcode them. Docker Compose goes further: service key names (not container names) become DNS entries, letting you rename containers without changing app config.

Part 4
Container-to-Container Communication
⏱ 15 min
7
Ping by Container Name
Prove that DNS is working
›

Use docker exec to run commands inside the running menu container:

🐧 bash · Test from Inside menu Container
# Install ping inside the nginx:alpine container (it's minimal)
docker exec menu apk add --no-cache iputils 2>/dev/null || true

# Ping redis by NAME from inside the menu container
docker exec menu ping -c 3 redis

# Expected output:
# PING redis (172.18.0.3): 56 data bytes
# 64 bytes from 172.18.0.3: seq=0 ttl=64 time=0.123 ms
# 64 bytes from 172.18.0.3: seq=1 ttl=64 time=0.098 ms
# 64 bytes from 172.18.0.3: seq=2 ttl=64 time=0.105 ms
#
# ✅ Docker DNS resolved "redis" to 172.18.0.3 automatically!

Now test connecting to Redis directly from the menu container:

🐧 bash · Connect to Redis via Name
# Connect to Redis from inside the menu container
# redis-cli is in the redis image, not nginx — use the redis container
docker exec -it redis redis-cli -h redis

# You'll see the Redis prompt: redis:6379>
# Try these commands:
SET greeting "Hello from CloudEats!"
GET greeting
# Output: "Hello from CloudEats!"

PING
# Output: PONG

# Exit Redis CLI
exit
📸
Screenshot · Successful Ping by Name
docker exec menu ping -c 3 redis output — showing PING redis (172.18.0.x) with 3 reply lines and round-trip times. Docker DNS resolved the name automatically.

Now test Redis from inside its own container:

🐧 bash · Connect to Redis via Name
docker exec -it redis redis-cli -h redis

# redis:6379> prompt appears — try:
SET greeting "Hello from CloudEats!"
GET greeting   # → "Hello from CloudEats!"
PING           # → PONG
exit
📸
Screenshot · redis-cli Session
Terminal showing the redis:6379> prompt, then SET greeting "Hello from CloudEats!" → OK, GET greeting → "Hello from CloudEats!", PING → PONG
🌱 The container name (redis) is the hostname on the network. In Week 4, the shopping cart Node.js app will connect using exactly redis://redis:6379 — same idea.
⚡ Connection string pattern: redis://redis:6379 — hostname = container name, port = service's internal port. App code never changes between dev and production; only the container names need to match.
🚀 Docker's embedded DNS at 127.0.0.11:53 auto-updates when a container is replaced (same name, new IP). Run docker exec menu cat /etc/resolv.conf to see it — this is automatic service discovery.
8
Network Isolation Demo
Containers on different networks can't communicate
›

Create a second network and run a container on it. Show that it cannot reach redis:

🐧 bash · Isolation Demonstration
# Create a separate network (simulates a different service team)
docker network create isolated-net

# Run a container on the isolated network
docker run -d --name outsider \
  --network isolated-net \
  alpine sleep 300

# Try to ping redis from 'outsider' — should FAIL
docker exec outsider ping -c 2 redis
# Result: ping: bad address 'redis'  ← CANNOT SEE IT!

# Try to ping menu from 'outsider' — should also FAIL
docker exec outsider ping -c 2 menu
# Result: ping: bad address 'menu'  ← ISOLATED!

# Clean up the demo container and network
docker stop outsider && docker rm outsider
docker network rm isolated-net
🔒
This is a feature, not a bug. Network isolation means a hacked container on one network cannot access services on another network. In production, you might have: frontend-net (web + cache), backend-net (API + database), and only the API container on both networks as the bridge between them.
🌱 Summary so far: Containers on the same custom network can talk by name ✅. Containers on different networks cannot see each other ✅. You control what can communicate with what, just by choosing which network to put each container on.
🚀 A container can actually be connected to multiple networks simultaneously: docker network connect backend-net api-container. This makes the api-container reachable from both networks. This is how an API service acts as a bridge between the frontend and database layers — without exposing the database to the frontend network.

That's 7 manual steps. And when it comes to restarting, updating, or deploying to a new server, you repeat all 7. Now imagine 5 services: web, API, MySQL, Redis, MongoDB.

🐧 bash · What Week 3 Will Look Like
# All 7 steps above become THIS in Docker Compose:
docker-compose up -d

# That's it. One command.
# Networks created automatically.
# Containers connected automatically.
# Container names = DNS hostnames automatically.
# Coming in Lab 3.1!
🚀
What you learned today is the foundation for Docker Compose. Compose just automates exactly these steps: create network → run containers → attach to network → set names. The docker-compose.yml file you write in Week 3 is a description of what you just did by hand.
🌱 Don't worry — you will NOT need to memorise all these manual commands once we learn Docker Compose. The goal of today was to understand what Docker Compose does under the hood. When you write docker-compose up, you now know exactly what it's doing.
🚀 Docker Compose also adds dependency management (depends_on), health-check-aware startup ordering, environment variable files (.env), named volumes, and resource limits — all things we'll use in Week 3. But none of it is magic. It all maps directly to the manual docker network, docker run, and docker volume commands you've now seen.

Help
Troubleshooting
🔴
docker network create fails: "network with name cloudeats-net already exists"
›

From a previous session. Either reuse it or remove and recreate:

🐧 bash · Fix
# Option A: Reuse it (check what's connected)
docker network inspect cloudeats-net

# Option B: Remove and recreate
# Must disconnect all containers first
docker network disconnect cloudeats-net menu 2>/dev/null
docker network disconnect cloudeats-net redis 2>/dev/null
docker network rm cloudeats-net
docker network create cloudeats-net
🔴
ping: executable file not found in PATH (nginx container)
›

The nginx:alpine image is minimal and doesn't include ping. Install it first, or use wget instead:

🐧 bash · Fix
# Install ping inside the nginx container
docker exec menu apk add --no-cache iputils

# OR use wget to test HTTP connectivity
docker exec menu wget -qO- http://redis:6379 2>&1 | head -3
# Redis responds with an error message (not HTTP) — but the name resolved!
🔴
redis-cli: command not found (when running from menu container)
›

The redis-cli tool is only available in the redis container — not in the nginx one. Use docker exec on the redis container:

🐧 bash · Fix
# Run redis-cli FROM the redis container itself
docker exec -it redis redis-cli

# Or connect to the redis server using its hostname
docker exec -it redis redis-cli -h redis PING
# Should output: PONG
🔴
docker network inspect shows empty Containers even after docker run
›

The container was run without the --network flag, so it joined the default bridge. Connect it:

🐧 bash · Fix
# Connect an existing container to the network
docker network connect cloudeats-net menu
docker network connect cloudeats-net redis

# Verify
docker network inspect cloudeats-net

Or stop and rerun with the --network cloudeats-net flag.

Review
Knowledge Check

Click an answer to check it.

1. Why can't containers on the default bridge network communicate using names like ping redis?
  • The default bridge is too slow for DNS
  • The default bridge network has no built-in DNS server — containers can only communicate via raw IP addresses
  • Redis doesn't support ping from other containers
  • You need to install a plugin to enable container names
2. You run Redis without a -p flag: docker run -d --name redis --network cloudeats-net redis:alpine. What can and cannot reach it?
  • Nothing can reach it — the container is completely isolated
  • Only your browser on the host machine can reach it
  • Containers on cloudeats-net can reach it by name; the host machine and external traffic cannot
  • All traffic is blocked until a -p flag is added
3. An app container needs to be accessible from both a frontend network and a backend network. What is the correct approach?
  • Run two copies of the container, one on each network
  • Use docker network connect to attach the container to both networks simultaneously
  • Set the container's network to "none" so it bypasses all restrictions
  • This is impossible in Docker — containers can only be on one network
4. What does Docker Compose automate compared to what you did manually in this lab?
  • Docker Compose runs faster because it uses a different network driver
  • Docker Compose bypasses the need for networks entirely
  • It creates the network, connects all containers, resolves names, and manages start-up order — all from a single docker-compose.yml file with one command
  • Docker Compose only manages images; networks are still manual
