Overview
Lab Overview & Scenario

Your manager at CloudEats has given you your first real task: "We just signed our first restaurant — Nasi Lemak Paradise. Get their menu online today."

You'll build a proper digital menu in HTML and CSS. Then — instead of leaving it running on your local machine — you'll package it into a Docker container so it can be deployed to any server in seconds.

⚠️ Prerequisite: Lab 1.1 must be complete — you need Docker installed and your ~/cloudeats-app project folder ready.
🌱 Beginner tip: This lab has two big ideas — HTML/CSS (building the menu) and Docker (packaging it). Take each part step by step. You'll first see how the menu looks WITHOUT Docker, then understand WHY Docker makes it better.
⚡ Average tip: Focus on the Dockerfile syntax and the docker build → docker run workflow. Notice that the image is immutable once built — any change means a new build. That's intentional.
🚀 Advanced tip: As you write the Dockerfile, think about image layering. Each instruction creates a new layer. The order matters for build cache efficiency: put instructions that change frequently (COPY your files) after instructions that are stable (FROM, RUN installs). Try docker image inspect after building to see layers.

How a browser request reaches your HTML files through Docker's port mapping and nginx web server

Python has a built-in web server. Use it to quickly preview your menu:

# Navigate into the frontend folder
cd ~/cloudeats-app/frontend

# Start Python's built-in web server on port 3000
python3 -m http.server 3000
# Output: Serving HTTP on 0.0.0.0 port 3000 ...

In your host computer's browser, navigate to:

🌐 Browser URL
# Get your VM IP first (in a second terminal):
ip addr show | grep "inet "

# Then visit (replace with your actual IP):
http://192.168.56.101:3000/html/index.html

You should see the Nasi Lemak Paradise menu with green header and card layout.

🌱 What's happening? Python is acting as a "waiter" — it listens for requests on port 3000, and when a browser asks for index.html, Python reads the file from your filesystem and sends it back. This is exactly how all web servers work.

When done, press Ctrl + C to stop the Python server.

5
Understand the Problem
Why Python alone is not enough for production
›
ProblemPython ServerDocker + nginx
SetupMust manually run on every serverOne command: docker run
RestartsStops if terminal closes or server rebootsContainer restarts automatically
Scale10 servers = 10 manual setupsSame image, deploy anywhere
PerformanceDevelopment-only, not production-gradenginx handles thousands of requests/sec
DependencyNeeds Python on every servernginx already inside the image
💡 A Docker container packages your code + the web server + the OS layer together — it runs identically everywhere Docker is installed.
🌱 Python serving files is like cooking at home and hoping every restaurant copies your kitchen. Docker packages the kitchen with the meal — same result, anywhere.
⚡ nginx (pronounced "engine-x") powers Netflix, Airbnb, and most major websites. The nginx:alpine image is only ~23MB vs ~80MB+ for an Ubuntu-based image — smaller means faster pulls and fewer security vulnerabilities.
🚀 Python's http.server is single-threaded. nginx uses an async, event-driven model — similar to Node.js — handling thousands of concurrent connections with ~5MB RAM. For a static site with 1,000 simultaneous users, the difference is significant.

Understand the Dockerfile
Recipe before cooking
›

A Dockerfile is a recipe for building a Docker image. You write it once, and Docker follows it to create an image — a portable, self-contained package of your app.

  • 📋
    Dockerfile — the recipe. Text instructions: FROM, COPY, EXPOSE
  • 📦
    Image — the built result. Read-only snapshot. Like a sealed package
  • 🐳
    Container — a running instance of an image. Many containers can run from one image
🌱 Recipe → baked cake → cake on the table. Dockerfile → docker build (image) → docker run (container).
⚡ Images are immutable — once built, they can't change. Update your HTML? Rebuild the image. This guarantees what you build is exactly what runs in production.
🚀 Each Dockerfile instruction creates a content-addressed layer (SHA256). Unchanged layers are pulled from cache — rebuild only touches what changed. Put frequently-changing instructions (COPY) after stable ones (FROM, RUN) to maximise cache hits.
7
Write the Dockerfile
3 lines is all you need
›

Create the Dockerfile inside the frontend/ folder (no file extension):

🐧 bash · Create Dockerfile
# Make sure you're in the frontend folder
cd ~/cloudeats-app/frontend

# Create the Dockerfile (no extension!)
touch Dockerfile

Open Dockerfile in VS Code and type this:

🐳 Dockerfile
# Start from the official nginx image (Alpine Linux variant)
FROM nginx:alpine

# Copy your HTML and CSS files into nginx's web root
COPY html/ /usr/share/nginx/html/
COPY css/  /usr/share/nginx/html/css/

# Tell Docker this container listens on port 80
EXPOSE 80

Each line explained:

  • FROM
    nginx:alpine — use the official nginx image (Alpine Linux). Downloads automatically from Docker Hub
  • COPY
    html/ → nginx's web root at /usr/share/nginx/html/
  • COPY
    css/ → matching subfolder so the HTML's ../css/style.css path resolves correctly
  • EXPOSE
    Documents that nginx listens on port 80 internally. Port binding to host happens at docker run -p 3000:80
📸
Screenshot · VS Code with Dockerfile
VS Code editor showing the 4-line Dockerfile, with the file tree on the left displaying frontend/ folder containing Dockerfile, html/, and css/
🌱 Important: The Dockerfile must be named exactly Dockerfile — capital D, no extension. Docker specifically looks for this filename.
⚡ nginx:alpine downloads from Docker Hub — the public image registry. It's ~23MB. The alternative nginx:latest is based on Debian and is ~140MB. Alpine is preferred in production because smaller = less attack surface + faster pulls.
🚀 EXPOSE is metadata only — it doesn't actually publish the port. The actual port binding happens at docker run -p 3000:80. Think of EXPOSE as documentation for other developers about what the container expects. In Docker Compose (Week 3), you'll see how EXPOSE helps with service-to-service networking inside the same compose network.
⚠️ The COPY path html/ is relative to where you run docker build. You must be inside the frontend/ folder when building, or the COPY will fail.

Build the Docker Image
Turn your Dockerfile into a packaged image
›

Run the build command from inside the frontend/ folder:

🐧 bash · docker build
# Make sure you're in frontend/ folder
cd ~/cloudeats-app/frontend

# Build the image
# -t = tag (name:version)   . = build context = current folder
docker build -t cloudeats-menu:v1.0 .

# You'll see something like:
# [+] Building 3.2s (7/7) FINISHED
#  => [1/3] FROM docker.io/library/nginx:alpine
#  => [2/3] COPY html/ /usr/share/nginx/html/
#  => [3/3] COPY css/  /usr/share/nginx/html/css/

Verify the image was created:

🐧 bash · List Images
docker images

# Expected output:
# REPOSITORY       TAG     IMAGE ID       CREATED         SIZE
# cloudeats-menu   v1.0    a3f9b1e2d...   10 seconds ago  23.4MB
# nginx            alpine  ...            ...             ...
📸
Screenshot · docker build Terminal Output
Terminal showing the full docker build output — [1/3] FROM nginx:alpine, [2/3] COPY html/, [3/3] COPY css/ with "FINISHED" status and elapsed time
🌱 Docker read your Dockerfile, downloaded nginx:alpine, and copied your files in. The result is stored locally — only ~23MB!

9
Run the Container
From image to live container in one command
›

Start the container from your image:

🐧 bash · docker run
docker run \
  -d \
  -p 3000:80 \
  --name menu \
  cloudeats-menu:v1.0

# What each flag means:
# -d           → detached (runs in background, no terminal blocking)
# -p 3000:80   → map HOST port 3000 to CONTAINER port 80
# --name menu  → friendly name for the container
# cloudeats-menu:v1.0 → which image to run
🌱 -p 3000:80 explained: Inside the container, nginx is listening on port 80. But to reach it from outside, we open a "door" on the host machine's port 3000. So: your browser on :3000 → Docker routes to container :80 → nginx responds. The format is always HOST:CONTAINER.
⚡ The -d flag runs the container in detached mode — it keeps running even after you close the terminal. Unlike Python's server which dies when you press Ctrl+C. You can stop it with docker stop menu.
🚀 Compare what you just did to the Python server workflow: Python required cd to the right folder, the right Python version installed, and a blocking terminal. Docker only needs the image name. This is the operational simplicity that makes containers so valuable in production automation.

Create .dockerignore
Keep images clean and small
›

A .dockerignore file works like .gitignore — it tells Docker which files to exclude from the build context. Create it in the frontend/ folder:

📄 frontend/.dockerignore
# Files we do NOT want inside the container image
.git
.gitignore
*.md
Dockerfile
.dockerignore
🌱 Why exclude these? The Dockerfile and .gitignore are instructions for tools — they're not part of your website. Including them in the container wastes space and can expose internal details. Only include files the web server actually needs to serve.
🚀 The .dockerignore also affects build speed. Docker calculates checksums of the build context before sending it to the build engine. Large .git folders (especially with long commit histories) can slow this step significantly. Always ignore .git in Docker builds.

Troubleshooting
🔴
docker build fails: "COPY failed: no such file or directory"
›

This means you ran docker build from the wrong folder. The COPY paths in the Dockerfile are relative to where you run the build command.

🐧 bash · Fix
# Make sure you're in the frontend/ folder
cd ~/cloudeats-app/frontend
ls
# Should show: Dockerfile  .dockerignore  html/  css/

# Now build
docker build -t cloudeats-menu:v1.0 .
🔴
docker run fails: "port is already allocated" or "name already in use"
›

A container named menu is already running (possibly from a previous attempt), or port 3000 is in use.

🐧 bash · Fix
# Stop and remove the old container
docker stop menu
docker rm menu

# If port 3000 is still in use, check what's using it
sudo lsof -i :3000
# Kill the process if needed, then run again
docker run -d -p 3000:80 --name menu cloudeats-menu:v1.0
🔴
Browser shows the page but CSS is missing (no styling)
›

The CSS file path in your HTML might be wrong, or the COPY instruction didn't include the css/ folder.

🐧 bash · Check Inside Container
# Check what's inside the running container
docker exec menu ls /usr/share/nginx/html/
# Should show: index.html  css/

docker exec menu ls /usr/share/nginx/html/css/
# Should show: style.css

# If css/ is missing, check your Dockerfile COPY lines
# Then rebuild: docker build -t cloudeats-menu:v1.0 .

Also check in index.html that the link tag says: href="../css/style.css"

🔴
Browser shows nginx default page, not my menu
›

You're accessing the root URL instead of the /html/ path. Or the HTML files landed in the wrong location inside the container.

🐧 bash · Fix
# Try the correct path in browser:
http://[VM-IP]:3000/html/index.html

# If that doesn't work, check file locations in container:
docker exec menu find /usr/share/nginx/html/ -name "*.html"
# Expected: /usr/share/nginx/html/index.html
🔴
docker: command not found
›

Docker is not installed or not accessible to your user. Run the installation commands from Lab 1.1 and add your user to the docker group.

🐧 bash · Fix
# Check if docker is installed
which docker
docker --version

# If permission denied (not "command not found"):
sudo usermod -aG docker $USER
newgrp docker
# Then try docker ps again

Knowledge Check

Test your understanding. Click an answer to check it.

1. In the command docker run -d -p 3000:80 cloudeats-menu:v1.0, what does -p 3000:80 mean?
  • Run 3000 copies on 80 servers
  • Map host port 3000 to container port 80 — browser connects on 3000, nginx listens on 80 inside
  • The image uses version 3000 of nginx and port 80 of Python
  • Reserve 3000MB of RAM and use CPU core 80
2. What is the difference between a Docker image and a Docker container?
  • They are the same thing — image is just an older name for container
  • An image runs on Linux, a container runs on Windows
  • An image is a read-only packaged snapshot; a container is a running instance of an image
  • Images are for databases, containers are only for web servers
3. Why is nginx:alpine preferred over nginx:latest for this project?
  • nginx:latest is an older, outdated version
  • Alpine Linux is a minimal OS — the image is ~23MB vs ~140MB, making it faster to pull and deploy with a smaller attack surface
  • nginx:alpine supports CSS; nginx:latest does not
  • Alpine version is free; latest requires a paid Docker licence
4. You update a menu item price in index.html. What steps are needed to see the change in the running container?
  • Refresh the browser — the container detects file changes automatically
  • Restart Docker Engine with sudo systemctl restart docker
  • Rebuild the image (docker build), stop the old container, run a new one from the updated image
  • Edit the file directly inside the running container — changes persist automatically
