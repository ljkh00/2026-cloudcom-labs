1.1 The Shared Responsibility Model ⏱ 20 min
🏠 Real-world analogy
Think of renting an apartment. The landlord is responsible for the building structure, the roof, and the plumbing inside the walls. You are responsible for locking your door, keeping your keys safe, and not leaving the stove on. Neither party can do the other's job. Cloud security works the same way.

When you run an application on a cloud provider, security is shared. The provider secures some layers. You secure the rest. Exactly where that line falls depends on which service model you chose:

ModelExampleProvider securesYou secure
IaaS AWS EC2 virtual machine Physical hardware, network cables, hypervisor Operating system, middleware, application, database, credentials, access rules
PaaS AWS Elastic Beanstalk, Azure App Service Hardware + OS + runtime platform Application code, data, who has access
SaaS Gmail, Salesforce Everything except your data and user accounts Who has accounts, what data you put in
🖥️
In our Proxmox environment: Proxmox is the physical server and hypervisor — it is "the cloud". You are responsible for everything inside your VM: the Ubuntu OS, Docker, your Node.js application, database credentials, and access control rules. There is no managed service to do it for you.
🌱 Beginner focus
The key takeaway: the cloud provider will never fix a bug in your code. If your app has no login protection, that is your problem to fix — not Amazon's or Microsoft's.
⚡ Average — think deeper
Consider: which parts of the CloudEats stack are your responsibility right now? (Answer: all of it — Node.js services, MySQL, credentials in docker-compose.yml, open ports, no authentication on API routes yet.)
🚀 Advanced
In a real AWS deployment, CloudEats would be split: EC2 (IaaS) for the app servers, RDS (PaaS) for the database. The responsibility boundary shifts — AWS patches the MySQL engine, you configure who connects to it. Think about how this changes your security checklist.
⚠️
Most common cloud breaches are customer mistakes, not provider failures: database left open to the internet, passwords committed to GitHub, no multi-factor authentication on the admin account, IAM roles with "give everything access to everything".
1.2 Common Security Threats — Awareness Level ⏱ 20 min

You do not need to be a security expert. You need to recognise these threats and not write vulnerable code. The five most relevant threats for a web application developer:

💉
SQL Injection
Attacker puts SQL code inside an input field to manipulate the database. Example: typing admin' OR '1'='1 as a username can bypass login entirely.
🔑
Broken Authentication
Weak passwords, tokens that never expire, or plain-text passwords stored in the database. Our bcrypt hashing (Week 3) already addresses the last one.
👁️
Sensitive Data Exposure
API keys or passwords committed to GitHub. Database credentials hardcoded in docker-compose.yml. Passwords printed to server logs.
🚪
Broken Access Control
Customer A can view Customer B's orders by guessing the order ID. Authenticated users reach admin endpoints that should be blocked. Fixed by RBAC (Lab 8.2).
⚙️
Security Misconfiguration
MySQL port 3306 open to the whole internet. Default passwords never changed. Admin panel with no authentication at /admin.
Fix SQL Injection Prevention — The Parameterised Query

The rule is simple: never build SQL strings by joining user input with text. Always use a ? placeholder:

❌ Vulnerable — never do this
JavaScript
// DANGER: user input goes directly into the query string
const query = "SELECT * FROM users WHERE email = '" + email + "'";
db.query(query, callback);

If email is x' OR '1'='1, this returns ALL users.

✅ Safe — parameterised query
JavaScript
// SAFE: the ? is a placeholder — input is treated as DATA
db.query(
  'SELECT * FROM users WHERE email = ?',
  [email],   // ← passed separately, never concatenated
  callback
);

The mysql2 library handles escaping automatically.

Why? When you use ?, the database driver escapes the input so it can never be interpreted as SQL code — it is treated as a raw string value. You already do this in your CloudEats code. Do not change to string concatenation for any reason.

You already know VPCs, subnets, and security groups from Week 2. Here is how they apply to security specifically:

🐳
Proxmox/Docker equivalent: In our stack, MySQL and MongoDB have no -p port mapping in docker-compose.yml — they cannot be reached from outside the Docker network. Only the API Gateway is exposed on port 8000. This mirrors the real-world pattern: load balancer in the public subnet, databases in private subnets with no internet route.
🚀 Advanced — VPN context
A VPN (Virtual Private Network) encrypts traffic between two networks. Cloud use cases: site-to-site VPN connects an office network to a cloud VPC; client VPN lets remote employees access private cloud resources (like the database subnet) without exposing ports to the internet. We do not implement VPN in this course — the concept is sufficient for the final exam and interview questions.
1.4 Encryption at Rest and in Transit ⏱ 5 min
💾
Encryption at Rest
Data stored on disk is encrypted. Even if someone physically steals the hard drive, they cannot read the data without the key. Managed cloud databases (AWS RDS, Azure Database) enable this with one checkbox — no code required from you.
🔐
Encryption in Transit (TLS/HTTPS)
Data moving between the browser and server is encrypted. Without HTTPS, JWT tokens and passwords travel in plain text — anyone on the same Wi-Fi can intercept them. In production, the API Gateway terminates HTTPS. Internal service-to-service traffic can remain HTTP.
📬 Analogy
Encryption at rest = locking documents in a safe. Encryption in transit = sending them in a sealed, tamper-evident envelope rather than on a postcard.
2.1 Authentication vs Authorisation ⏱ 10 min
🏨 Hotel analogy
Authentication is showing your passport at check-in — proving who you are. Authorisation is the key card that only opens your room — even though you are authenticated as a guest, you cannot open every door in the hotel.
🪪
Authentication (AuthN) — "Who are you?"
Verify the user is who they claim to be. Method: username + password, biometric, OTP. Result: a confirmed identity — "this is user ID 5, email ali@example.com".
🛡️
Authorisation (AuthZ) — "What can you do?"
Given a confirmed identity, decide what they may access. Method: RBAC, permission lists. Result: access granted or denied — "Ali can view his own orders but not the admin dashboard".
⚠️
Both are required. Authentication without authorisation means any logged-in user can do anything. Authorisation without authentication means anyone can claim any identity. This week we implement both: Lab 8.1 adds authentication (JWT), Lab 8.2 adds authorisation (RBAC).
2.2 JSON Web Tokens (JWT) ⏱ 30 min
🌱 Beginner — plain English first
A JWT is like a signed wristband at a concert. The venue stamps it when you enter (login). Every time you want a beer or access a VIP area, staff check the stamp — they do not radio back to the ticket office each time. The stamp itself proves you were authorised.

Before JWT, the common approach was server-side sessions:

🗄️ Session-based (older approach)
  • User logs in → server stores a session record in a database
  • Server gives user a session cookie with a session ID
  • On every request, server queries the database to look up the session
  • Problem: every request hits the database; hard to scale across multiple servers
🎫 JWT (stateless, modern)
  • User logs in → server creates a signed token containing user info
  • Server sends token to the client; client stores it
  • On every request, client sends the token; server verifies the signature — no database lookup
  • Benefit: fast, stateless, any server can verify (scales horizontally)

JWT Structure — Three Parts

Part 1 · Header
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
Algorithm + token type (base64 encoded)
.
Part 2 · Payload
eyJ1c2VySWQiOjEsImVtYWlsIjoidXNlckBleGFtcGxlLmNvbSIsInJvbGUiOiJjdXN0b21lciJ9
User data: ID, email, role (base64 encoded)
.
Part 3 · Signature
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
HMAC-SHA256 of header+payload signed with JWT_SECRET
⚠️
JWT is NOT encrypted — it is signed. Anyone can decode the payload and read the user ID and email. Never put passwords, credit card numbers, or secrets inside a JWT. The signature only proves it has not been tampered with.
JavaScript — decoded JWT payload
{
  "userId": 1,
  "email": "ali@example.com",
  "role": "customer",
  "iat": 1750000000,   // issued at (Unix timestamp)
  "exp": 1750086400    // expires at (24 hours later)
}

The Full JWT Authentication Flow

1
Login: User sends POST /api/auth/login with email + password.
2
Verify credentials: Server checks bcrypt hash. If valid, creates a JWT with jwt.sign({ userId, email, role }, JWT_SECRET, { expiresIn: '24h' }).
3
Token returned: Server responds with { token: "eyJ..." }. Client stores it (usually in memory or localStorage).
4
Subsequent requests: Client includes the token in the Authorization header: Bearer eyJ...
5
Middleware verifies: authenticateToken middleware calls jwt.verify(token, JWT_SECRET). If valid, it attaches req.user = decoded and passes on to the route handler.
6
Response: Route handler uses req.user.userId to serve only that user's data. Returns 200 if valid, 401 if missing/invalid, 403 if wrong role.
JavaScript — authenticateToken middleware
function authenticateToken(req, res, next) {
  // Extract token from: "Bearer eyJ..."
  const authHeader = req.headers['authorization'];
  const token = authHeader && authHeader.split(' ')[1];

  if (!token) {
    return res.status(401).json({ error: 'No token provided' });
  }

  jwt.verify(token, process.env.JWT_SECRET, (err, decoded) => {
    if (err) {
      return res.status(401).json({ error: 'Invalid or expired token' });
    }
    req.user = decoded;   // { userId, email, role, iat, exp }
    next();               // pass control to the route handler
  });
}
🔑
JWT_SECRET must never be in your code or committed to Git. Store it in a .env file, add .env to .gitignore, and load it with require('dotenv').config(). If the secret leaks, anyone can forge valid tokens for any user.
2.3 Role-Based Access Control (RBAC) ⏱ 15 min

RBAC is the answer to: "A user is authenticated — but what are they allowed to do?"

The principle: grant the minimum access a user needs to do their job — nothing more. This is called the principle of least privilege.

🛒
Customer
Browse menus, place orders, view own orders. Cannot see other customers' data. Cannot modify menus.
🍽️
Restaurant Owner
All customer permissions + add/edit menu items for their own restaurant + view restaurant-level analytics.
⚙️
Admin
All permissions + manage all users + view system-wide stats + access admin endpoints.

RBAC is implemented in two steps: the role is stored in the JWT payload (so the server knows who you are), and a requireRole() middleware checks it before allowing access to protected routes:

JavaScript — requireRole middleware
// Factory function — returns a middleware configured for the required role(s)
function requireRole(...roles) {
  return (req, res, next) => {
    if (!req.user) {
      return res.status(401).json({ error: 'Not authenticated' });
    }
    if (!roles.includes(req.user.role)) {
      return res.status(403).json({
        error: `Access denied — requires role: ${roles.join(' or ')}`
      });
    }
    next();
  };
}

// Usage on routes:
app.get('/api/admin/users',
  authenticateToken,          // step 1: must have valid JWT
  requireRole('admin'),       // step 2: must be admin
  (req, res) => { /* ... */ }
);

app.post('/api/menu',
  authenticateToken,
  requireRole('admin', 'owner'), // either role is fine
  (req, res) => { /* ... */ }
);
HTTP CodeMeaningWhen we use itWhat client should do
200 OK Valid token, correct role, data returned Show the data
401 Unauthorized Not authenticated Missing token, expired token, invalid signature Redirect to login page
403 Forbidden Not authorised Valid token but wrong role (customer trying admin route) Show "Access Denied" — do NOT redirect to login
401 vs 403 — why does the distinction matter? A 401 tells the client "we don't know who you are — log in". A 403 tells the client "we know exactly who you are, and you are not allowed". Treating them the same leads to a confusing UX and leaks information about what routes exist.
⚡ Average — checkpoint question
A restaurant owner's JWT contains "role": "owner". They try to access GET /api/admin/users which requires requireRole('admin'). What HTTP status code is returned, and why? (Answer: 403 — they are authenticated but not in the admin role.)
🚀 Advanced — real-world extension
The requireRole() pattern above checks role names exactly. Production systems often use permission-based RBAC instead: a role maps to a set of permissions ("orders:read", "menus:write"), and middleware checks individual permissions rather than role names. This makes it easier to add new roles without rewriting middleware. See AWS IAM policies for a real example.

Why JWT over sessions in microservices?
JWT is stateless — any service can verify it using the shared secret without contacting a central session store. Sessions require shared database access across all services.
Why must JWT_SECRET not be in Git?
If the secret is public, anyone can run jwt.sign({ userId: 1, role: 'admin' }, knownSecret) and forge an admin token for any user ID.
