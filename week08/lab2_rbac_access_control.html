Part 1 Add a Role Column to the Users Table ⏱ 10 min
13 steps across 5 parts
1
Connect to MySQL and inspect the users table
🌱 Beginner — what are we doing?
We need to add a "role" column to the database so we can store whether each user is a customer, owner, or admin. We do this directly in MySQL using SQL commands.
Terminal

  -ucloudeats_user -pcloudeats_pass cloudeats
✅ You should see the MySQL prompt
mysql>

Now look at the current table structure:

MySQL
DESCRIBE users;
✅ Current columns — no role column yet
+---------------+--------------+------+-----+ | Field | Type | Null | Key | +---------------+--------------+------+-----+ | id | int | NO | PRI | | name | varchar(100) | YES | | | email | varchar(255) | NO | UNI | | password_hash | varchar(255) | NO | | | created_at | timestamp | YES | | +---------------+--------------+------+-----+
2
Add the role column with a default of 'customer'

We use an ENUM (enumeration) column to restrict the role to a fixed set of allowed values. The DEFAULT means every new user automatically gets the 'customer' role unless we specify otherwise:

MySQL
ALTER TABLE users 
ADD COLUMN role ENUM('customer','owner','admin') NOT NULL DEFAULT 'customer';
✅ Expected
Query OK, 0 rows affected (0.03 sec)
🌱 Beginner — what is ENUM?
ENUM is like a multiple-choice field. The database will only accept one of the listed values: 'customer', 'owner', or 'admin'. If you try to insert 'superuser', MySQL rejects it. This prevents typos and invalid roles.
Why DEFAULT 'customer'? Security principle: new accounts should have the minimum access level by default. An admin must actively promote someone to 'owner' or 'admin'. This is the principle of least privilege applied at the database level.

Part 2 Include Role in the JWT Payload ⏱ 8 min
4
Update jwt.sign() to include the role

Open server.js and find the jwt.sign() call you added in Lab 8.1. Add role: user.role to the payload:

server.js — jwt.sign() update
// BEFORE (Lab 8.1):
const token = jwt.sign(
  { userId: user.id, email: user.email, name: user.name },
  process.env.JWT_SECRET,
  { expiresIn: process.env.JWT_EXPIRES_IN || '24h' }
);

// AFTER (Lab 8.2) — ADD role:
const token = jwt.sign(
  {
    userId: user.id,
    email:  user.email,
    name:   user.name,
    role:   user.role   // ← ADD THIS
  },
  process.env.JWT_SECRET,
  { expiresIn: process.env.JWT_EXPIRES_IN || '24h' }
);
Why put the role in the token? The middleware needs to know the user's role to make access decisions. Without the role in the JWT, the server would have to query the database on every request to look it up — eliminating the stateless benefit of JWT. Storing the role in the token keeps things fast.
⚠️
Important: After this change, existing tokens (from Lab 8.1) will not contain a role. Users must log out and log in again to get a new token with the role included. This is normal — tokens are issued at login time with a snapshot of the user's data.

Part 3 Build the requireRole() Middleware ⏱ 10 min
7
Write requireRole() — add it below authenticateToken

Add this function in server.js, directly after your authenticateToken function from Lab 8.1:

server.js — add after authenticateToken
// ── ROLE AUTHORISATION MIDDLEWARE ──
// Usage: requireRole('admin') or requireRole('admin', 'owner')
function requireRole(...roles) {
  return (req, res, next) => {
    // authenticateToken must have run first — req.user must exist
    if (!req.user) {
      return res.status(401).json({ error: 'Not authenticated' });
    }

    // Check if the user's role is in the allowed list
    if (!roles.includes(req.user.role)) {
      return res.status(403).json({
        error: `Access denied. This route requires role: ${roles.join(' or ')}.`
      });
    }

    next(); // Role is allowed — continue to the route handler
  };
}
🌱 Beginner — how does this function work?

requireRole('admin') returns a new middleware function. That returned function checks req.user.role (set by authenticateToken) against the list of allowed roles. If the role is in the list, it calls next(). If not, it returns 403.

Think of it as a second security guard, standing inside the room: the first guard (authenticateToken) checked your identity badge; this guard checks whether your job title allows you into this particular room.

⚡ Average — 401 vs 403
Notice that requireRole returns 401 if req.user is missing (shouldn't happen if middlewares are chained correctly, but defensive coding), and 403 if the user is authenticated but in the wrong role. These two codes have different meanings that clients must handle differently.
🚀 Advanced — the factory pattern
requireRole('admin') returns a function — this is the factory function pattern (or higher-order function). It lets you configure middleware at route definition time rather than checking arguments inside the middleware itself. This is the same pattern used by Express's own express.static() and express.json().
Part 4 Create Admin-Only Routes ⏱ 12 min
8
Add a GET /api/admin/users route (admin only)

Add this new route in server.js — it lists all users with their roles. Only an admin token can access it:

server.js — admin route
// ── ADMIN ROUTES ──

/**
 * GET /api/admin/users
 * Returns all users with their roles.
 * Requires: valid JWT (authenticateToken) AND role = admin (requireRole)
 */
app.get('/api/admin/users',
  authenticateToken,          // step 1: must be logged in
  requireRole('admin'),       // step 2: must be admin
  (req, res) => {
    db.query(
      'SELECT id, name, email, role, created_at FROM users ORDER BY id',
      (err, results) => {
        if (err) return res.status(500).json({ error: 'Database error' });
        res.json({ users: results });
      }
    );
  }
);
Why chain authenticateToken AND requireRole? These two middlewares do different jobs. authenticateToken proves identity (who are you?). requireRole checks permission (can you do this?). Separating them follows the single-responsibility principle — each function does one thing. You can mix and match them on any route.
9
Add a GET /api/admin/stats route

A simple dashboard-style endpoint that only admins can see:

server.js — stats route
app.get('/api/admin/stats',
  authenticateToken,
  requireRole('admin'),
  (req, res) => {
    db.query(
      `SELECT
        (SELECT COUNT(*) FROM users) AS total_users,
        (SELECT COUNT(*) FROM users WHERE role = 'admin') AS admin_count,
        (SELECT COUNT(*) FROM users WHERE role = 'customer') AS customer_count,
        (SELECT COUNT(*) FROM orders) AS total_orders`,
      (err, results) => {
        if (err) return res.status(500).json({ error: 'Database error' });
        res.json({ stats: results[0], requested_by: req.user.email });
      }
    );
  }
);

Part 5 Test — The Key Checkpoint ⏱ 15 min
11
Get a customer token and test admin route — expect 403

Log in as a regular customer (an account you registered in Lab 3.2 — it should have role 'customer' by default):

Terminal
CUSTOMER_TOKEN=$(curl -s -X POST http://localhost:8000/api/auth/login \
  -H "Content-Type: application/json" \

Terminal

HTTP/1.1 403 Forbidden {"error":"Access denied. This route requires role: admin."}
🎯
403 is the correct response: the customer is authenticated (valid JWT, so not 401) but not in the admin role (so not 200 — instead 403 Forbidden).

🎯 Lab 8.2 Key Checkpoint — all must pass
  • ✅ Customer token + /api/admin/users → 403 Forbidden
  • ✅ Admin token + /api/admin/users → 200 OK with user list
  • ✅ Customer token + /api/orders/1 (own orders) → 200 OK
  • ✅ No token + any route → 401 Unauthorized

All four passing means your authentication (Lab 8.1) and authorisation (Lab 8.2) layers are both working correctly.

🚀 Advanced Challenge Extension

The current setup does not check which restaurant an owner belongs to. An owner with role 'owner' could theoretically edit any restaurant's menu. Fix this:

  1. Add a restaurant_id column to the users table (nullable — customers and admins have NULL).
  2. When an owner calls PUT /api/menu/:itemId, query the menu item to find its restaurant_id.
  3. Compare it to req.user.restaurantId (you will need to include this in the JWT payload too).
  4. If they do not match, return 403.

This is how multi-tenant SaaS products (like restaurant management platforms) enforce data isolation between tenants.
