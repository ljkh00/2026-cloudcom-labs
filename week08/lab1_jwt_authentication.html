Part 1 The Security Problem ⏱ 10 min
15 steps across 5 parts
1
Understand what is currently unprotected

Right now, anyone on the network can call any CloudEats API endpoint without proving who they are. There is no login check. Try this in your terminal:

🌱 Beginner — what is curl?
curl is a command-line tool that sends HTTP requests. We use it to test APIs without a browser. It comes pre-installed on Linux (your VM).
Terminal
curl http://localhost:8000/api/orders/1
✅ You will see — any order data returned with no login
{"id":1,"userId":1,"items":[...],"total":12.50} ← returned without any login!

This is the problem we are fixing today. By the end of this lab, that same request will return:

🔒 After this lab — protected
{"error":"No token provided"} ← HTTP 401
Why does this matter? Right now any script, bot, or malicious user can place orders as any user ID, read anyone's order history, and access every API endpoint. This is a critical security hole in any real application.

jsonwebtoken creates and verifies JWT tokens. dotenv loads variables from a .env file into process.env so your code can use them without hardcoding values.

4
Create the .env file with your secrets

A .env file (pronounced "dot env") stores configuration values and secrets. It is never committed to Git. The file lives on the server only.

🌱 Beginner — what is a .env file?
Think of it as a private notepad that your application reads at startup. You put secrets in here (like passwords and API keys) instead of writing them directly in your code.
Terminal
nano .env

Copy the entire block below into the file, then press Ctrl+O (save), Enter, Ctrl+X (exit):

.env
# CloudEats User Service — secrets
# DO NOT COMMIT THIS FILE TO GIT

PORT=3001
NODE_ENV=development

DB_HOST=mysql
DB_USER=cloudeats_user
DB_PASSWORD=cloudeats_pass
DB_NAME=cloudeats

JWT_SECRET=cloudeats-super-secret-key-change-in-production
JWT_EXPIRES_IN=24h
⚠️
Important: In a real project, JWT_SECRET should be a long random string (32+ characters). Never use a predictable phrase. For this lab a simple value is fine for learning, but remember to change it before any public deployment.
5
Add .env to .gitignore

If .env is committed to GitHub, anyone who reads your repository can steal your JWT_SECRET and forge tokens for any user. Prevent this by listing .env in .gitignore:

Terminal
echo ".env" >> .gitignore
cat .gitignore
✅ .gitignore should contain .env
node_modules/ .env
Part 2B Make Login Return a JWT Token ⏱ 15 min
6
Add JWT imports to server.js

Open server.js in the user-service. Find the existing require statements at the very top of the file and add the three new lines shown below:

server.js — top of file
const express = require('express');
const mysql   = require('mysql2');
const bcrypt  = require('bcrypt');
const cors    = require('cors');

// ── ADD THESE THREE LINES ──
const jwt = require('jsonwebtoken');
require('dotenv').config();  // must be before any process.env use
// ──────────────────────────

const app  = express();
const PORT = process.env.PORT || 3001;
🌱 Beginner — where exactly does this go?
Open server.js with nano server.js. The very first lines of the file start with const express = require(...);. Add the new lines after the last existing require() call but before const app = express();.
⚠️
require('dotenv').config() must come before any process.env access. If you load it later, variables will be undefined when the database connection is created.
7
Update database connection to use .env variables

Find your existing mysql.createConnection block and replace the hardcoded values with process.env references:

server.js — database connection
const db = mysql.createConnection({
  host:     process.env.DB_HOST,
  user:     process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME
});
Why? Hardcoded database passwords in source code are one of the most common causes of data breaches. If the code is on GitHub (even a private repo), the credentials are exposed. Environment variables keep secrets out of version control.
8
Update the login endpoint to sign and return a JWT

Find your existing POST /api/auth/login endpoint. Inside the callback, after you verify the bcrypt password, replace the response with this updated block that creates and returns a JWT:

server.js — login endpoint (password verified block)
// --- ADD THIS AFTER bcrypt.compare() succeeds ---

// Create JWT token — payload contains user identity
const token = jwt.sign(
  {
    userId: user.id,
    email:  user.email,
    name:   user.name
  },
  process.env.JWT_SECRET,            // secret key from .env
  { expiresIn: process.env.JWT_EXPIRES_IN || '24h' }
);

// Respond with token — do NOT include the password!
return res.json({
  message: 'Login successful',
  token:   token,
  user: {
    id:    user.id,
    email: user.email,
    name:  user.name
  }
});
🌱 Beginner — what is jwt.sign() doing?

jwt.sign(payload, secret, options) creates a token:

  • payload = the data to put inside the token (userId, email)
  • secret = the private key used to create the signature
  • options = settings, like when it expires
The token is a long string starting with eyJ. The client stores this and sends it with every future request.
⚠️ Trouble: Where exactly do I paste this?
Look for the line const isValidPassword = await bcrypt.compare(...);. Just below the if (!isValidPassword) return block (that sends 401 for wrong password), paste this new block. It runs only when the password is correct.
Part 3 Build the authenticateToken Middleware ⏱ 10 min
9
Write the middleware function

A middleware (a function that runs before a route handler) checks the token on every protected request. Add this function in server.js before any route definitions but after your imports and database setup:

server.js — add before route definitions
// ── JWT AUTHENTICATION MIDDLEWARE ──
function authenticateToken(req, res, next) {
  // Get the Authorization header: "Bearer eyJ..."
  const authHeader = req.headers['authorization'];
  const token      = authHeader && authHeader.split(' ')[1];

  // No token at all → 401 Unauthorized
  if (!token) {
    return res.status(401).json({ error: 'No token provided. Please log in.' });
  }

  // Verify the token using our secret
  jwt.verify(token, process.env.JWT_SECRET, (err, decoded) => {
    if (err) {
      // Token is invalid OR has expired
      return res.status(401).json({ error: 'Invalid or expired token. Please log in again.' });
    }
    // Token is valid — attach decoded user info to the request
    req.user = decoded;  // { userId, email, name, iat, exp }
    next();              // pass control to the actual route handler
  });
}
🌱 Beginner — what does "middleware" mean?
Middleware is like a security guard standing at the door of each protected room. Before you can enter (reach the route handler), you must show your ID (the JWT). If you have no ID or it's fake, the guard turns you away. If it's valid, the guard waves you through.
⚡ Average — the next() function
next() is what passes control to the next function in Express's chain. Calling next() at the end of middleware lets the request continue. If you call res.json() instead, the chain stops — the route handler never runs. This is how we block unauthorised requests.
🚀 Advanced — why split(' ')[1]?
The Authorization header value looks like Bearer eyJ.... We split on the space to get just the token string (index 1). The word "Bearer" is a token type from the OAuth 2.0 standard (RFC 6750) — it signals this is a bearer token, meaning whoever holds it is allowed in.
Part 4 Apply Middleware to Protected Routes ⏱ 10 min
10
Protect order and cart routes

Find your existing order and cart route definitions and add authenticateToken as a second argument before the handler function:

server.js — protecting routes
// ── BEFORE (unprotected) ──
app.get('/api/orders/:userId',  (req, res) => { /* ... */ });
app.post('/api/orders',         (req, res) => { /* ... */ });
app.get('/api/cart/:userId',    (req, res) => { /* ... */ });

// ── AFTER (protected by JWT middleware) ──
app.get('/api/orders/:userId',  authenticateToken, (req, res) => { /* ... */ });
app.post('/api/orders',         authenticateToken, (req, res) => { /* ... */ });
app.get('/api/cart/:userId',    authenticateToken, (req, res) => { /* ... */ });

Also add an ownership check inside the GET /api/orders/:userId handler so users can only see their own orders:

server.js — ownership check inside handler
app.get('/api/orders/:userId', authenticateToken, (req, res) => {
  const userId = parseInt(req.params.userId);

  // ← ADD THIS: user can only read their own orders
  if (req.user.userId !== userId) {
    return res.status(403).json({
      error: 'Access denied. You can only view your own orders.'
    });
  }

  // ... existing code to query and return orders ...
});
🌱 Beginner — leave public routes alone
Do NOT add authenticateToken to routes that should be public: GET /api/menu (anyone should see the menu), POST /api/auth/login (users need to log in to get a token), and POST /api/auth/register. Only protect routes that involve private user data.

Part 5 Test and Verify — The Key Checkpoint ⏱ 13 min
12
Test: no token → 401

Try a protected route with no token. It must now return 401:

Terminal
curl -i http://localhost:8000/api/orders/1
✅ Expected — 401 Unauthorized
HTTP/1.1 401 Unauthorized {"error":"No token provided. Please log in."}
🎯
If you see 401, your middleware is working. The route is now protected.
13
Log in and capture the JWT token

Log in with an existing account to receive a JWT (use an email + password you registered in Lab 3.2):

Terminal
curl -s -X POST http://localhost:8000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"your@email.com","password":"yourpassword"}'
✅ Expected — login returns token
{"message":"Login successful","token":"eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOjEsImVtYWlsIjoidXNlckBleGFtcGxlLmNvbSJ9.XXX","user":{"id":1,"email":"..."}}

Copy the token string (the eyJ... part only). Save it as a shell variable for convenience:

Terminal — save token to variable
TOKEN="eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOjEuLi4XXX"
# Replace the above with your actual token from the login response
⚠️ Trouble: Login returns "Invalid email or password"
Check that you are using credentials that exist in the MySQL users table. If you are not sure, connect to MySQL and list users: docker exec -it cloudeats-mysql mysql -ucloudeats_user -pcloudeats_pass cloudeats -e "SELECT id, email FROM users;"
14
Test: valid token → 200

Now repeat the protected request, this time including the JWT in the Authorization header:

Terminal
curl -i http://localhost:8000/api/orders/1 \
  -H "Authorization: Bearer $TOKEN"
✅ Expected — 200 OK with data
HTTP/1.1 200 OK {"id":1,"userId":1,"items":[...],"total":12.50}
⚠️
Common mistake: Authorization: eyJ... (missing Bearer prefix). The format must be exactly: Bearer followed by a space then the token. If you see "invalid token" double-check you included Bearer .
15
Decode your token at jwt.io (optional visual check)

Visit jwt.io in a browser, paste your token into the debugger, and you will see the three parts decoded. You can confirm your userId, email, and expiry are stored correctly in the payload.

🚀 Advanced — test token expiry
Temporarily change JWT_EXPIRES_IN=1m in your .env file, rebuild the container, log in again, wait 65 seconds, then try the authenticated request. You should receive 401 "Invalid or expired token". Reset back to 24h when done.
🎯 Lab 8.1 Key Checkpoint — all three must pass
  • ✅ curl http://localhost:8000/api/orders/1 (no token) → 401
  • ✅ curl with Authorization: Bearer [valid token] → 200
  • ✅ curl with Authorization: Bearer [tampered/expired token] → 401

When all three pass, your authentication layer is working correctly. Move on to Lab 8.2 to add role-based access control.
