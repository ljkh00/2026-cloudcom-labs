1.2 SELECT — Reading Data 25 min

We build a SELECT query one clause at a time. Each step adds one new piece. Watch the query grow — you will type these in Lab 4.1.

1
All rows, all columns
SELECT *
▶
SQL
SELECT * FROM menu_items;

The * means "give me every column". This returns the full table — all rows, all fields.

2
Pick specific columns
SELECT name, price
▶
SQL
SELECT name, price FROM menu_items;

Only the name and price columns are returned. Reduces data transferred — useful when a table has 20+ columns.

3
Filter rows with WHERE
WHERE category = 'Breakfast'
▶
SQL
SELECT name, price
FROM   menu_items
WHERE  category = 'Breakfast';

WHERE is a filter. Only rows where the condition is true are returned. All other rows are ignored.

4
Add a second condition with AND
AND price < 10
▶
SQL
SELECT name, price
FROM   menu_items
WHERE  category = 'Breakfast'
AND    price < 10;

Both conditions must be true. Use OR if either condition is enough.

5
Sort and limit results
ORDER BY price DESC · LIMIT 3
▶
SQL
SELECT   name, price
FROM     menu_items
ORDER BY price DESC
LIMIT    3;

ORDER BY price DESC = most expensive first. ASC = cheapest first. LIMIT 3 = only return the first 3 rows after sorting.

6
Partial text search with LIKE
LIKE '%Nasi%'
▶
SQL
SELECT name
FROM   menu_items
WHERE  name LIKE '%Nasi%';

The % symbol is a wildcard — it means "any characters here". '%Nasi%' matches Nasi Lemak, Nasi Goreng, Nasi Ayam — anything with "Nasi" anywhere in the name.

🔎
This is how a search bar works. When you type "Nasi" into CloudEats, the API runs a query like this in the background.

1.3 JOIN — Combining Two Tables 20 min

Our data is spread across two tables — users and orders. A JOIN lets us read from both at once, matching rows that belong together.

SQL — JOIN query
SELECT   users.full_name, orders.total_amount, orders.status
FROM     orders
JOIN     users ON orders.user_id = users.id;

Read it aloud: "Start with the orders table. Bring in the users table. Match each order to the user whose id equals the order's user_id. Return the name, total, and status."

INNER JOIN
Only returns rows where a match exists in both tables
A user with no orders? Not shown
Use when: you need complete pairs only
Example: "Show all orders with the customer name"
LEFT JOIN
Returns all rows from the left table, match or not
A user with no orders? Shown, with NULL for order columns
Use when: you want everything, with related data if it exists
Example: "Show all users, and their orders if they have any"
🧠
Rule of thumb: Not sure which to use? Start with LEFT JOIN. You'll see all your data, and NULL values tell you where there's no match. You can always tighten to INNER JOIN once you understand your data.
🟢 Beginner 🔵 Average 🟣 Advanced
🟢 Beginner Focus
A JOIN is like a VLOOKUP in Excel — you're looking up a value from another sheet using a shared ID number. The difference is the database does it for thousands of rows instantly.
🔵 Average Focus
This is why we designed the user_id foreign key in Week 3. Without it, we'd have to store the customer's full name in every order row — wasteful and error-prone if the name changes.
🟣 Advanced Focus
Performance note: JOINs on non-indexed columns are slow on large tables. The ON orders.user_id = users.id is fast because users.id is a primary key (auto-indexed) and you should add an index on orders.user_id.

2.1 Why Not Just Use MySQL for Everything? 10 min

MySQL is excellent at what it does. But not all data fits neatly into tables. Two specific problems arise in CloudEats:

🛒
Problem 1 — Speed
A shopping cart is checked on every page load, every time an item is added, and on checkout. Writing to MySQL for every interaction adds delay. We need something faster — much faster.
Latency issue
📋
Problem 2 — Flexible structure
An order has a variable number of items. Order 101 has 2 items. Order 102 has 5. Storing this in MySQL requires an extra table and complex joins just to read one order.
Schema rigidity
💡
Key idea: "NoSQL" does not mean "no SQL language." It means "Not Only SQL" — we use the right database for each type of problem. This is called polyglot persistence.
2.2 Redis — Key-Value Store 20 min
🎯
One-sentence definition: Redis stores data in RAM (not on disk), so reads and writes happen in under 1 millisecond — thousands of times faster than a regular database.

The three core Redis commands used in CloudEats:

  • SET key valueStore a value. Optionally add EX seconds to set expiry.
  • GET keyRetrieve a value by its key. Returns the value or nothing if it doesn't exist.
  • DEL keyDelete a key-value pair. Used when a customer checks out — cart is cleared.
Redis Shell (redis-cli)
# Store the shopping cart for user 1 (expires in 1 hour)
SET cart:user1 '{"items":[{"id":1,"name":"Nasi Lemak","qty":2}],"total":16.00}' EX 3600

# Read it back
GET cart:user1

# Delete on checkout
DEL cart:user1

# Check how many seconds remain before expiry
TTL cart:user1
✅ Use Redis when
Data is temporary (carts, sessions)
Speed matters more than persistence
Auto-expiry is useful (abandoned carts)
Caching slow database query results
❌ Don't use Redis when
Data must survive a server restart
You need to query across many records
Data has complex relationships
You're storing large files
🟢 Beginner 🔵 Average 🟣 Advanced
🟢 Beginner Focus
Think of Redis as a whiteboard. You write on it quickly, read it quickly, and wipe it when done. It's not for permanent records — it's for things that need to be fast and temporary.
🔵 Average Focus
When Ali adds Nasi Lemak to his cart, it takes under 1ms for Redis to store it. If he abandons the cart, the TTL automatically deletes it after an hour — no orphaned data, no cleanup job.
🟣 Advanced Focus
By default, Redis stores everything in RAM only. If the server crashes, data is lost. For production carts, you'd enable appendonly yes (AOF persistence) or use AWS ElastiCache with Multi-AZ. The trade-off: persistence adds a small write overhead.

2.3 MongoDB — Document Database 20 min
🎯
One-sentence definition: MongoDB stores each record as a self-contained JSON document — no fixed columns, no join required to get all the details of one order.

The four MongoDB shell commands students use in Lab 4.2:

MongoDB Shell (mongosh)
// Insert one order document
db.orders.insertOne({
  userId: 1,
  items: [{ name: "Nasi Goreng", qty: 2, price: 12.00 }],
  total: 12.00,
  status: "pending"
})

// Find all orders for user 1
db.orders.find({ userId: 1 })

// Update an order's status
db.orders.updateOne(
  { _id: orderId },
  { $set: { status: "confirmed" } }
)

// Add a history entry to the status log
db.orders.updateOne(
  { _id: orderId },
  { $push: { statusHistory: { status: "confirmed", timestamp: new Date() } } }
)
  • DocumentOne record in MongoDB. Like a row in MySQL, but it can contain nested arrays and objects. No fixed columns.
  • CollectionA group of documents. Like a table in MySQL, but documents in the same collection can have different fields.
  • _idAuto-generated unique ID for every document. Similar to INT AUTO_INCREMENT in MySQL.
  • $setMongoDB update operator — changes a specific field without touching the rest of the document.
  • $pushMongoDB update operator — appends a new item to an array inside a document.
🟢 Beginner 🔵 Average 🟣 Advanced
🟢 Beginner Focus
A MongoDB document is like a WhatsApp message thread — all the messages (order items) are stored together under one conversation (order). You don't need to look in another folder to find them.
🔵 Average Focus
The statusHistory array inside the document grows every time the order status changes. In MySQL, this would require a separate order_status_history table and a JOIN. In MongoDB, it's just $push — one operation, data stays in one place.
🟣 Advanced Focus
MongoDB's flexible schema is powerful but has risks: if one document stores "status": "PENDING" and another stores "status": "pending", queries break. In production, you'd use schema validation rules ($jsonSchema) or an ODM like Mongoose to enforce consistency.

2.4 Choosing the Right Database 10 min

Not a rigid rule — a conversation. Ask these questions about your data:

Is the data highly structured with consistent fields?
→ MySQL (Relational)
Examples: users, menu items, payment records
Is the data temporary and accessed very frequently?
→ Redis (Key-Value)
Examples: shopping carts, login sessions, API rate limits
Is the data document-like, nested, or evolving in structure?
→ MongoDB (Document)
Examples: orders with items, blog posts with comments
Not sure? Ask: will this data exist in 6 months?
→ If yes → MySQL or MongoDB.
If no → Redis.
🔮
Polyglot persistence — using multiple database types in one application. CloudEats uses MySQL + Redis + MongoDB deliberately. Real-world apps like Grab, Netflix, and Shopee use 4–6 different database technologies. The skill is knowing which tool fits which problem.
DatabaseTypeStores what in CloudEatsWhy this one
MySQLRelationalUsers, menu items, structured ordersConsistent structure, relationships between data
RedisKey-Value (in-memory)Shopping carts, sessionsSub-millisecond speed, TTL auto-expiry
MongoDBDocumentOrder history with nested itemsVariable number of items per order, one read = full data

Quiz Quiz Preparation — Week 4 Topics
📋
These question types are based on the Week 4 learning objectives. Click an answer to check it — the correct answer is revealed after you choose.
1. You want to find all menu items in the 'Drinks' category with a price below RM 5. Which query is correct?
  • SELECT * FROM menu_items WHERE category = 'Drinks' OR price < 5;
  • SELECT * FROM menu_items WHERE category = 'Drinks' AND price < 5;
  • SELECT * FROM menu_items LIMIT 5 WHERE category = 'Drinks';
  • SELECT menu_items WHERE category = 'Drinks' AND price < 5;
2. What is the difference between INNER JOIN and LEFT JOIN?
  • INNER JOIN is faster than LEFT JOIN on all databases
  • LEFT JOIN returns only rows from the right table; INNER JOIN returns both
  • INNER JOIN returns only rows where a match exists in both tables. LEFT JOIN returns all rows from the left table, with NULL in the right-side columns if there is no match.
  • They are identical — just different syntax for the same result
3. True or False: Redis persists data to disk by default. If the Redis container is restarted, all shopping carts are still there.
  • True — Redis writes everything to disk automatically
  • False — Redis stores data in RAM by default. If the container stops, all data is lost unless persistence (AOF or RDB snapshots) is explicitly enabled. This is acceptable for shopping carts — a restarted server simply means customers start a fresh cart.
4. A CloudEats order has 2 items. Another has 7 items. Another has 0 items (the customer changed their mind). Which database is the best fit for storing these orders with their items?
  • MySQL — because orders are structured data and we already have the orders table
  • Redis — because we want orders to be retrieved quickly
  • MongoDB — because each order has a variable number of items. In MongoDB, the items array can have 0, 2, or 7 entries inside one document. No separate table or JOIN is needed — one read returns the full order.
  • Any database works equally — the number of items does not affect the choice
5. What does SET cart:user5 '{"items":[...]}' EX 1800 do in Redis?
  • Stores the cart permanently for user 5 and limits the cart to 1800 items
  • Stores the shopping cart JSON under the key "cart:user5" and sets a Time To Live of 1800 seconds (30 minutes). After 30 minutes, Redis automatically deletes the key — no code needed.
  • Stores the cart and checks for 1800 duplicate items before saving
  • EX 1800 means the cart is encrypted with a 1800-bit key
6. Scenario: The CloudEats team wants to find all customers who have placed at least one order. Which SQL approach is correct?
  • SELECT * FROM users LEFT JOIN orders ON users.id = orders.user_id WHERE orders.id IS NULL;
  • SELECT DISTINCT users.full_name FROM users INNER JOIN orders ON users.id = orders.user_id; — INNER JOIN only returns users who have a matching row in orders. DISTINCT removes duplicates if they placed multiple orders.
  • SELECT * FROM orders WHERE user_id EXISTS;
  • SELECT * FROM users WHERE orders = TRUE;
