Overview
Scenario & Goals
📖
The story: Ali Hassan is hungry. He opens CloudEats, adds Nasi Lemak and Teh Tarik to his cart, and places the order. Behind the scenes, two completely different databases are involved — for two completely different reasons. Today you play both databases manually, so you see exactly what each one holds and why.
🧠
Today's focus: Not the commands. The difference in how Redis and MongoDB store data, and why each is the right tool for its job. The commands are just a way to see that difference in action.

What you will accomplish:

  • Add Redis and MongoDB services to docker-compose.yml
  • Store and retrieve a shopping cart in Redis using SET and GET
  • Set a TTL and watch a key expire automatically
  • Insert a full order document into MongoDB with nested items
  • Update an order's status and add a history entry with $push
  • Run the full cart → place order → clear cart flow
  • Explain in your own words why the cart is in Redis but the order is in MongoDB
  • Identify where each database fits in the CloudEats architecture
Part 1
Add Redis & MongoDB to Docker Compose
⏱ 10 min
8 steps across 4 parts
1
Add two new services to docker-compose.yml
▶

Open your docker-compose.yml. Add the redis and mongo blocks inside the services: section, alongside your existing db and backend services.

yaml · Add inside services:
  # ── Add these two services ─────────────────────

  redis:
    image: redis:7-alpine
    container_name: cloudeats-redis
    ports:
      - "6379:6379"
    networks:
      - cloudeats-network

  mongo:
    image: mongo:7
    container_name: cloudeats-mongo
    ports:
      - "27017:27017"
    volumes:
      - mongo-data:/data/db
    networks:
      - cloudeats-network

Also add mongo-data to the volumes: section at the bottom of the file:

yaml · Under volumes:
volumes:
  mysql-data:    # already exists
  mongo-data:    # ← add this line
🔍 Why is Redis using alpine but MongoDB is not?
redis:7-alpine uses the minimal Alpine Linux base image — smaller and faster to download, fine for Redis since it has no complex dependencies. mongo:7 uses the full Debian base because MongoDB's tooling expects a fuller environment. You'll see this pattern often: use -alpine where possible to keep images small.
🔍 Why does MongoDB have a named volume but Redis does not?
Orders are permanent records — we need them to survive a container restart. MongoDB needs a volume for persistence. Redis carts are temporary — if Redis restarts, carts reset. That's acceptable. Customers just start a new cart. No data loss that matters.

Start the new services:

bash
docker compose up -d redis mongo
Verify all containers are running
docker compose ps NAME STATUS PORTS cloudeats-backend Up 0.0.0.0:3000->3000/tcp cloudeats-db Up 3306/tcp cloudeats-mongo Up 0.0.0.0:27017->27017/tcp cloudeats-redis Up 0.0.0.0:6379->6379/tcp
🔴 Port 27017 already in use
▶
Another MongoDB instance may be running on your machine. Stop it first, or change the host port mapping to "27018:27017" in docker-compose.yml. The container still uses 27017 internally — only the host port changes.

Part 2
⚡ Redis — The Shopping Cart
⏱ 15 min
💡
The idea before you start: Redis is like a whiteboard. Writing and reading happen in under 1 millisecond. You write a note, read it back, and wipe it when done. It is not for permanent storage — it is for data that needs to be very fast and temporary.
2
Enter the Redis shell
▶
bash
docker exec -it cloudeats-redis redis-cli
You should see the Redis prompt
127.0.0.1:6379>
🔍 What's different from the MySQL shell?
In MySQL you typed SQL sentences. In Redis you type command + key + value — short, direct instructions. There is no schema, no tables, no column definitions. Redis is deliberately simple: give it a name (key) and a value, and it remembers it — until you delete it or it expires.
🔴 "No such container" error
▶
Run docker compose ps and use the exact Redis container name from the output. It may be cloudeats-redis or follow the project-service-1 pattern like cloudeats-app-redis-1.
3
Store Ali's shopping cart — SET and GET
▶

Ali adds Nasi Lemak and Teh Tarik to his cart. Store the cart:

Redis shell · Store the cart
SET cart:user1 '{"items":[{"name":"Nasi Lemak","qty":2,"price":8.00},{"name":"Teh Tarik","qty":1,"price":3.00}],"total":19.00}'
OK

Read the cart back:

Redis shell · Read the cart
GET cart:user1
"{\"items\":[{\"name\":\"Nasi Lemak\",\"qty\":2,\"price\":8.00},{\"name\":\"Teh Tarik\",\"qty\":1,\"price\":3.00}],\"total\":19.00}"
🔍 What is cart:user1?
cart:user1 is just a key name — a string we invented. The colon in the middle is a naming convention (like a folder path) to group related keys. The value is the entire cart stored as a JSON string. Redis does not know or care what the JSON contains — it just stores and returns the whole string as-is. The application code is responsible for parsing it.
🟢 Beginner
Think of it as a labelled box. The label is cart:user1. The contents are the JSON string. You put things in by label (SET), take them out by label (GET). That's the entire Redis data model.
🔵 Average
Try storing a second user's cart: SET cart:user2 '{"items":[],"total":0}'. Each user gets their own key. This is how Redis separates data between users — by key naming, not by table rows.
4
Set an expiry — TTL (Time To Live)
▶

Overwrite the cart with an expiry time of 60 seconds, so you can watch it disappear:

Redis shell · Set cart with 60-second TTL
SET cart:user1 '{"items":[{"name":"Nasi Lemak","qty":2,"price":8.00}],"total":16.00}' EX 60

Check how many seconds are left:

Redis shell · Check remaining seconds
TTL cart:user1
(integer) 54

Run TTL cart:user1 a few more times — watch the number count down. After 60 seconds, run GET cart:user1:

Redis shell · After expiry
GET cart:user1
(nil)
🔍 What just happened — and why does it matter?
Redis automatically deleted the key when the timer ran out. No code ran. No scheduled job fired. Redis handles expiry internally.

This solves a real problem: abandoned carts. If Ali adds items to his cart and never checks out, the cart disappears by itself after 30 minutes (or 1 hour in production). Without TTL, you'd need a scheduled script to clean up expired carts — extra code, extra complexity, more things to break.
❗
A TTL of -1 means the key has no expiry — it stays until you delete it. A TTL of -2 means the key does not exist. Run TTL cart:user1 after the key expires and you'll see -2.
🟣 Advanced
In production, the cart TTL would be set in the application code as an environment variable (e.g. CART_TTL=1800 for 30 minutes). Changing the TTL would require only a config change and restart — no database migration, no schema change.
📸
Student Screenshot · TTL countdown in Redis shell
Three consecutive terminal commands and their output: TTL cart:user1 returning 54, then 41, then (after expiry) GET cart:user1 returning (nil). This sequence shows auto-expiry in action.
✅
Part 2 Checkpoint You've stored a cart, read it, watched it expire automatically. The key concept: Redis is fast and temporary. TTL means you never have to clean up old carts manually. Type exit to leave the Redis shell.
Part 3
📦 MongoDB — The Order History
⏱ 15 min
💡
The idea before you start: An order is permanent — it must survive restarts, backups, and audits. It also has a variable number of items and a growing status history. MongoDB stores the whole order as one self-contained document, so one read gives you everything about an order without any JOIN.
5
Enter the MongoDB shell
▶
bash · Open a new terminal tab first
docker exec -it cloudeats-mongo mongosh
You'll see the MongoDB shell prompt
Current Mongosh Log ID: ... Connecting to: mongodb://127.0.0.1:27017/ test>

Switch to the CloudEats database (MongoDB creates it automatically if it doesn't exist):

mongosh
use cloudeats_db
switched to db cloudeats_db cloudeats_db>
🔍 What's different from MySQL and Redis?
In MySQL you used SQL. In Redis you used short commands. In MongoDB you use JavaScript-like method calls — db.orders.find(), db.orders.insertOne(). The db refers to the current database. orders is the collection (like a table). The method says what to do.
6
Place an order — insertOne with nested items
▶

Ali places his order. The entire order — including all items — goes into one document:

mongosh · Insert one order
db.orders.insertOne({
  userId: 1,
  customerName: "Ali Hassan",
  items: [
    { name: "Nasi Lemak", qty: 2, price: 8.00  },
    { name: "Teh Tarik",  qty: 1, price: 3.00  }
  ],
  total: 19.00,
  status: "pending",
  deliveryAddress: "No. 12, Jalan Bukit Bintang, KL",
  placedAt: new Date()
})
{ acknowledged: true, insertedId: ObjectId('64f1a2b3c4d5e6f7a8b9c0d1') }
🔍 Notice the items array — this is the key difference
The items field holds an array of objects directly inside the order document. Order 101 might have 2 items. Order 102 might have 7. MongoDB doesn't care — each document can have a different number of items. In MySQL, you'd need a separate order_items table and a JOIN every time you read an order. Here, one read returns the complete picture.

Read the order back — see the full document:

mongosh · Find all orders
db.orders.find().pretty()
🔍 What is .pretty()?
Without .pretty(), the document prints on one long line — hard to read. .pretty() formats it with indentation so the nested structure is clearly visible. In newer versions of mongosh, output is already formatted by default.
📸
Student Screenshot · MongoDB insertOne + find result
Terminal showing the insertOne output with the auto-generated ObjectId, then db.orders.find().pretty() displaying the full document with the items array visible as nested objects. Highlight that the items array is inside the single document.
7
Update the order status and record its history
▶

The restaurant confirms the order. Update the status field:

mongosh · Update order status
db.orders.updateOne(
  { userId: 1 },
  { $set: { status: "confirmed" } }
)
{ acknowledged: true, matchedCount: 1, modifiedCount: 1 }

Now add a status history entry so the customer can track their order:

mongosh · Push a history entry into the order
db.orders.updateOne(
  { userId: 1 },
  { $push: {
      statusHistory: {
        status: "confirmed",
        at: new Date()
      }
  }}
)

Read the order again to see both changes:

mongosh
db.orders.find({ userId: 1 }).pretty()
🔍 What do $set and $push do — and why not just rewrite the whole document?
$set changes only the status field. Everything else in the document — items, total, address — is untouched. You're performing a surgical update, not replacing the whole record.

$push appends a new object to the statusHistory array. Every time the status changes, you push a new entry. After delivery, the history might have 5 entries: pending → confirmed → preparing → out_for_delivery → delivered. All of these live inside the same single document. In MySQL, each of these would be a separate row in a separate table.
🟢 Beginner
Think of $push like adding a new message to a WhatsApp thread. The thread is the order document. Each status update is a new message appended to the history inside it. The thread (document) grows over time without needing a new file.
🟣 Advanced
MongoDB's $push with $sort and $slice lets you push to an array while keeping it sorted and capped at a max size — useful for "last 10 events" patterns without ever reading and rewriting the whole array.
📸
Student Screenshot · Order with status + statusHistory
The find().pretty() output after both updates, showing "status": "confirmed" and a statusHistory array containing one entry with the status string and timestamp. The nested structure shows items array and statusHistory array coexisting in one document.
✅
Part 3 Checkpoint You've inserted an order with nested items, updated a field with $set, and grown an array with $push — all inside one document. The key concept: one document holds the complete, evolving state of one order.
Part 4
The Full Flow — Cart to Order to Clear
⏱ 15 min
🔄
Now put both databases together. Run this flow manually — the same sequence that happens automatically when a customer places an order in a real app. Use two terminal tabs: one for Redis, one for MongoDB.
8
Simulate the full customer journey across both databases
▶
1
⚡ Redis shell
Siti adds Roti Canai to her cart.
redis-cli
SET cart:user2 '{"items":[{"name":"Roti Canai","qty":2,"price":3.50}],"total":7.00}' EX 3600
2
⚡ Redis shell
She reviews her cart before checking out.
redis-cli
GET cart:user2
3
📦 mongosh
She confirms the order. The cart contents become a permanent MongoDB document.
mongosh
db.orders.insertOne({
  userId: 2,
  customerName: "Siti Aminah",
  items: [{ name: "Roti Canai", qty: 2, price: 3.50 }],
  total: 7.00,
  status: "pending",
  placedAt: new Date()
})
4
⚡ Redis shell
Checkout complete — delete the cart. Redis is cleared immediately.
redis-cli
DEL cart:user2
GET cart:user2   # should return (nil)
5
📦 mongosh
The order is still here — permanently stored. Update its status as the kitchen works.
mongosh
db.orders.updateOne(
  { userId: 2 },
  { $set: { status: "preparing" } }
)
db.orders.find({ userId: 2 }).pretty()
🔍 The most important thing you just did
Step 3 is the checkout moment. The cart — which lived in Redis — became an order in MongoDB. The cart was temporary. The order is permanent. After step 4, the cart is completely gone from Redis. But the order in MongoDB stays forever, trackable, updatable, retrievable years later. This transition is the architectural boundary between Redis and MongoDB.
📸
Student Screenshot · Two terminals side by side
Two terminal windows open: (Left) Redis shell showing DEL cart:user2 → 1 then GET cart:user2 → (nil). (Right) MongoDB shell showing db.orders.find({userId:2}).pretty() with the full order document still present. The contrast — cart gone, order permanent — is the key visual.
✅
Part 4 Checkpoint Cart is gone from Redis. Order is alive in MongoDB. The flow is: Redis holds the working state → MongoDB holds the permanent record. Two databases, one journey.
Part 5
Redis vs MongoDB — The Comparison
⏱ 5 min
🧠
Stop and think: You've used both databases. Before reading the table below, try to answer this: why is the cart in Redis but the order in MongoDB? If you can answer that in your own words, you understand the lesson.
Topic ⚡ Redis (Shopping Cart) 📦 MongoDB (Orders)
How long does the data last? Minutes to hours. TTL deletes it automatically. Permanently. Survives restarts. Stored on disk.
What is stored? One JSON string per user. Simple key → value. Full document with nested items array, status history, addresses.
How fast is it? Under 1ms. Lives in RAM. Milliseconds. Lives on disk with indexing.
What happens if the container restarts? Cart is lost. Customer starts a fresh cart. Order is safe. Named volume preserves the data.
Can items vary per record? The JSON string can contain anything — but Redis doesn't query inside it. Yes. Each order document can have a different number of items. MongoDB can query inside the array.
Cloud equivalent AWS ElastiCache, Azure Cache for Redis MongoDB Atlas, AWS DocumentDB

Experiment 2 — Query by status in MongoDB

Insert two more orders, then filter by status — like a WHERE clause, but for documents:

mongosh
// Add a delivered order
db.orders.insertOne({ userId: 3, status: "delivered", total: 45.00, items: [], placedAt: new Date() })

// Find only pending orders
db.orders.find({ status: "pending" }).pretty()

// Find orders with total above RM 15
db.orders.find({ total: { $gt: 15 } }).pretty()

// Count total orders in the collection
db.orders.countDocuments()
🏆
Challenge: Can you find all orders that contain "Nasi Lemak" in their items array? Hint: look up $elemMatch in MongoDB. This is the power of document databases — you can query inside nested arrays without a JOIN.
Wrap-Up
What to Remember
🧠
The one question that captures the whole lab:
Why is the cart in Redis but the order in MongoDB?

Answer: The cart is temporary and needs to be fast — Redis stores it in RAM with auto-expiry. The order is permanent and has a complex nested structure — MongoDB stores it as a document that can hold a variable number of items and a growing status history, all in one place.
