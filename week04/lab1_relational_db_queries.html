Overview
Scenario & Goals
📖
The story: The CloudEats manager walks over. "Can you pull the breakfast items under RM 10? Also — which customers placed orders? And add Laksa Sarawak to the menu." The database is live. No one needs to change any code. You just need to ask the right questions — in SQL.
🧠
Remember: You do not need to memorise this SQL syntax. Focus on the idea — a database is a structured store you can interrogate with questions. The syntax is something you look up. The thinking is what matters.

What you will accomplish today:

  • Connect directly to the running MySQL container
  • Explore tables and column definitions with DESCRIBE
  • Filter rows using WHERE and AND
  • Sort results with ORDER BY and limit them with LIMIT
  • Search text with LIKE and the % wildcard
  • Combine the users and orders tables with JOIN
  • Add a new menu item with INSERT
  • Explain the difference between INNER JOIN and LEFT JOIN
Part 1
Get Into MySQL
⏱ 10 min
8 steps across 4 parts
1
Check your containers are running
▶

Open a terminal. Navigate to your project folder and check that the database container is up.

bash
cd ~/cloudeats-app
docker compose ps
Expected output — look for db with status Up
NAME STATUS PORTS cloudeats-backend Up 0.0.0.0:3000->3000/tcp cloudeats-db Up 3306/tcp
🔴 db container is not running
▶
Run docker compose up -d db to start only the database container. Wait 15–20 seconds for MySQL to initialise, then run docker compose ps again to confirm it's Up.
2
Enter the MySQL shell inside the container
▶

We use docker exec to run the MySQL client inside the running container.

bash
docker exec -it cloudeats-db mysql -u cloudeats_user -pcloudeats_password cloudeats_db
🔍 What does this command do?
docker exec -it opens an interactive terminal session inside the running container.
mysql is the MySQL command-line client, already installed inside the MySQL container.
-u cloudeats_user is the username. -p... is the password (no space between flag and password).
cloudeats_db is the database to connect to. You land directly inside it.
You should see the MySQL prompt
Welcome to the MySQL monitor. Commands end with ; or \g. mysql>
⚠️
Every SQL command you type must end with a semicolon ; before pressing Enter. Without it, MySQL waits for more input. If you accidentally press Enter without a semicolon, just type ; on the next line and press Enter again.
📸

🔴 "No such container" error
▶
Your container might have a slightly different name. Run docker compose ps and copy the exact name of the db container from the output, then replace cloudeats-db in the command above.

Part 2
See What's There
⏱ 10 min
3
Create and seed the users and orders tables
▶

init.sql only created menu_items back in Week 3. For this lab we also need a users table and an orders table with some sample rows, so the JOIN queries later in this lab return real results. Paste this at the mysql> prompt:

💡
This subject focuses on cloud, not database design — so table creation and SQL syntax aren't deep-dived here. Copy the statements below to move forward, but take initiative to read up on CREATE TABLE, FOREIGN KEY, and INSERT on your own if they're unfamiliar.
SQL · Create users and orders tables
CREATE TABLE IF NOT EXISTS users (
  id INT AUTO_INCREMENT PRIMARY KEY,
  full_name VARCHAR(100) NOT NULL
);

CREATE TABLE IF NOT EXISTS orders (
  id INT AUTO_INCREMENT PRIMARY KEY,
  user_id INT NOT NULL,
  total_amount DECIMAL(6,2) NOT NULL,
  status VARCHAR(20) NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id)
);

Now insert the sample rows used throughout this lab:

SQL · Seed sample data
INSERT INTO users (full_name) VALUES
  ('Ali Hassan'), ('Siti Aminah'), ('Rajan Kumar');

INSERT INTO orders (user_id, total_amount, status) VALUES
  (1, 26.00, 'delivered'),
  (1, 14.00, 'pending'),
  (2, 12.00, 'confirmed');
🔍 What does this do?
users.id auto-increments, so Ali Hassan becomes id = 1, Siti Aminah id = 2, Rajan Kumar id = 3 — in insertion order. The FOREIGN KEY on orders.user_id means MySQL will refuse to insert an order pointing to a user_id that doesn't exist in users. This is the same user_id column you'll JOIN against in Part 4.
⚠️
Rajan Kumar (id = 3) deliberately has no orders. You'll use this in Part 4's LEFT JOIN discussion — an INNER JOIN will never show him, but a LEFT JOIN will.
🔴 "Table 'orders' already exists" or duplicate rows
▶
If you run the INSERT statements twice, you'll get duplicate rows (auto_increment keeps counting up). Run DELETE FROM orders; DELETE FROM users; first if you need to start over, or just check with SELECT * FROM users; before inserting again.
4
List tables, then inspect a table's structure
▶

Before writing queries, confirm what tables exist and what columns they contain.

SQL · List all tables
SHOW TABLES;
+----------------------+ | Tables_in_cloudeats_db | +----------------------+ | menu_items | | orders | | users | +----------------------+
SQL · Inspect the menu_items table
DESCRIBE menu_items;
+------------+--------------+------+-----+---------+----------------+ | Field | Type | Null | Key | Default | Extra | +------------+--------------+------+-----+---------+----------------+ | id | int | NO | PRI | NULL | auto_increment | | name | varchar(100) | YES | | NULL | | | category | varchar(50) | YES | | NULL | | | price | decimal(6,2) | YES | | NULL | | | available | tinyint(1) | YES | | 1 | | +------------+--------------+------+-----+---------+----------------+
🔍 What does DESCRIBE tell us?
Each row is one column in the table. The Field column is the column name. Type is what kind of data it holds — varchar is text, decimal is a precise number (good for prices), tinyint(1) is a yes/no flag. The Key: PRI shows id is the primary key. auto_increment means MySQL assigns the next number automatically — you never set it yourself.
🟢 Beginner
DESCRIBE is like reading the column headers of a spreadsheet before you start using it. It tells you what information this table is capable of holding.
🟣 Advanced
Run DESCRIBE users; and DESCRIBE orders; as well. Notice orders.user_id — this is the foreign key column that links to users.id. You will use this in Part 4 to JOIN the two tables.
✅
Part 2 Checkpoint You created and seeded users and orders, and confirmed all three tables exist. menu_items has columns: id, name, category, price, available. Move to Part 3.
Part 3
SELECT — Ask the Database Questions
⏱ 15 min
💡
The idea: SELECT is how you read from a database. Every time you open the CloudEats menu in the browser, a SELECT runs in the background. You are now doing manually what the app does automatically.
5
Filter rows with WHERE
▶

The manager wants Breakfast items only. Add a WHERE clause to filter:

SQL
SELECT name, price
FROM   menu_items
WHERE  category = 'Breakfast';
🔍 What happened?
MySQL scanned every row in menu_items. For each row, it checked: is category equal to 'Breakfast'? Only the rows that passed the test appear in the result. The others were silently skipped. This is the core job of WHERE — it is a filter, not a search engine.

Now tighten it — the manager said under RM 10. Add a second condition:

SQL
SELECT name, price
FROM   menu_items
WHERE  category = 'Breakfast'
AND    price < 10;
💡 AND vs OR
AND — both conditions must be true. The item must be Breakfast and cost under RM 10.
OR — either condition is enough. Show me Breakfast items or anything under RM 5.
Think of AND as narrowing the result. Think of OR as widening it.

6
Sort and limit with ORDER BY and LIMIT
▶

Show the most expensive items first, but only the top 3:

SQL
SELECT   name, price
FROM     menu_items
ORDER BY price DESC
LIMIT    3;
🔍 What happened?
ORDER BY price DESC sorted all rows — highest price first. DESC = descending (biggest → smallest). ASC = ascending (smallest → biggest). LIMIT 3 then cut the result to the first three rows after sorting. Think of it as: sort the entire pile, then hand me only the top 3.
🟢 Beginner
ORDER BY + LIMIT is how leaderboards work. "Show me the top 10 highest-scoring players" is exactly this pattern — sort by score descending, limit to 10.
🔵 Average
Change DESC to ASC and observe the result flip. Then try sorting by name ASC — the items appear alphabetically. The column you sort by does not have to appear in your SELECT list.
7
Search text with LIKE and the % wildcard
▶

Find every menu item that contains the word "Nasi" anywhere in its name:

SQL
SELECT name, category, price
FROM   menu_items
WHERE  name LIKE '%Nasi%';
🔍 What does % mean?
% is a wildcard — it means "any text here, of any length." '%Nasi%' matches anything with "Nasi" anywhere: Nasi Lemak, Nasi Goreng, Ayam Nasi. 'Nasi%' would only match names that start with "Nasi". '%Goreng' would only match names that end with "Goreng".
🌐 Real-world connection
When you type "Nasi" into a search bar on any website and results appear as you type, the server is running a query like this — usually LIKE '%your_text%' — against the database. The percent signs are what make partial matches work.
🟣 Advanced
LIKE with leading % (e.g. '%Nasi') cannot use a column index, so it performs a full table scan — slow on millions of rows. Production search features use a dedicated full-text search engine (Elasticsearch, MySQL FULLTEXT index) instead of LIKE. For CloudEats at this scale, LIKE is fine.
✅
Part 3 Checkpoint You can filter, sort, and search your menu data. The key idea: WHERE filters rows in or out. ORDER BY controls the order. LIKE searches inside text. Proceed to Part 4.
Part 4
JOIN — Combine Two Tables
⏱ 15 min
💡
The idea: The orders table stores a user_id number — not the customer's name. The actual name lives in the users table. A JOIN brings both together in one result, matching orders to the right customer automatically.
8
JOIN orders with users to see customer names
▶

First, look at the orders table on its own — notice it has user_id numbers, not names:

SQL · Orders alone — ID numbers only
SELECT id, user_id, total_amount, status
FROM   orders;
+----+---------+--------------+-----------+ | id | user_id | total_amount | status | +----+---------+--------------+-----------+ | 1 | 1 | 26.00 | delivered | | 2 | 1 | 14.00 | pending | | 3 | 2 | 12.00 | confirmed | +----+---------+--------------+-----------+

Now run the JOIN — the names appear alongside the orders:

SQL · JOIN to get the customer name
SELECT   users.full_name,
         orders.total_amount,
         orders.status
FROM     orders
JOIN     users ON orders.user_id = users.id;
+-------------+--------------+-----------+ | full_name | total_amount | status | +-------------+--------------+-----------+ | Ali Hassan | 26.00 | delivered | | Ali Hassan | 14.00 | pending | | Siti Aminah | 12.00 | confirmed | +-------------+--------------+-----------+
🔍 What happened — and why?
MySQL looked at each row in orders. For each order, it took the user_id number and found the matching row in users where users.id equals that number. Then it merged both rows into one result row. Ali Hassan appears twice because he placed two orders — both match his id = 1. This is why we stored a user_id foreign key instead of copying the name into every order row.
💡 INNER JOIN vs LEFT JOIN — the difference that matters
The JOIN you wrote above is an INNER JOIN. It only shows orders that have a matching user. If an order had a broken user_id that pointed to no one, that order would not appear.

A LEFT JOIN shows every row from the left table (orders) regardless — even if there's no match on the right. A user with no orders would appear with NULL in the order columns.

The concept, not the syntax, is the exam point — which join keeps all rows, and which keeps only matched pairs.
📸
Student Screenshot · JOIN result
Your terminal showing the result of the JOIN query — customer names appearing alongside order amounts and statuses. Ali Hassan should appear twice (two orders). If you have more seed data, more rows may appear.
🟢 Beginner
Imagine having two separate Excel sheets — one for orders, one for customers. JOIN is doing an automatic VLOOKUP across both sheets based on the ID column. The database does this for every row instantly.
🔵 Average
Notice we write orders.user_id and users.id — the table name prefix avoids ambiguity when both tables have a column with the same name (like id). Without the prefix, MySQL would ask: "which table's id?"
🟣 Advanced
Try: SELECT users.full_name, COUNT(orders.id) AS total_orders FROM users LEFT JOIN orders ON users.id = orders.user_id GROUP BY users.id; — this shows every user and how many orders they've placed, including users with zero orders (they show 0, not nothing).
🔴 "Column 'id' in ON clause is ambiguous" error
▶
Both tables have a column named id. MySQL doesn't know which you mean. Always prefix with the table name: orders.user_id = users.id, not just user_id = id.
✅
Part 4 Checkpoint You can see customer names next to their order amounts. The key idea: JOIN links two tables using a shared ID column. Without it, you'd have to query each table separately and connect the dots manually.
Part 5
INSERT — Add a New Menu Item
⏱ 10 min
9
Add Laksa Sarawak to the menu
▶

The manager asked us to add Laksa Sarawak to the menu. One SQL command does this:

SQL
INSERT INTO menu_items (name, category, price, available)
VALUES ('Laksa Sarawak', 'Main', 11.50, 1);
🔍 What happened — and what about the id?
MySQL added a new row with the name, category, price, and available flag we provided. We did not specify the id — we left it out of the column list intentionally. Because the column is AUTO_INCREMENT, MySQL automatically assigned the next available integer. The new item gets its own unique ID without any effort from us.

Verify it was added:

SQL
SELECT * FROM menu_items WHERE name = 'Laksa Sarawak';
+----+---------------+----------+-------+-----------+ | id | name | category | price | available | +----+---------------+----------+-------+-----------+ | 11 | Laksa Sarawak | Main | 11.50 | 1 | +----+---------------+----------+-------+-----------+
🌐
Now open your browser and go to http://localhost:3000. If the frontend fetches the menu from the database, Laksa Sarawak appears on the menu automatically — no rebuild, no redeploy. This is the whole point of separating data from code.
📸
Student Screenshot · Laksa Sarawak in the Browser
Two screenshots side by side: (Left) The SELECT result in the MySQL shell confirming Laksa Sarawak was inserted with its auto-generated ID. (Right) The CloudEats menu page in the browser showing Laksa Sarawak now appearing in the menu list without any code change.
🟣 Advanced — What if you insert a duplicate?
Try inserting "Laksa Sarawak" a second time. It works — MySQL happily creates a second row with a new ID. To prevent duplicates, you'd add a UNIQUE constraint on the name column (as done for the email column in users). The database enforces uniqueness, not just the application code.

🟣 Advanced Extension UPDATE, DELETE and a small challenge — 15 min

Completed Parts 1–5 with time to spare? Try these. They are not required — they are for students who want to push further.

UPDATE — change an existing row

SQL · Change a price
UPDATE menu_items
SET    price = 12.50
WHERE  name = 'Laksa Sarawak';
⚠️
Always include WHERE in an UPDATE. UPDATE menu_items SET price = 0; without WHERE sets every menu item's price to zero. MySQL will not ask you to confirm — it just does it.

DELETE — remove a row

SQL · Remove a specific item
DELETE FROM menu_items
WHERE       name = 'Laksa Sarawak';

Wrap-Up
What You Learned — and What to Remember
🧠
What to remember — not the syntax, the concepts:
WHERE = filter. Only rows that pass the test appear.
ORDER BY + LIMIT = sort, then take the top N.
LIKE %text% = find rows where a column contains that text anywhere.
JOIN = combine two tables on a shared ID column. INNER = only matches. LEFT = all rows from the left side.
INSERT = add a row. AUTO_INCREMENT handles the ID automatically.
