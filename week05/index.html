1.1 Where We Are Now — The CloudEats Monolith 15 min

You have spent four weeks building the CloudEats Food Ordering App. Look at what lives inside backend/server.js right now — one file, one process, three databases, 500+ lines.

backend/server.js — the monolith
// 500+ lines · everything in one file · one process
const express  = require('express');
const mysql    = require('mysql2');
const redis    = require('redis');
const mongodb  = require('mongodb');

// ── USER ROUTES (bcrypt, JWT, MySQL) ──
app.post('/api/auth/register', ...);
app.post('/api/auth/login', ...);

// ── MENU ROUTES (MySQL) ───────────────
app.get('/api/menu', ...);

// ── CART ROUTES (Redis) ───────────────
app.get('/api/cart/:userId', ...);

// ── ORDER ROUTES (MongoDB) ────────────
app.post('/api/orders', ...);
// All in ONE file ← this is the monolith

This is a monolithic architecture. For a course project, it is perfectly fine. For a real business serving thousands of customers, it becomes a serious problem.

🟢 Beginner 🔵 Average 🟣 Advanced
🟢 Beginner — The Restaurant Kitchen
Imagine one cook in a tiny kitchen doing everything — taking orders, cooking, washing dishes, handling payments — all at the same time. When the restaurant gets busy, everything slows down because one person is the bottleneck. A monolith is exactly that kitchen. Microservices means splitting roles: one cook for starters, one for mains, one for desserts.
🔵 Average — One Process, All Problems
A monolith runs as a single OS process. One process means one memory space, one restart cycle, one deployment pipeline. If you update the menu feature, you redeploy everything — including auth code that hasn't changed. Any deployment, however small, touches 100% of production.
🟣 Advanced — Blast Radius
Every change has a blast radius — the potential area of damage if something goes wrong. A bug in cart code can crash user registration. The blast radius of every deployment is 100% of production traffic. Microservices reduce the blast radius of each deployment to only the service being changed.
1.2 What Goes Wrong as the Monolith Grows 20 min

Imagine CloudEats hires 15 developers split into three teams — User team, Menu team, Orders team. Within weeks:

❌ Monolith Growing Pains
Team A and Team B edit the same server.js — merge conflicts every day
Menu needs 8× CPU at lunch rush — must scale the entire app (including auth) at 3× cost
Cart bug crashes the app — users cannot log in or browse the menu
Team C wants Python for analytics — impossible, whole app is Node.js
One-line bug fix requires full 20-minute QA cycle for the entire app
✅ Microservices Fix
Team A owns User Service. Team B owns Menu Service. No shared files — no conflicts
Scale Menu Service to 8 copies, User stays at 1. Pay only for what you need
Cart Service crashes — users can still log in and browse. Fault is isolated
Team C builds analytics in Python — other teams stay in Node.js
Bug fix in Menu Service deploys in 3 minutes, touches zero other services

🟣 Advanced — Conway's Law
Melvin Conway (1967): "Any organisation that designs a system will produce a design whose structure is a copy of the organisation's communication structure." Three teams → three services is not just technical convenience. It is how organisations naturally communicate. Microservices-first thinking aligns technical structure with team structure, reducing friction by design.
1.3 Trade-offs — Microservices Are Not Always the Right Choice 15 min
⚠️
Important: Microservices are not a silver bullet. The industry trend can make them sound mandatory. Monoliths are the correct choice for small teams and early-stage products. Earn the split through pain — don't start with it.
✅ When Microservices Make Sense
Multiple teams working on the same codebase simultaneously
Different parts have radically different scaling needs
Different parts need different technology stacks
Need to deploy parts multiple times per day independently
The monolith is causing measurable, documented pain
❌ When Microservices Hurt
Small team (1–5 developers) — overhead costs more than it saves
Early-stage product — you don't know the right boundaries yet
No CI/CD pipeline — manual deployment of 10 services is a nightmare
Limited DevOps experience — distributed systems are harder to operate
Network latency adds up — 10 service calls vs 10 function calls
💡
The Martin Fowler Rule: Don't start with microservices. Build a monolith first, understand your domain, feel the pain — then split. Premature splitting creates a distributed monolith — the worst of both worlds: all the complexity of microservices, none of the independence.

🎯
Database per service — the most important rule: Each service owns its database. If Order Service needs user data, it calls the User Service API — it does not query the users table directly. This rule enforces loose coupling and is the single most important design principle in microservices.
2.1 What Makes a Good Service Boundary 20 min

A service boundary defines what one microservice owns — and more critically, what it does not own. Getting boundaries wrong creates a distributed monolith: services deployed separately but so tightly coupled they must still be deployed together.

🔑
The rule: Map each service to a business capability — something the business does, not a technical concern. "User Authentication" is a business capability. "Database Layer" is not.
👤
User Service
Owns: who the user is, how they log in, their profile. Does NOT own: what they ordered, what's on the menu.
Business: Identity
🍽️
Menu Service
Owns: food items, prices, descriptions, categories. Does NOT own: who ordered what, who is logged in.
Business: Catalogue
📦
Order Service
Owns: what was ordered, when, by whom (user_id reference only), order status. Does NOT own: user details or menu items.
Business: Fulfilment
🟢 Beginner — The LEGO Brick Test
A good service should be like a LEGO brick — self-contained, connecting to others through defined connection points (APIs), not by merging material. If you can describe a service in one clear sentence ("the User Service manages who users are and how they log in"), the boundary is probably right.
🟣 Advanced — Domain-Driven Design (DDD)
In production systems, service boundaries are derived using Domain-Driven Design. Each service maps to a bounded context — a coherent domain model with its own language. "Order" means different things to the Delivery team vs the Finance team — these may become two separate services. Sam Newman's Building Microservices Chapter 3 covers this in depth.
2.2 How Services Communicate — Sync vs Async 20 min
🔄 Synchronous (REST / HTTP)
Service A calls Service B and waits for the response before continuing
Simple — works like a function call across the network
If Service B is down, Service A's request fails immediately
Used in CloudEats: Order Service calls User Service to verify a user exists
Risk: Chain A→B→C means latency adds up
📡 Asynchronous (Events)
Service A emits an event ("order.placed") and continues immediately — no waiting
Other services listen for events and react when ready
If a service is temporarily down, events queue up and process when it comes back
Example: "Send confirmation email after order placed" — email service listens for the event
Resilient: Services are truly independent
Synchronous example — Order Service calls User Service
// In order-service/server.js — verify user before placing order
const response = await fetch(
  `http://user-service:3001/api/users/${userId}`
);
if (!response.ok) {
  return res.status(404).json({ error: 'User not found' });
}
// ↑ Uses Docker DNS: 'user-service' resolves to container IP automatically
🟢 Beginner — Don't Worry About Async Yet
In Lab 5.1 we use synchronous HTTP calls between services. This is the simpler pattern and more than adequate for a three-service system. Async messaging (RabbitMQ, Kafka) is for production systems with strict resilience requirements. Knowing it exists and why is enough for Week 5.
🔵 Average — Docker DNS Magic
Notice the URL: http://user-service:3001 — not an IP address. In Docker Compose, service names become DNS entries. Docker's internal DNS resolves user-service to the correct container IP automatically, even if that IP changes every restart. Never hardcode container IP addresses.
🟣 Advanced — Choosing Sync vs Async
Useful heuristic: if the caller needs the answer to continue its work, use sync. If the caller just needs to notify something happened, use async. "Does this user exist?" → sync. "Email the user their receipt" → async. Async adds operational complexity (you need a message broker), so don't use it unless the benefit justifies it.
2.3 The API Gateway Pattern 15 min
🏨
Hotel reception desk analogy: Every guest (client request) goes through reception first. Reception checks your ID (authentication), decides which room (service) you're going to, and directs you there. Guests never wander the corridors finding rooms themselves — that's the API Gateway.
😩 Without Gateway
Frontend must know 3 service URLs and ports
:3001/api/auth/login
:3002/api/menu
:3003/api/orders
Auth logic must be duplicated in every service
Moving any service breaks all clients
😌 With Gateway (:8000)
Frontend uses one URL for everything
:8000/api/auth/login → User Service
:8000/api/menu → Menu Service
:8000/api/orders → Order Service
Auth validated once at the gateway
Services can move without frontend changes
  • RoutingForwards each request to the correct upstream service based on the URL path.
  • AuthenticationValidates JWT tokens once at the gateway. Downstream services trust that gateway-forwarded requests are pre-authenticated.
  • Rate LimitingLimits requests per client per minute. Protects services from being overwhelmed.
  • Load BalancingIf Menu Service runs 3 copies, the gateway distributes requests across them.
  • Centralised LoggingAll requests pass through one point — easy to trace, log, and audit.

Practice Sample Mid-Term Questions — Click to Check Answer
1. Which cloud service model gives the customer the most control over the underlying operating system?
  • SaaS — Software as a Service
  • PaaS — Platform as a Service
  • IaaS — Infrastructure as a Service. The customer manages the OS, runtime, and applications. The provider manages only hardware and virtualisation.
  • FaaS — Function as a Service
2. What is the main difference between a virtual machine (VM) and a Docker container?
  • Containers are more secure because they include a full operating system
  • A VM includes a full guest OS (kernel + userspace) — heavier, slower to start. A container shares the host OS kernel, packages only the app and its dependencies — starts in milliseconds, uses far less memory.
  • VMs can run on any OS; containers can only run on Linux
  • Containers and VMs are identical in resource usage
3. Name TWO specific problems that occur when a monolithic application grows large.
  • ✅ Model answer: (1) Deployment coupling — changing one feature forces full redeployment of all code. (2) Scaling inefficiency — must scale the entire application even if only one component is under load. Other valid: team bottlenecks (merge conflicts), technology lock-in, large blast radius.
  • "It becomes slow and hard to read" — too vague; does not name a specific architectural problem
4. The CloudEats Order Service needs to verify a user exists before placing an order. Where should it get that data?
  • Query the MySQL users table directly from Order Service — it's faster
  • Call the User Service API (GET /api/users/:id) via HTTP. The Order Service does not own the users table. Querying it directly violates the "database per service" rule and creates tight coupling.
  • Share the MySQL database between Order Service and User Service using separate schemas
  • Store a copy of all user data inside the Order Service MongoDB database
5. A startup with 3 developers is building a new food ordering app from scratch. Should they use microservices from day one?
  • Yes — microservices are always the best architecture
  • ✅ No. A 3-person team building a new product does not yet know the correct service boundaries. Microservices add operational overhead that far exceeds the benefit at this scale. Build a monolith first, understand the domain, and split only when the monolith's limitations cause measurable pain.
  • Only if they plan to use Docker
  • Only for the front-end; the back-end should always be a monolith
6. In Docker Compose, the Order Service needs to call the User Service. What URL should it use?
  • http://172.18.0.3:3001/api/users — use the container's IP address
  • http://localhost:3001/api/users — localhost resolves to the other container
  • http://user-service:3001/api/users — Docker Compose creates internal DNS where the service name resolves to the correct container IP automatically. IP addresses change on restart; names stay stable.
  • http://0.0.0.0:3001/api/users — use the wildcard address
Tips Exam Technique for Diploma Students
✍️
Short-Answer Strategy
Always: (1) name the concept, (2) explain in one sentence, (3) give a CloudEats example. Example: "Redis is an in-memory key-value store [concept]. It stores data in RAM for sub-millisecond access [explain]. In CloudEats, we use SET cart:user1 '...' EX 1800 to store and auto-expire carts [example]."
⚡
Scenario Question Strategy
Read the scenario for the pain point first. Scaling specific feature? → microservices. Team conflicts? → service ownership. Sub-millisecond speed? → Redis. Variable data shapes? → MongoDB. Matching the pain to the solution is what the examiner is testing.
