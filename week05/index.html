🔍 Why annotate before cutting?
Professional refactoring always starts with understanding. By labelling zones you can immediately see: (1) which npm packages each service needs in its own package.json, and (2) which database connection code moves with each service. This prevents missed dependencies when you extract.

🟢 Beginner — What is src/?
Each service folder has a src/ (source) subfolder. This keeps your application code separate from the configuration files (package.json, Dockerfile) that sit at the service root. Think of it like keeping your essay document in a Documents folder inside your project folder.

Create package.json — User Service owns its own dependencies

Create a new file: services/user-service/package.json

🔍 Why no Redis or MongoDB here?
The User Service handles only authentication — it uses MySQL only. Listing only the packages you actually need means: faster npm install, smaller Docker image, fewer security vulnerabilities. This is the "minimum footprint" principle in microservices.

Create src/server.js — Order Service scaffold
▶
services/order-service/src/server.js
const express  = require('express');
const { MongoClient } = require('mongodb');
const redis    = require('redis');
const jwt      = require('jsonwebtoken');
const cors     = require('cors');

const app = express();

app.use(express.json());

app.get('/health', (req, res) =>

// ── Redis connection
const REDIS_URL = process.env.REDIS_URL || 'redis://redis:6379';
const redisClient = redis.createClient({ url: REDIS_URL });
redisClient.connect().then(() =>
  console.log('[order-service] Redis connected')
);

// ── PASTE your /api/cart routes here ─────────────────
app.get('/api/cart/:userId', async (req, res) => {
  // copy from server.js.monolith
});
app.post('/api/cart/:userId/items', async (req, res) => {
  // copy from server.js.monolith
});

// ── PASTE your /api/orders routes here ───────────────
app.post('/api/orders', async (req, res) => {
  // copy from server.js.monolith
});
app.get('/api/orders/user/:userId', async (req, res) => {
  // copy from server.js.monolith
});

const PORT = process.env.PORT || 3003;
app.listen(PORT, () =>
  console.log(`[order-service] Running on http://localhost:${PORT}`)
);
🔵 Average — Two DB connections in one service
Order Service is the only service with two database connections (MongoDB + Redis). This is fine — a service can use multiple databases as long as it owns them. No other service should directly read from orders in MongoDB or the cart:* keys in Redis.
🟣 Advanced — Cross-service call when creating an order
When a new order is placed, the Order Service should verify the user exists. Instead of querying MySQL directly, add a fetch call to the User Service: await fetch(`http://user-service:3001/api/users/${userId}`). If the user is not found, return 404 before creating the order. This is the "database per service" rule in action — Order Service never touches the users table directly.

Add 3 new service blocks to docker-compose.yml
▶

Add these three service blocks to your existing docker-compose.yml, alongside your existing database services.

docker-compose.yml — add inside services:
  # ── Keep your old backend block commented out as fallback ──
  # backend:
  #   build: ./backend
  #   ports: ["3000:3000"]

  user-service:
    build: ./services/user-service
    ports:
      - "3001:3001"
    environment:
      - MYSQL_HOST=db
      - MYSQL_USER=root
      - MYSQL_PASSWORD=password
      - MYSQL_DATABASE=cloudeats
      - JWT_SECRET=your_jwt_secret
      - PORT=3001
    depends_on:
      - db
    restart: unless-stopped

  menu-service:
    build: ./services/menu-service
    ports:
      - "3002:3002"
    environment:
      - MYSQL_HOST=db
      - MYSQL_USER=root
      - MYSQL_PASSWORD=password
      - MYSQL_DATABASE=cloudeats
      - PORT=3002
    depends_on:
      - db
    restart: unless-stopped

  order-service:
    build: ./services/order-service
    ports:
      - "3003:3003"
    environment:
      - MONGO_URL=mongodb://mongo:27017
      - REDIS_URL=redis://redis:6379
      - JWT_SECRET=your_jwt_secret
      - PORT=3003
    depends_on:
      - mongo
      - redis
    restart: unless-stopped
🟢 Beginner — What does "depends_on" do?
depends_on: - db tells Docker Compose: "start the db container before starting user-service". Without this, your service might start before the database is ready and crash on the first connection attempt.
🔵 Average — Docker service DNS names
Notice MYSQL_HOST=db — this matches the service name in docker-compose.yml. Docker creates an internal DNS entry for each service name. So user-service can reach MySQL at the hostname db, MongoDB at mongo, and Redis at redis — Docker resolves these names automatically inside the shared network.
13
Add a Dockerfile to each service folder
▶

Each service needs its own Dockerfile at the service root. All three use the same pattern — only the service name in the label differs.

services/user-service/Dockerfile (repeat for menu + order)
FROM node:18-alpine

# Set working directory inside container
WORKDIR /app

# Copy package files first (layer caching)
COPY package*.json ./
RUN npm install --production

# Copy source code
COPY src/ ./src/

# Expose the service port
EXPOSE 3001

# Start the service
CMD ["node", "src/server.js"]
💡
Change EXPOSE 3001 to 3002 for menu-service and 3003 for order-service. Everything else stays the same — all three services are Node.js apps.
🟣 Advanced — Layer caching explained
Copying package*.json and running npm install before copying source code is intentional. Docker caches each build step. Since package.json rarely changes, the npm install layer stays cached across most rebuilds — only the COPY src/ step re-runs when you change code. This makes iterative builds much faster.

A health endpoint is like a "ping" — it tells you the service is alive and responding. Monitoring tools, load balancers, and Docker itself use health checks to automatically restart services that stop responding. It's good practice to add one to every service you build.
16
The independence test — stop one service, check the others
▶

This test proves the microservices separation actually works — stopping one service must not affect the others.

bash
# Stop order-service only
docker compose stop order-service

# User Service and Menu Service should still respond
curl http://localhost:3001/health   # must still work
curl http://localhost:3002/health   # must still work
curl http://localhost:3003/health   # will fail (expected)

# Bring it back
docker compose start order-service
🔍 This is the whole point
In the monolith, any crash killed all routes. Now, Order Service going down has zero effect on user login or menu browsing. This is fault isolation — one of the core benefits of microservices. Users can still browse the menu and log in even if orders is temporarily down.

18
Add a cross-service HTTP call: Order Service verifies user via User Service
▶

In services/order-service/src/server.js, update your POST /api/orders handler to call the User Service before creating an order:

services/order-service/src/server.js — POST /api/orders
app.post('/api/orders', async (req, res) => {
  const { userId, items } = req.body;

  // ── Cross-service call: verify user exists in User Service
  try {
    const userRes = await fetch(
      `http://user-service:3001/api/users/${userId}`
    );
    if (!userRes.ok) {
      return res.status(404).json({
        error: 'User not found',
        hint: 'Order Service checked User Service'
      });
    }
  } catch (err) {
    return res.status(503).json({ error: 'User Service unreachable' });
  }

  // ── Proceed with order creation in MongoDB
  // ... your existing order creation code here ...
});
🔍 Database-per-service rule in action
