What you're building: An API Gateway is a thin Express server that sits in front of all three microservices. The frontend calls only :8000. The gateway reads the URL path, decides which service to forward to, validates JWT tokens, and proxies the request. No business logic lives in the gateway.
Part 1 🏨 The Problem — 3 URLs is 3 Problems 10 min · Concept

After Lab 5.1 your frontend must call three different URLs to use your app. This creates real problems in development and production.

❌ Without Gateway (current state)
  • Frontend must know 3 separate service URLs and ports
  • CORS must be configured on every individual service
  • JWT token must be validated in every service separately
  • Moving a service to a new port breaks all frontend calls to it
  • Rate limiting and logging must be added to each service
  • HTTPS certificates needed on 3 separate services
✅ With Gateway (after this lab)
  • Frontend calls :8000 for everything — one URL
  • CORS handled in one place — gateway only
  • JWT validated once at the gateway — services trust it
  • Services can move/change ports — gateway absorbs the change
  • Rate limiting, logging, analytics all in one place
  • One HTTPS certificate on the gateway
🏨
The hotel reception desk: In a hotel, every guest goes through reception. Reception checks your ID, gives you a key, tells you your room number. You never wander backstage finding rooms yourself. The API Gateway is the reception desk for your microservices. Services are the rooms — guests (clients) never access them directly.

🔍 http-proxy-middleware
This npm package does the heavy lifting of forwarding HTTP requests to upstream services. It rewrites the URL, copies headers, streams the response back, and handles connection errors. We don't have to write raw HTTP proxy logic from scratch — this package is used in production by thousands of applications.

Part 3 📡 Write the Routing Logic 15 min
3
Create src/server.js — the gateway core
▶

Create services/api-gateway/src/server.js. This file contains the complete gateway:

services/api-gateway/src/server.js
const express      = require('express');
const cors         = require('cors');
const jwt          = require('jsonwebtoken');
const { createProxyMiddleware } = require('http-proxy-middleware');

const app = express();
app.use(cors());
app.use(express.json());

// ── Service URLs (Docker Compose DNS names) ────────────
const SERVICES = {
  user:  process.env.USER_SERVICE_URL  || 'http://user-service:3001',
  menu:  process.env.MENU_SERVICE_URL  || 'http://menu-service:3002',
  order: process.env.ORDER_SERVICE_URL || 'http://order-service:3003',
};

// ── Health check for the gateway itself ────────────────
app.get('/health', (req, res) =>
  res.json({ status: 'ok', service: 'api-gateway', port: 8000, routes: SERVICES })
);

// ── JWT Authentication Middleware ──────────────────────
const JWT_SECRET = process.env.JWT_SECRET || 'your_jwt_secret';

function requireAuth(req, res, next) {
  const header = req.headers['authorization'];
  if (!header || !header.startsWith('Bearer ')) {
    return res.status(401).json({
      error: 'Missing or malformed Authorization header',
      hint:  'Send: Authorization: Bearer <your_token>'
    });
  }
  const token = header.slice(7);
  try {
    const decoded = jwt.verify(token, JWT_SECRET);
    req.user = decoded;   // downstream services can read this header
    req.headers['x-user-id']    = decoded.id;
    req.headers['x-user-email'] = decoded.email;
    next();
  } catch (err) {
    return res.status(401).json({ error: 'Invalid or expired token' });
  }
}

// ── Proxy factory helper ───────────────────────────────
function proxy(target) {
  return createProxyMiddleware({
    target,
    changeOrigin: true,
    on: {
      error: (err, req, res) => {
        res.status(503).json({
          error: 'Upstream service unavailable',
          target,
          detail: err.message
        });
      }
    }
  });
}

// ══════════════════════════════════════════════════════
//  ROUTE TABLE
// ══════════════════════════════════════════════════════

// ── User Service — public routes (no auth) ─────────────
app.use('/api/auth', proxy(SERVICES.user));

// ── User Service — protected routes ───────────────────
app.use('/api/users', requireAuth, proxy(SERVICES.user));

// ── Menu Service — public (browsing doesn't need login) ─
app.use('/api/menu', proxy(SERVICES.menu));

// ── Order Service — protected (must be logged in) ─────
app.use('/api/cart',   requireAuth, proxy(SERVICES.order));
app.use('/api/orders', requireAuth, proxy(SERVICES.order));

// ── 404 for unknown routes ─────────────────────────────
app.use((req, res) =>
  res.status(404).json({
    error:           'Route not found in gateway',
    requestedPath:   req.path,
    availableRoutes: ['/api/auth', '/api/users', '/api/menu', '/api/cart', '/api/orders']
  })
);

const PORT = process.env.PORT || 8000;
app.listen(PORT, () => {
  console.log(`[api-gateway] Listening on :${PORT}`);
  console.log(`  /api/auth    → ${SERVICES.user}`);
  console.log(`  /api/menu    → ${SERVICES.menu}`);
  console.log(`  /api/orders  → ${SERVICES.order}`);
});
🔍 How the routing works — line by line
app.use('/api/auth', proxy(SERVICES.user)) tells Express: "for any request whose path starts with /api/auth, forward it to user-service:3001 and stream the response back." The changeOrigin: true option rewrites the Host header so the upstream service accepts the forwarded request. The requireAuth middleware runs before the proxy — so a bad token is rejected at the gateway and never reaches the upstream service.
🟣 Advanced — x-user-id header forwarding
Notice how requireAuth sets req.headers['x-user-id'] = decoded.id before proxying. This means downstream services (order-service, user-service) can read the authenticated user's ID from the request header without having to re-validate the JWT themselves. This is the pattern used by Kong, AWS API Gateway, and nginx-based gateways in production.

Part 4 🔑 Understanding JWT at the Gateway 10 min · Concept + Verify

The requireAuth middleware in the gateway validates every protected request. Here is what happens at each stage:

💡
Key insight: Once the gateway validates the JWT, downstream services (user-service, order-service) don't need to validate it again. They can trust that any request reaching them from the gateway is already authenticated. They just read the x-user-id header. This is called trust boundary shifting — the gateway is the trust boundary.
🟣 Advanced — What about service-to-service calls?
When order-service calls user-service directly (as in Part 8 of Lab 5.1), that request does NOT go through the gateway — it uses Docker's internal network directly. That call is already inside the trust boundary. This is why the internal URL is http://user-service:3001 (internal Docker DNS), not http://api-gateway:8000.

Part 5 🐳 Add Gateway to Docker Compose 10 min
4
Add api-gateway service block to docker-compose.yml
▶

Add this block inside the services: section of your docker-compose.yml:

docker-compose.yml — add inside services:
  api-gateway:
    build: ./services/api-gateway
    ports:
      - "8000:8000"
    environment:
      - USER_SERVICE_URL=http://user-service:3001
      - MENU_SERVICE_URL=http://menu-service:3002
      - ORDER_SERVICE_URL=http://order-service:3003
      - JWT_SECRET=your_jwt_secret
      - PORT=8000
    depends_on:
      - user-service
      - menu-service
      - order-service
    restart: unless-stopped
🔍 Why depends_on the services, not the databases?
The gateway doesn't connect to any database — it only talks to the three services. So depends_on lists the services, not the databases. The services themselves already declare their own database dependencies. Docker Compose handles the full startup chain: databases first → services → gateway.

🔍 Why this matters
Tests 2 and 3 prove the gateway acts as a security firewall. The order-service never even receives a request when the token is invalid — the gateway rejects it before proxying. This centralises security and means your services can focus on business logic, not authentication code.
