1.1 The Invisible System Problem ⏱ 15 min
🚗 Analogy
An application without monitoring is like driving a car with the entire dashboard covered. It might be running fine — or the engine might be about to fail. You won't know until it stops.
😰 Without monitoring
  1. Customer reports the app is broken
  2. Developer SSHs into the server
  3. Reads console output if the container is still running
  4. Guesses what went wrong
  5. Cannot reproduce it — the state is gone
  6. Resolution time: hours or days
✅ With structured logging + metrics
  1. Alert fires automatically when error rates spike
  2. Developer opens the log dashboard
  3. Finds 47 "JWT verification failed" errors in last hour
  4. Correlates with a deploy 2 hours ago that changed JWT_SECRET
  5. Rolls back — problem resolved
  6. Resolution time: 10 minutes
☁️
Cloud production reality: You cannot SSH into a running container and look at console output. Containers are ephemeral — they start, stop, and are replaced automatically. All observability comes from logs shipped to a central service and metrics collected by an agent. This is why logging and metrics are a fundamental cloud skill, not an optional extra.
1.2 Logging — What, Why, and How ⏱ 25 min

A log is a record that something happened. Logs answer: "What did the application do, and when?"

❌ console.log() — not production logging
  • No timestamp — when did this happen?
  • No severity level — is this an error or info?
  • No structure — impossible to query or search
  • No routing — errors and debug go to the same stream
  • No persistence — lost when the container restarts
✅ Winston — production logging
  • Automatic timestamps on every entry
  • Five severity levels with different destinations
  • JSON format — queryable and searchable
  • Multiple transports (console, file, cloud service)
  • Persists to files; survives container restarts

Log Levels — High to Low Severity

error › warn › info › http › debug
LevelWhen to useCloudEats exampleIn production?
errorSomething broke — requires immediate attentionDatabase connection lost, JWT_SECRET missingYes
warnUnexpected but not fatal — may become a problemFailed login attempt, duplicate registrationYes
infoNormal operations worth recordingUser registered, order placed, service startedYes
httpEvery incoming HTTP request (logged by Morgan)GET /api/menu 200 45ms, POST /api/auth/login 401Yes
debugDetailed developer info for debuggingVariable values, function call tracesNo
Why silence debug in production? In development, set LOG_LEVEL=debug to see everything. In production, set LOG_LEVEL=info — debug messages are silenced with no code changes. Just change the environment variable. This pattern keeps logs clean and reduces storage costs.

What to Log — and What Never to Log

✅
DO log these
  • Every login attempt (success and failure)
  • Every user registration
  • Every order placement
  • Every 4xx and 5xx HTTP response
  • Admin actions (delete user, change role)
  • Database connection events
  • Application startup and shutdown
❌
NEVER log these
  • Passwords — even hashed ones
  • JWT tokens — if logged, can be stolen from log files
  • Credit card numbers
  • Personal ID numbers
  • Full request bodies (may contain sensitive fields)

Structured JSON Log Entry vs Plain Text

❌ Unstructured — hard to search
console.log
User ali@example.com logged in at 10:23:45

How do you find all failed logins from the last hour? grep is slow and brittle.

✅ Structured JSON — queryable
Winston JSON log
{
  "level": "warn",
  "message": "Login failed",
  "service": "user-service",
  "timestamp": "2026-06-26 10:23:45:123",
  "email": "ali@example.com",
  "ip": "192.168.1.10"
}

Query: level="warn" AND message="Login failed" — instant results.

1.3 Morgan — HTTP Request Logging Middleware ⏱ 10 min

Morgan is an Express middleware that logs every incoming HTTP request automatically. You wire it to write through Winston so all logs go to the same destination:

config/morganLogger.js
const morgan = require('morgan');
const logger = require('./logger');

// Route Morgan's output stream into Winston's http level
const stream = {
  write: (message) => logger.http(message.trim())
};

const morganMiddleware = morgan(
  ':method :url :status :res[content-length] - :response-time ms',
  { stream }
);

module.exports = morganMiddleware;
Morgan formatOutput detailUse case
'combined'IP, user, method, URL, status, size, referrer, user-agentProduction — full audit trail
'short'Method, URL, status, response timeBalanced — most useful fields
'dev'Coloured condensed outputDevelopment only — visual readability
🚀 Advanced — cloud logging pipeline
In a cloud deployment, Winston would write to stdout (not a file). The container platform (ECS, Cloud Run, AKS) collects stdout from all containers and forwards it to the cloud logging service — CloudWatch Logs, Google Cloud Logging, or Azure Monitor. The same Winston code works — only the transport destination changes. You never need to SSH into a container to read logs.
3.1 Metrics — The Dashboard of Your Application ⏱ 20 min
📊 Logs vs Metrics
Logs answer: "What happened?" — a flight recorder of individual events.
Metrics answer: "How is the system performing right now?" — a live instrument panel.
📋
Logs
Individual events with full context. High volume. Used for debugging, security audit, incident investigation. Example: "User ID 5 placed order #142 at 10:23:45."
📈
Metrics
Aggregated numbers sampled over time. Low volume. Used for dashboards, alerts, capacity planning. Example: "The /api/orders endpoint processed 45 requests in the last minute with a 98% success rate."

Key Metric Types (prom-client)

TypeBehaviourCloudEats example
CounterOnly ever increases; never goes downTotal requests, total user registrations, total logins
GaugeCan go up or down; a current snapshotActive HTTP requests right now, memory usage MB
HistogramSamples values into configurable buckets; calculates percentilesResponse time — bucket counts at 10ms, 50ms, 100ms, 300ms, 500ms, 1s
🌱 Beginner — why percentiles?
An average response time of 50ms sounds fine. But if 5% of requests take 2,000ms, those slow requests represent real users having a terrible experience. P95 (95th percentile) means "95% of requests finish faster than this." It exposes the slow tail that averages hide.
⚡ Average — the Prometheus format
prom-client exports metrics in Prometheus text format at a /metrics endpoint. Each line is: metric_name{label="value"} number. Prometheus (an open-source monitoring server) scrapes this endpoint every 15 seconds. We use prom-client without a full Prometheus server — we collect and read the metrics directly. The format is the industry standard.
🚀 Advanced — RED method
A structured way to define what to monitor for any service: Rate (requests per second), Errors (requests that fail), Duration (how long requests take). These three metrics — all collectable with prom-client — give a complete picture of service health. Google's SRE book expands this into "four golden signals": latency, traffic, errors, saturation.
3.2 Performance Optimisation Strategies ⏱ 20 min

When metrics reveal a problem (slow responses, high CPU), these are the four primary tools:

⚡
Strategy 1 — Caching (Redis)
Store the result of an expensive operation and reuse it. The CloudEats menu rarely changes — querying MySQL on every request is wasted work. Cache the result in Redis for 5 minutes.
↕️
Strategy 2 — Vertical Scaling
Give the existing VM more CPU and RAM. Simple but has a ceiling — you cannot add hardware beyond the largest available instance. In Proxmox: increase VM resource allocation. In cloud: upgrade instance type.
↔️
Strategy 3 — Horizontal Scaling
Run more copies of the same container behind a load balancer. No ceiling — add as many as needed. CloudEats microservices are stateless (state is in databases) — they scale horizontally with no code changes.
🗄️
Strategy 4 — Database Query Optimisation
Slow queries are the most common bottleneck. Add an INDEX on columns used in WHERE clauses. Use EXPLAIN SELECT ... to see if MySQL is using the index or doing a full table scan.

Caching Example — Menu Route with Redis

menu-service/server.js
app.get('/api/menu', async (req, res) => {
  // Step 1: Check the Redis cache first (fast path)
  const cached = await redis.get('menu:all');
  if (cached) {
    logger.debug('Cache hit: menu:all');
    return res.json(JSON.parse(cached));   // 1ms response
  }

  // Step 2: Cache miss — query the database
  logger.debug('Cache miss: menu:all — querying MySQL');
  const results = await db.query('SELECT * FROM menu_items');

  // Step 3: Store in Redis for 5 minutes (300 seconds)
  await redis.setex('menu:all', 300, JSON.stringify(results));

  res.json(results);  // first request: ~50ms; all subsequent: ~1ms
});
⚡ Average — checkpoint question
The menu was cached at 10:00. A restaurant owner adds a new item at 10:02. A customer requests the menu at 10:03. What do they see? (Answer: the old cached menu — the new item appears at 10:05 when the 5-minute TTL expires. This is the cache invalidation trade-off: freshness vs performance.)

💡
Common cost waste: Overprovisioned instances running at 5% CPU. Dev/test environments running 24/7 when used 8 hours/day. Database volumes from deleted instances still being billed. Data transfer charges between regions. Set a budget alert before you deploy anything — many students get surprise bills from forgetting to stop a cloud VM.
🌱 Beginner — CloudEats cost estimate
A small CloudEats deployment on AWS (3 app containers + 3 managed databases) would cost roughly USD 100–150/month on-demand, or USD 60–80/month with reserved instances. This is far cheaper than a physical server in a data centre — and you only pay for what you actually use.
3.4 Introduction to Cloud Migration Planning ⏱ 10 min

By the end of Week 9 you have a complete, production-quality application running on Proxmox. Moving it to a real cloud requires a plan — not just a docker compose up on a different server.

A cloud migration plan must answer five questions:

1. What are we migrating?
Inventory every service, database, volume, and network component. For CloudEats: user-service, menu-service, order-service, MySQL, MongoDB, Redis, API Gateway.
2. What replaces each component?
Map each local component to a cloud equivalent. MySQL → AWS RDS. Redis → ElastiCache. Docker container → ECS task. .env secrets → AWS Secrets Manager.
3. What must change in the code?
Identify blockers: hardcoded IP addresses, local file paths, missing health checks, secrets not using environment variables. These must be fixed before migration.
4. In what order do we migrate?
Phase approach: databases first (preserve data), then services, then DNS switchover. Never attempt a big-bang migration of everything at once.
5. How do we verify it worked?
Success criteria: all health checks pass, smoke tests succeed, metrics show normal error rates, no data loss. Define these before starting — not after.
