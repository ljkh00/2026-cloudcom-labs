Part 1 The Logging Problem ⏱ 5 min
14 steps across 5 parts
1
See what logging looks like right now

Check the current console output from your user-service. It shows console.log() output with no timestamps, no levels, and nothing survives a restart:

Terminal
docker logs cloudeats-user-service --tail 20
🔍 What you see now — no structure
User logged in Error: something went wrong Server running on port 3001

By the end of this lab, the same events will look like:

✅ What you will see after this lab
{"level":"info","message":"User login successful","service":"user-service","userId":1,"email":"ali@example.com","timestamp":"2026-06-26 10:23:45:123"} {"level":"warn","message":"Login failed - invalid password","service":"user-service","email":"hacker@bad.com","ip":"192.168.1.10","timestamp":"2026-06-26 10:23:51:456"}
Why does JSON matter? The structured version is machine-readable. You can query: "show all warn-level entries from user-service in the last hour where email contains @bad.com". You cannot do that with plain text.

3
Create the logs directory and add it to .gitignore

Winston needs the logs/ folder to exist before it can write to it. Log files must never be committed to Git — they can be large and may contain sensitive data.

Terminal
mkdir -p logs
echo "logs/" >> .gitignore
echo ".env" >> .gitignore
cat .gitignore
✅ .gitignore should contain
node_modules/ .env logs/
⚠️ Trouble: ENOENT: logs directory not found (after rebuild)
The logs/ folder is created on the host but the Docker container has its own filesystem. Make sure your Dockerfile has RUN mkdir -p logs or create the folder in the container entrypoint. Alternatively, add a volume mount in docker-compose.yml: - ./services/user-service/logs:/app/logs
4
Create config/logger.js — the Winston configuration

Create the config/ directory and the logger file. This is the single source of truth for all logging configuration in the user-service:

Terminal
mkdir -p config
nano config/logger.js

Copy the complete logger configuration below:

config/logger.js
const winston = require('winston');

// Log level from environment variable — debug in dev, info in production
const LOG_LEVEL = process.env.LOG_LEVEL || 'info';

// Custom level definitions (error=0 is most severe; debug=4 is least)
const levels = { error: 0, warn: 1, info: 2, http: 3, debug: 4 };

// Colour map for console output
const colors = { error: 'red', warn: 'yellow', info: 'green', http: 'magenta', debug: 'white' };
winston.addColors(colors);

// Console format: coloured, human-readable
const consoleFormat = winston.format.combine(
  winston.format.timestamp({ format: 'YYYY-MM-DD HH:mm:ss:ms' }),
  winston.format.colorize({ all: true }),
  winston.format.printf(({ timestamp, level, message }) => `${timestamp} ${level}: ${message}`)
);

// File format: uncoloured JSON — searchable, machine-readable
const fileFormat = winston.format.combine(
  winston.format.timestamp({ format: 'YYYY-MM-DD HH:mm:ss:ms' }),
  winston.format.uncolorize(),
  winston.format.json()
);

const logger = winston.createLogger({
  level: LOG_LEVEL,
  levels,
  transports: [
    // Console: coloured output for development
    new winston.transports.Console({ format: consoleFormat }),

    // error.log: only error-level entries
    new winston.transports.File({
      filename: 'logs/error.log',
      level: 'error',
      format: fileFormat
    }),

    // combined.log: everything at or above LOG_LEVEL
    new winston.transports.File({
      filename: 'logs/combined.log',
      format: fileFormat
    }),
  ],
});

// Add a service label to every log entry
logger.defaultMeta = { service: 'user-service' };

module.exports = logger;
🌱 Beginner — what are transports?
A transport is a destination for log entries. We have three: Console (you see it while the container is running), error.log (errors only — for quick incident response), and combined.log (everything — for searching through history). The same event can go to multiple transports at once.
🚀 Advanced — cloud transport
In a cloud deployment, replace the File transports with a single Console transport writing to stdout. The container orchestrator (ECS, GKE, AKS) captures stdout from all containers and ships it to CloudWatch Logs, Google Cloud Logging, or Azure Monitor. Add winston-cloudwatch or similar npm packages for direct integration. The same logger.info() calls in your code work unchanged.
5
Create config/morganLogger.js — HTTP request logging
Terminal
nano config/morganLogger.js
config/morganLogger.js
const morgan  = require('morgan');
const logger  = require('./logger');

// Route Morgan's output into Winston's http level
const stream = {
  write: (message) => logger.http(message.trim())
};

// Format: METHOD URL STATUS size - responseTimeMs
const morganMiddleware = morgan(
  ':method :url :status :res[content-length] - :response-time ms',
  { stream }
);

module.exports = morganMiddleware;

Part 4 Add Business Event Logging ⏱ 15 min
8
Log successful and failed logins

Find your login endpoint (POST /api/auth/login) and add logger calls at the key decision points:

server.js — login endpoint
// Inside the login endpoint, after bcrypt.compare():

// Failed password:
if (!isValidPassword) {
  logger.warn('Login failed - invalid password', {
    email: email,
    ip: req.ip
  });
  return res.status(401).json({ error: 'Invalid email or password' });
}

// Successful login (just before returning the token):
logger.info('User login successful', {
  userId: user.id,
  email: user.email
});
return res.json({ token: token, user: { ... } });
🌱 Beginner — why log the IP on failure?
If the same IP address has 50 failed login attempts in one minute, that's a brute-force attack. Logging the IP lets you identify and block attackers. We log the IP only on failure — on success, we log the userId instead.
⚠️
Never pass the password into the logger. Not the plain text, not the hash. If you log { password: req.body.password }, it is stored permanently in the log file where anyone who can read the file can see it.

Log user registration

// After INSERT succeeds and you have the new userId:

🚀 Advanced — grep log analysis
You can search logs like a database query using grep: docker exec cloudeats-user-service grep '"level":"warn"' logs/combined.log | wc -l — counts all warn entries. Or: grep 'Login failed' logs/combined.log to list all failed attempts. This is the basic version of what Kibana or CloudWatch Logs Insights do.
