1.1 Why Applications Need a Database 15 min

In Lab 2.1, the CloudEats menu was hardcoded directly in HTML. For a single restaurant, this was fine. Let's think about what happens when the business grows.

😰 Without a Database
Menu lives inside the HTML file
Change menu = edit code file + rebuild + redeploy container
100 restaurants = 100 separate deployments per menu update
No history — who changed what and when?
Developers become the restaurant's menu editors
✅ With a Database
Menu lives in a database table separate from code
Change menu = update one database row, instant reflection
100 restaurants = all pull from the same database
Every change is a new row — full audit history built-in
Restaurant staff can edit menus themselves via an admin panel
💡
Core principle: A database separates data from code. The application logic (what the code does) and the application data (what the app knows) should live in different places. This is the foundation of scalable software design.
📸

Understand that a database stores data separately from code. Think of it like a spreadsheet that your app can read and update automatically.

1.2 Tables, Primary Keys & Foreign Keys 20 min

A relational database organises data into tables. Each table is like a spreadsheet — rows are individual records, columns are the properties of each record.

Example: The menu_items table

id (PK)namecategorypricedescriptioncreated_at
1Nasi Lemak SpecialBreakfast12.00Fragrant coconut rice...2024-01-15 09:00:00
2Nasi Lemak RegularBreakfast8.00Classic nasi lemak...2024-01-15 09:00:00
3Roti Canai with CurryBreakfast6.00Crispy flaky flatbread...2024-01-15 09:00:00
4Teh TarikBeverage3.00Pulled milk tea...2024-01-15 09:00:00
🔑
Primary Key (PK)
The id column uniquely identifies each row. MySQL auto-assigns it using AUTO_INCREMENT — you never need to set it manually. No two rows share the same id, even if their names are identical.
AUTO_INCREMENT
📋
Rows = Records
Each row is one complete menu item. If you add a new dish, you INSERT a new row. If the price changes, you UPDATE that row. To remove a dish, you DELETE the row.
INSERT · UPDATE · DELETE
📊
Columns = Properties
Each column holds one specific piece of information. Every row in the table has the same set of columns — the structure is fixed when the table is created.
Schema

Now — relationships between tables (Foreign Keys)

Once we add user accounts, we need to link orders to the user who placed them. We do this with a Foreign Key (FK).

users table:

id (PK)full_nameemail
1Ali Hassanali@example.com
2Siti Aminahsiti@example.com

orders table:

id (PK)user_id (FK)total_amountstatus
1126.00delivered
2114.00pending
3212.00confirmed
🤔
Why not just put the user's name in the orders table?
If Ali changes his name, you'd have to update every single order row. With a foreign key, you update users once — all orders automatically reflect it. This principle is called normalisation: store each piece of data exactly once, reference it with a key.
🔵 Average — Make the Connection
This is how every app you use works. Your Grab order history links your user_id to a list of orders. Your Shopee order links to the seller's product. The "relational" in relational database means tables relate to each other through keys.
🟣 Advanced — ON DELETE CASCADE
What happens if you delete user Ali? Without special handling, MySQL refuses — it won't leave orders pointing to a non-existent user (these are called orphan rows). We use ON DELETE CASCADE so when a user is deleted, all their orders are deleted automatically. Lab 3.2 uses this in the orders table definition.
1.3 Data Types in MySQL 15 min

Every column in MySQL has a data type. Choosing the right type prevents bad data from entering the database and improves query speed.

TypeWhat It StoresCloudEats ExampleWhy Not Something Else?
INT Whole numbers (no decimals) id = 42 IDs never have decimal places. INT is faster to index than text.
DECIMAL(10,2) Exact decimal numbers price = 12.50 Never use FLOAT for money — floating-point rounding errors can make RM12.50 become RM12.49999...
VARCHAR(255) Short text, max 255 chars name = 'Nasi Lemak' More efficient than TEXT for short strings. MySQL can index VARCHAR.
TEXT Long text, no fixed limit description = 'Fragrant...' For descriptions, notes, addresses. Cannot be fully indexed.
TIMESTAMP Date and time created_at = '2024-01-15 09:30:00' Use DEFAULT CURRENT_TIMESTAMP so MySQL fills it automatically.
ENUM(...) One value from a fixed list status = 'pending' Prevents typos. Inserting status = 'shipped' fails if that value isn't in the ENUM list.
BOOLEAN True / False (stored as 0/1) is_active = true MySQL stores BOOLEAN as TINYINT(1) internally. Both work.
📌
NOT NULL — add this to any column that must never be empty. A menu item without a name is meaningless data. name VARCHAR(255) NOT NULL forces MySQL to reject any INSERT that doesn't include a name. Think of it as a contract: the database enforces what your app might forget to check.
🟢 Beginner — Quick Rule
When in doubt: numbers without decimals → INT, prices/money → DECIMAL, words and names → VARCHAR, long text → TEXT, date/time → TIMESTAMP. You'll use these five types in 90% of tables.

Today we run MySQL in a Docker container on Proxmox. In a real production deployment, the same database would sit inside a managed cloud database service. The SQL is identical — the difference is who manages the server.

Free — runs on your own hardware
Full control over configuration
Great for development & learning
You manage backups (or data is lost)
You apply security patches manually
Single container = single point of failure
Scaling requires manual setup

Automatic daily backups, 35-day retention
Security patches applied automatically

Scale storage without downtime

Costs money (~USD 30–50/month for small instance)
Less direct control (managed = less access)

So far, you ran containers with long docker run commands. Docker Compose lets you declare your entire multi-container setup in a single docker-compose.yml file and start everything with one command.

😫 Without Docker Compose

Start DB: 1 long command with 5+ flags
Connect DB to network: another command
Start backend: another long command
Hope you wrote down all those flags correctly
Every new team member must repeat this
✅ With Docker Compose
Write docker-compose.yml once
docker compose up -d — everything starts
Network is created automatically
Service order handled automatically
Every team member runs the same command
The YAML file is version-controlled with the code

VS Code editor showing the project root with docker-compose.yml open and highlighted. File tree on the left: backend/ (Dockerfile, server.js, db.js, init.sql), docker-compose.yml at root. Here is the docker-compose.yml that students build in Lab 3.1. Every line is explained:

🐳 docker-compose.yml — Annotated
services:

  # ── WEB / BACKEND ────────────────────────────────
  backend:
    build: ./backend             # Build from local Dockerfile
    ports:
      - "3000:3000"              # Host:Container — browser hits :3000
    environment:
      DB_HOST: db               # ← Service name, not an IP address!
      DB_USER: cloudeats_user
      DB_PASSWORD: cloudeats_password
      DB_NAME: cloudeats_db
    depends_on:
      db:
        condition: service_healthy # Wait until MySQL is READY, not just started
    networks:
      - cloudeats-network

  # ── DATABASE ─────────────────────────────────────
  db:
    image: mysql:8.0              # Official MySQL image from Docker Hub
    environment:
      MYSQL_ROOT_PASSWORD: rootpassword
      MYSQL_DATABASE: cloudeats_db   # Creates this database on first run
      MYSQL_USER: cloudeats_user     # Creates this user on first run
      MYSQL_PASSWORD: cloudeats_password
    volumes:
      - mysql-data:/var/lib/mysql  # CRITICAL: persist data across restarts
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      timeout: 5s
      retries: 10
    networks:
      - cloudeats-network

volumes:
  mysql-data:                   # Named volume — managed by Docker, persists on disk

networks:
  cloudeats-network:            # Both services share this network = can talk to each other

Four things to understand about this file:

🌐
Service Name = Hostname
When backend connects to the database, it uses hostname db — the service name in the YAML. Docker's built-in DNS resolves db to the database container's IP automatically. No hard-coded IPs that change every restart.
Docker DNS · same as Week 2 Lab 2.2
💾
Named Volume = Persistent Data
MySQL stores data files in /var/lib/mysql inside the container. Without a volume, this folder disappears when the container stops — all your data is gone. The named volume mysql-data stores that folder outside the container on the host machine.
Critical!
🏥
depends_on + healthcheck
MySQL takes ~5–10 seconds to fully start after the container begins. Without healthcheck, the backend starts and immediately tries to connect — MySQL isn't ready yet, connection fails. The healthcheck pings MySQL every 5 seconds; backend only starts when MySQL responds.
Race condition fix
🔐
Environment Variables
Passwords in the YAML file work for local development. In production (Week 8), these move to a .env file excluded from Git, or to a secrets manager like AWS Secrets Manager. Never commit real passwords to version control.
Week 8 preview
⚠️
Common mistake — data loss demo: Run docker compose down (without a volume) then docker compose up -d — all menu items gone. With the named volume: docker compose down && docker compose up -d — menu items still there. This is Lab 3.1's key checkpoint.

How Node.js connects to MySQL using the service name:

JavaScript · db.js (Backend)
const mysql = require('mysql2/promise');

const pool = mysql.createPool({
  host:     process.env.DB_HOST,      // 'db' — the Docker service name
  user:     process.env.DB_USER,      // 'cloudeats_user'
  password: process.env.DB_PASSWORD,  // from docker-compose.yml environment
  database: process.env.DB_NAME,      // 'cloudeats_db'
  waitForConnections: true,
  connectionLimit: 10,
  queueLimit: 0
});

module.exports = pool;
🟢 Beginner — One Command to Remember
docker compose up -d starts everything. docker compose down stops everything. You don't need to touch individual containers. The YAML file is your infrastructure recipe.
🟣 Advanced — Why Connection Pools?
createPool instead of createConnection — a pool maintains multiple open connections. Without pooling, every API request creates a new TCP connection to MySQL (slow) and closes it after (wasteful). A pool reuses existing connections. connectionLimit: 10 means up to 10 concurrent database operations can run simultaneously. Week 9 covers monitoring these.
2.2 CloudEats Schema Design 25 min

These are the three tables built across Labs 3.1 and 3.2. Study each SQL statement — every keyword appears in the quiz.

① menu_items (Lab 3.1)

SQL · Table 1 — menu_items
CREATE TABLE IF NOT EXISTS menu_items (
  id          INT AUTO_INCREMENT PRIMARY KEY,  -- Auto-assigned unique ID
  name        VARCHAR(255) NOT NULL,          -- Required — no nameless items
  category    VARCHAR(100) NOT NULL,
  price       DECIMAL(10, 2) NOT NULL,       -- Exact decimal for money
  description TEXT,                            -- Optional long text
  badge       VARCHAR(50),                     -- Optional label: 'New', 'Popular'
  created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP  -- MySQL fills this automatically
);
↳IF NOT EXISTS — safe to run multiple times. If the table already exists, this line is silently skipped instead of throwing an error.
↳DECIMAL(10,2) — up to 10 digits total, 2 after the decimal point. Max price = RM99,999,999.99. Use this for all monetary values, never FLOAT.

② users (Lab 3.2)

SQL · Table 2 — users
CREATE TABLE IF NOT EXISTS users (
  id            INT AUTO_INCREMENT PRIMARY KEY,
  email         VARCHAR(255) UNIQUE NOT NULL,      -- No duplicate accounts
  password_hash VARCHAR(255) NOT NULL,             -- bcrypt hash, NEVER plain text
  full_name     VARCHAR(255) NOT NULL,
  phone         VARCHAR(20),                         -- Optional
  created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_email (email)                         -- Fast lookup by email on login
);
↳UNIQUE on email — MySQL rejects a second registration with the same email. The database enforces this, not just the application code.
↳INDEX idx_email — without this, finding a user by email scans every row. With 10 rows: doesn't matter. With 1 million rows: the difference between 1ms and 10 seconds.
↳ON UPDATE CURRENT_TIMESTAMP — MySQL automatically updates updated_at whenever any column in that row changes. Free audit trail.

③ orders (Lab 3.2)

SQL · Table 3 — orders
CREATE TABLE IF NOT EXISTS orders (
  id               INT AUTO_INCREMENT PRIMARY KEY,
  user_id          INT NOT NULL,
  total_amount     DECIMAL(10, 2) NOT NULL,
  status           ENUM('pending','confirmed','preparing','delivered','cancelled')
                   DEFAULT 'pending',               -- Default state for new orders
  delivery_address TEXT,
  notes            TEXT,
  created_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
  -- ↑ orders.user_id must exist in users.id | delete user → delete all their orders

  INDEX idx_user_id (user_id),   -- Fast: "show me all orders for user #42"
  INDEX idx_status  (status)     -- Fast: "show me all pending orders"
);
↳FOREIGN KEY is enforced at the database level. MySQL will reject an INSERT into orders if user_id doesn't exist in users.id. The database is the last line of defence.
↳ENUM restricts status to exactly these five values. INSERT INTO orders SET status = 'shipped' fails — preventing invalid states from ever entering the database.
2.3 Password Security — Why We Hash with bcrypt 15 min
🚨
Real incident context: In 2019, a major e-commerce platform stored user passwords in plain text. When attackers breached the database, they instantly had access to millions of passwords — and because people reuse passwords, they then accessed victims' banking and email accounts too. This is exactly what bcrypt prevents.
❌ Plain Text (Never Do This)
idemailpassword
1ali@example.comMyPassword1
2siti@example.comCuteKitten!
Database breached = instant access to all passwords
Attackers try these on Gmail, banking apps, etc.
Legal liability · reputational damage · user lawsuits
✅ bcrypt Hash (What We Use)
idemailpassword_hash
1ali@example.com$2b$10$XYZ8fGhJ2kL...
2siti@example.com$2b$10$ABCdEfGhI3...
Database breached = useless garbage to attackers
Hash cannot be reversed — it's a one-way function
Different hash per user, even for identical passwords
📸
Instructor Demo · MySQL Terminal — Hashed Passwords in Table
Terminal showing: docker exec -it [db] mysql -u cloudeats_user -p cloudeats_db → then SELECT id, email, password_hash FROM users\G. Output shows two rows — password_hash: $2b$10$XYZ... — a 60-character string that is clearly not the original password. Point out the $2b$10$ prefix: $2b$ = bcrypt v2b algorithm, $10$ = 10 salt rounds, remaining characters = salt + hash combined.

What bcrypt does — step by step:

①
Take Password
User submits "MyPassword1" in the registration form. This is the only moment the plain text exists — in memory, briefly.
②
Add a Salt
bcrypt generates a random 22-character string (the salt) and mixes it into the password. Two users with the same password get completely different hashes.
③
Hash (slowly)
bcrypt runs a slow algorithm intentionally — 210 = 1,024 rounds. Takes ~100ms on your laptop. A human doesn't notice. An attacker running billions of guesses is stopped.
④
Store the Hash
The 60-character hash string goes into password_hash. The original password is discarded — never stored, not even temporarily.

bcrypt in Node.js — registration and login:

JavaScript · auth.js (Registration + Login)
const bcrypt = require('bcrypt');
const SALT_ROUNDS = 10;  // 2^10 = 1,024 hashing rounds — never lower this below 10

// ── REGISTRATION ─────────────────────────────────────────
app.post('/api/auth/register', async (req, res) => {
  const { email, password, full_name } = req.body;

  // 1. Hash the password — this takes ~100ms (intentionally slow)
  const password_hash = await bcrypt.hash(password, SALT_ROUNDS);

  // 2. Store ONLY the hash — plain text password is now gone from memory
  await db.query(
    'INSERT INTO users (email, password_hash, full_name) VALUES (?, ?, ?)',
    [email, password_hash, full_name]
  );

  res.status(201).json({ message: 'Account created successfully' });
});

// ── LOGIN ─────────────────────────────────────────────────
app.post('/api/auth/login', async (req, res) => {
  const { email, password } = req.body;

  // 1. Look up user by email (fast — we have an INDEX on email)
  const [rows] = await db.query('SELECT * FROM users WHERE email = ?', [email]);
  const user = rows[0];

  if (!user) return res.status(401).json({ error: 'Invalid credentials' });

  // 2. Compare submitted password against stored hash — no decryption!
  const match = await bcrypt.compare(password, user.password_hash);

  if (!match) return res.status(401).json({ error: 'Invalid credentials' });

  res.json({ message: 'Login successful', userId: user.id });
});
🔐
Security detail: Both "user not found" and "wrong password" return the same error message: "Invalid credentials". This is intentional — if you return "user not found" separately, attackers can enumerate which emails are registered in your system. One generic message reveals nothing.
🔵 Average — SALT_ROUNDS = 10
SALT_ROUNDS = 10 means bcrypt runs 210 = 1,024 rounds. ~100ms per hash on modern hardware. 10 million brute-force attempts × 100ms = 11.5 days. For comparison, without bcrypt, MD5 hashing is so fast attackers can try 10 billion passwords per second.
🟣 Advanced — Rainbow Tables
A rainbow table is a pre-computed lookup: hash → original password for billions of common passwords. The bcrypt salt defeats this completely: even if two users both have the password "hello123", their hashes are different (because their salts are different). An attacker would need a separate rainbow table for every single user — computationally infeasible.
🗺️
Week 8 connection — JWT: This login endpoint currently returns a plain JSON success message. In Week 8, it will instead return a JSON Web Token (JWT) — a signed credential the browser sends with every subsequent request to prove the user is logged in. The users table and bcrypt you build this week are the exact foundation of that system.

Mid-Term Quiz Preparation — Week 3 Topics
📋
The mid-term quiz is in Week 5. These are the Week 3 question types based on learning objectives. Click an answer to check it.
1. A menu_items table has an id column with INT AUTO_INCREMENT PRIMARY KEY. What does AUTO_INCREMENT do?
  • You must manually provide a unique number for every row you insert
  • MySQL automatically assigns the next available integer — you never need to set the id yourself
  • The id column automatically increments every minute based on the system clock
  • AUTO_INCREMENT stores timestamps instead of integers
2. The orders table has: FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE. What happens if you delete the user with id = 5?
  • MySQL returns an error — you cannot delete a user who has orders
  • The user is deleted but all their orders remain in the database, now pointing to nothing
  • The user is deleted and all orders with user_id = 5 are automatically deleted too — no orphan rows
  • The user's id changes to NULL in the orders table
3. True or False: bcrypt.compare() works by decrypting the stored hash and comparing it to the submitted password.
  • True — bcrypt stores a reversible encrypted string
  • False — bcrypt is a one-way function. compare() re-hashes the submitted password using the same salt embedded in the stored hash, then compares the two hashes. The original password can never be recovered.
4. In docker-compose.yml, the backend connects to MySQL using DB_HOST: db. What is db here?
  • The IP address 127.0.0.1 (localhost) assigned to the MySQL container
  • A shorthand that Docker translates to 0.0.0.0
  • The service name defined in docker-compose.yml — Docker's built-in DNS resolves it to the database container's current IP address automatically
  • A hardcoded alias you must configure in /etc/hosts inside each container
5. Why does the CloudEats docker-compose.yml use a named volume for MySQL (mysql-data:/var/lib/mysql)?
  • To make MySQL start faster on subsequent runs
  • Named volumes allow multiple containers to read the same database simultaneously
  • Without a volume, MySQL's data files exist only inside the container and are deleted when the container stops. The named volume stores the data on the host machine so it survives container restarts and rebuilds.
  • Named volumes encrypt the database files for security purposes
6. You design a table for product prices. Which data type should you use?
  • FLOAT — it stores decimal numbers and takes less space
  • DECIMAL(10,2) — it stores exact decimal values. FLOAT uses binary floating-point and can introduce rounding errors that make RM12.50 become RM12.4999999...
  • VARCHAR(10) — storing numbers as text avoids rounding issues
  • INT — prices never have decimal places in practice
7. The users table has an INDEX idx_email (email). A second user tries to register with the same email. What prevents duplicate accounts?
  • The INDEX automatically rejects duplicate email values
  • The UNIQUE constraint on the email column rejects the duplicate. The INDEX speeds up lookups but does not enforce uniqueness on its own — UNIQUE does both.
  • The Node.js application code checks for duplicates before inserting
  • MySQL ignores the second INSERT and inserts NULL instead
