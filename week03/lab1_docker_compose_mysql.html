Stop Previous Containers & Clean Up
⏱ 2 min
0
Stop Everything from Lab 2.2
▶

In Lab 2.2 you started a menu container and a redis container manually using docker run. Before adding Docker Compose, stop and remove them — otherwise their ports and names will conflict.

bash · Stop Lab 2.2 Containers
# Stop and remove the containers from Lab 2.2
docker stop menu redis 2>/dev/null || true
docker rm   menu redis 2>/dev/null || true

# Remove the manual network (Docker Compose creates its own)
docker network rm cloudeats-net 2>/dev/null || true

# Check nothing is running on port 3000
docker ps

# Expected: no cloudeats containers in the list
⚠️
If you also ran the Week 1 Lab 1 docker-compose.yml (which had a web, database, and cache service), run docker compose down inside that folder first. Today's docker-compose.yml is a complete replacement — not an update to that file.
✅
Your files are safe. Stopping containers does not delete your frontend/ folder, HTML, CSS, or any code. You're only removing the running processes, not the project files.
🟢 Beginner — Why are we doing this?
In Lab 2.2 you started containers by typing docker run commands one by one. Docker Compose does the same thing automatically from a YAML file. We need a clean slate so the new Compose setup doesn't collide with your manually started containers.
🟣 Advanced — Volume Safety
Running docker compose down removes containers but keeps named volumes. That means if Week 1 Lab 1 created a volume called cloudeats_mysql_data, it still exists. Today's Compose uses a different volume name (mysql-data) to avoid inheriting an old schema. Run docker volume ls to see what's on your machine — anything prefixed cloudeats_ from a previous lab is safe to leave or remove with docker volume rm.
Part 1
Why Docker Compose?
⏱ 5 min
11 steps across 5 parts
1
The Problem with Manual docker run
▶

In Lab 2.2 you connected two containers using docker network create and two separate docker run commands. For two containers that was manageable. For a real application with web server + database + cache, it becomes:

bash · The Manual Way (Bad)
# 1. Create the network
docker network create cloudeats-network

# 2. Start MySQL — 5 flags, easy to mistype
docker run -d --name db \
  --network cloudeats-network \
  -e MYSQL_ROOT_PASSWORD=rootpassword \
  -e MYSQL_DATABASE=cloudeats_db \
  -e MYSQL_USER=cloudeats_user \
  -e MYSQL_PASSWORD=cloudeats_password \
  -v mysql-data:/var/lib/mysql \
  mysql:8.0

# 3. Wait for MySQL to be ready (how long? nobody knows)
sleep 15

# 4. Start the backend — hope you remembered all the env vars
docker run -d --name backend \
  --network cloudeats-network \
  -p 3000:3000 \
  -e DB_HOST=db \
  -e DB_USER=cloudeats_user \
  -e DB_PASSWORD=cloudeats_password \
  -e DB_NAME=cloudeats_db \
  cloudeats-backend:v1

# Total: 4 commands, 15+ flags, reproducibility = 0%

With Docker Compose, all of this is declared in one docker-compose.yml file and launched with a single command:

bash · The Compose Way (Good)
docker compose up -d    # That's it. Everything starts in the right order.
🟢 Beginner
Think of docker-compose.yml as a recipe card. Instead of following 4 separate cooking steps from memory each time, you write the recipe once and hand it to anyone. They follow the same recipe, get the same result.
🟣 Advanced
Docker Compose also handles dependency ordering, environment variable injection, health checks, and network creation — all declaratively. This is Infrastructure as Code at the development level. Week 7 applies these same principles to production environments.

Part 3
Add MySQL to Docker Compose
⏱ 20 min
3
Write docker-compose.yml
▶

Create (or replace) docker-compose.yml in the project root. Copy this file exactly — every indentation matters in YAML.

⚠️
YAML indentation: Use spaces, not tabs. YAML treats tabs as errors. Two spaces per indent level. VS Code shows a YAML syntax error (red squiggle) if the indentation is wrong — check it before saving.
yaml · docker-compose.yml
services:

  backend:
    build: ./backend
    container_name: cloudeats-backend
    ports:
      - "3000:3000"
    environment:
      DB_HOST:     db
      DB_USER:     cloudeats_user
      DB_PASSWORD: cloudeats_password
      DB_NAME:     cloudeats_db
      PORT:        3000
    depends_on:
      db:
        condition: service_healthy
    networks:
      - cloudeats-network
    restart: on-failure

  db:
    image: mysql:8.0
    container_name: cloudeats-db
    environment:
      MYSQL_ROOT_PASSWORD: rootpassword
      MYSQL_DATABASE:      cloudeats_db
      MYSQL_USER:          cloudeats_user
      MYSQL_PASSWORD:      cloudeats_password
    volumes:
      - mysql-data:/var/lib/mysql
      - ./backend/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-u", "root", "-prootpassword"]
      interval: 5s
      timeout:  5s
      retries:  10
    networks:
      - cloudeats-network

volumes:
  mysql-data:

networks:
  cloudeats-network:
    driver: bridge

Key lines explained:

LineWhat It Does
build: ./backendBuild the backend image from the Dockerfile inside backend/. Docker will look for backend/Dockerfile.
DB_HOST: dbThe hostname of the database container is its service name. Docker DNS resolves db to the container's IP automatically.
depends_on: db: condition: service_healthyBackend waits until MySQL passes its healthcheck before starting. Prevents the "cannot connect" race condition.
mysql-data:/var/lib/mysqlNamed volume. MySQL stores all data here. Volume survives docker compose down.
./backend/init.sql:/docker-entrypoint-initdb.d/init.sql:roMySQL runs any .sql files in /docker-entrypoint-initdb.d/ automatically on first start. This creates our tables.
healthcheck: test: ["CMD", "mysqladmin", "ping"...]Docker pings MySQL every 5 seconds. The backend only starts when MySQL responds to pings — usually after 10–20 seconds.
🟣 Advanced — Named Volume vs Bind Mount
The YAML has two types of volumes for the db service. mysql-data:/var/lib/mysql is a named volume — Docker manages the storage location on the host. ./backend/init.sql:... is a bind mount — mounts a specific file from your host into the container. Named volumes are better for databases (Docker manages them, better performance). Bind mounts are better for config files and code you want to share directly.

Write init.sql — Create the Database Schema
▶

MySQL reads init.sql automatically on first startup (via the docker-entrypoint-initdb.d mount). This creates the table and seeds sample data.

⚠️
The init script runs only on first startup — when the named volume is empty. If you need to re-run it, you must delete the volume: docker compose down -v (the -v flag removes volumes). Without -v, the volume is kept.
sql · backend/init.sql
-- Use the database created by Docker Compose environment variables
USE cloudeats_db;

-- Create menu_items table
CREATE TABLE IF NOT EXISTS menu_items (
  id          INT AUTO_INCREMENT PRIMARY KEY,
  name        VARCHAR(255) NOT NULL,
  category    VARCHAR(100) NOT NULL,
  price       DECIMAL(10, 2) NOT NULL,
  description TEXT,
  badge       VARCHAR(50),
  created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

Create db.js — MySQL Connection Pool
▶

The connection pool is created once when the app starts and reused for every query. Never create a new connection per request — it's slow and crashes under load.

javascript · backend/db.js
const mysql = require('mysql2/promise');

const pool = mysql.createPool({
  host:             process.env.DB_HOST     || 'db',         // Service name in docker-compose.yml
  user:             process.env.DB_USER     || 'cloudeats_user',
  password:         process.env.DB_PASSWORD || 'cloudeats_password',
  database:         process.env.DB_NAME     || 'cloudeats_db',
  waitForConnections: true,
  connectionLimit:    10,    // Max 10 simultaneous DB operations
  queueLimit:         0     // Queue unlimited requests (0 = no limit)
});

// Test the pool at startup — logs an error if MySQL is unreachable
pool.getConnection()
  .then(conn => {
    console.log('✅ MySQL connected — pool ready');
    conn.release();
  })
  .catch(err => console.error('❌ MySQL connection error:', err.message));

module.exports = pool;
🔵 Average — Why mysql2/promise?
mysql2/promise is the async/await-compatible version of the mysql2 driver. It lets you write const [rows] = await pool.query(...) instead of callback functions. The /promise suffix is important — without it, you get the callback-style API.
7
Create server.js — API Endpoints
▶
javascript · backend/server.js
const express = require('express');
const cors    = require('cors');
const db      = require('./db');

const app  = express();
const PORT = process.env.PORT || 3000;

app.use(cors());
app.use(express.json());
app.use(express.static('public'));        // Serve HTML/CSS from /public

// ── HEALTH CHECK ───────────────────────────────────
app.get('/health', (req, res) => {
  res.json({ status: 'ok', service: 'cloudeats-backend' });
});

// ── GET ALL MENU ITEMS ──────────────────────────────
app.get('/api/menu', async (req, res) => {
  try {
    const [rows] = await db.query('SELECT * FROM menu_items ORDER BY category, name');
    res.json({ success: true, data: rows });
  } catch (err) {
    console.error('Menu fetch error:', err.message);
    res.status(500).json({ success: false, error: 'Could not load menu' });
  }
});

// ── GET MENU BY CATEGORY ───────────────────────────
app.get('/api/menu/category/:category', async (req, res) => {
  try {
    const [rows] = await db.query(
      'SELECT * FROM menu_items WHERE category = ? ORDER BY name',
      [req.params.category]
    );
    res.json({ success: true, data: rows });
  } catch (err) {
    res.status(500).json({ success: false, error: err.message });
  }
});

app.listen(PORT, () => console.log(`CloudEats backend running on port ${PORT}`));
💡
Parameterised queries: Notice 'WHERE category = ?', [req.params.category] — the ? placeholder. Never concatenate user input directly into SQL strings (`WHERE category = '${req.params.category}'`). That creates an SQL injection vulnerability. The ? syntax automatically escapes the value.
🟣 Advanced — Add a Category Filter to the Frontend
The /api/menu/category/:category endpoint lets you filter by category. Try calling http://[VM-IP]:3000/api/menu/category/Breakfast directly. Then update the frontend to add filter buttons that call this endpoint when clicked.

8
Start Everything with docker compose up
▶
⚠️
Heads up — localhost:3000 now returns JSON, not your menu page. In Lab 2.1, port 3000 served your HTML menu via nginx. From this lab onwards, port 3000 is the Node.js API. Opening it in a browser will show raw JSON like {"success":true,"data":[...]}. That is correct. The frontend reconnects to this API in the next step — don't panic if the HTML page appears broken for now.
bash · Launch the Stack
# From the project root (where docker-compose.yml lives)
cd ~/cloudeats

# Build backend image and start all services in detached mode
docker compose up -d --build

# Watch logs in real-time (Ctrl+C to stop watching, containers keep running)
docker compose logs -f

Watch the logs. You should see this sequence:

Ready for start up. cloudeats-db | mysqld: ready for connections. cloudeats-db | Version: '8.0.x' socket: '/var/run/mysqld/mysqld.sock' port: 3306 cloudeats-backend | ✅ MySQL connected — pool ready cloudeats-backend | CloudEats backend running on port 3000
📸
Screenshot · docker compose logs — Both Containers Starting
Terminal showing docker compose up -d --build output — build steps for backend (Step 1/4, 2/4...), then [+] Running 2/2, followed by docker compose logs -f showing both container names with timestamps: db showing "ready for connections" and backend showing "✅ MySQL connected — pool ready" and "CloudEats backend running on port 3000".
❌ "Cannot connect to database" or backend keeps restarting ▶
Cause 1 — healthcheck not working: Check docker compose ps. Is the db service showing healthy or starting? If it stays on starting for more than 60 seconds, the healthcheck command may be wrong. Verify the MySQL root password in the healthcheck matches MYSQL_ROOT_PASSWORD.

Cause 2 — DB_HOST typo: Check DB_HOST: db in the YAML. The value must be db (the service name), not localhost or an IP.

Cause 3 — old container conflict: Run docker compose down first to remove old containers, then docker compose up -d --build.
❌ "Error response from daemon: Conflict. The container name ... is already in use" ▶
A container with that name already exists from a previous run. Stop and remove it: docker compose down — this removes containers but keeps volumes. Then re-run docker compose up -d --build.

10
Persistence Test — The Key Checkpoint
▶

This is the most important test of this lab. It proves that the named volume is working and data is not stored inside the container.

bash · Persistence Test
# Step 1: Add a new menu item via MySQL
docker exec -it cloudeats-db mysql -u cloudeats_user -pcloudeats_password cloudeats_db \
  -e "INSERT INTO menu_items (name, category, price, badge) VALUES ('Cendol', 'Desserts', 5.50, 'New');"

# Step 2: Verify it appears in the API
curl http://localhost:3000/api/menu | python3 -m json.tool | grep Cendol

# Step 3: STOP and REMOVE all containers (but NOT volumes)
docker compose down

# Step 4: Start them all again
docker compose up -d

# Step 5: Check if Cendol is still there
curl http://localhost:3000/api/menu | python3 -m json.tool | grep Cendol
📸
Screenshot · Persistence Test — Cendol Survives Restart
Terminal showing two grep Cendol results — before and after docker compose down && docker compose up -d. Both outputs show "name": "Cendol", proving the named volume persisted the data. Second screenshot: docker volume ls showing cloudeats_mysql-data as a separate entry from the containers.
🏆
Checkpoint 2 — Persistence Confirmed Cendol appears in the API response both before and after docker compose down && docker compose up -d. This proves the named volume is working — MySQL data lives outside the container.
🟣 Advanced — What Happens with docker compose down -v?
Try: docker compose down -v then docker compose up -d. The -v flag deletes the named volume. Cendol is gone — and so are all 7 seed items. init.sql runs again on first start and re-inserts them. This simulates a complete data loss scenario. In production, you'd have automated backups (RDS automatic backups, mysqldump to S3) to recover from this.
