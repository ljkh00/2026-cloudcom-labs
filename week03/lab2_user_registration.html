Overview
Lab Scenario & Objectives
📖
The story: CloudEats customers love the menu — now they're asking: "How do I place an order? I need an account!" This lab adds the user registration system. Customers can create accounts with a secure password. Their data is stored safely with bcrypt hashing.

What you'll build: Two new database tables (users, orders), a registration API endpoint, and a simple HTML registration form to test it. By the end, you can register a user and confirm in MySQL that the password is stored as a hash — never in plain text.

🚨
Security rule — non-negotiable: Passwords are never stored in plain text. Ever. Not even temporarily. bcrypt converts the password into a 60-character hash before it reaches the database. This lab enforces that rule from the start.

Learning objectives (click to track):

  • Write CREATE TABLE SQL for users (with UNIQUE email + INDEX)
  • Write CREATE TABLE SQL for orders (with FOREIGN KEY referencing users)
  • Install bcrypt and explain what SALT_ROUNDS means
  • Implement POST /api/auth/register with bcrypt hashing
  • Implement POST /api/auth/login using bcrypt.compare()
  • Build and test an HTML registration form
  • Verify registered user in MySQL shows $2b$10$ hash
  • Test that duplicate email returns an error (UNIQUE constraint)
  • Explain why bcrypt.compare() does NOT decrypt the hash
  • Complete all checkpoints successfully
Part 1
Extend the Database Schema
⏱ 15 min
8 steps across 4 parts
1
Add the users Table to init.sql
▶

Open backend/init.sql and append the following after the menu_items table definition. Do not replace it.

⚠️
Adding to init.sql only works if the database volume is fresh. Since the volume already contains menu_items, you need to run the new SQL manually or reset the volume. Step 2 covers how to do this safely.
sql · Append to backend/init.sql — users table
-- ── USERS TABLE ────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS users (
  id            INT AUTO_INCREMENT PRIMARY KEY,
  email         VARCHAR(255) UNIQUE NOT NULL,        -- No duplicate accounts
  password_hash VARCHAR(255) NOT NULL,               -- NEVER plain text
  full_name     VARCHAR(255) NOT NULL,
  phone         VARCHAR(20),                           -- Optional
  created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_email (email)                           -- Fast login lookup by email
);

Column-by-column explanation:

ColumnWhy This Choice
email UNIQUE NOT NULLPrevents two accounts with the same email. MySQL enforces at DB level — even if the app code forgets to check.
password_hash VARCHAR(255)bcrypt always produces a 60-char string. VARCHAR(255) gives room for any future algorithm change.
updated_at ... ON UPDATEMySQL automatically updates this column when any field in the row changes. Free audit trail — no code needed.
INDEX idx_email (email)Without an index, login requires scanning every user row. With it, MySQL jumps directly to the matching email. Critical at scale.
🟣 Advanced — UNIQUE vs INDEX
UNIQUE NOT NULL on email does two things: (1) creates an implicit index for fast lookup, AND (2) adds a uniqueness constraint. Adding a separate INDEX idx_email might seem redundant, but it's explicit documentation and allows non-unique indexes on the same column if the constraint is later removed. In practice with MySQL, the UNIQUE constraint IS the index.
2
Add the orders Table & Apply the Schema
▶

Continue appending to init.sql. The orders table must come after users because its FOREIGN KEY references users.id.

sql · Append to backend/init.sql — orders table
-- ── ORDERS TABLE ───────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS orders (
  id               INT AUTO_INCREMENT PRIMARY KEY,
  user_id          INT NOT NULL,
  total_amount     DECIMAL(10, 2) NOT NULL,
  status           ENUM('pending', 'confirmed', 'preparing', 'delivered', 'cancelled')
                   DEFAULT 'pending',
  delivery_address TEXT,
  notes            TEXT,
  created_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
  INDEX idx_user_id (user_id),
  INDEX idx_status  (status)
);

Now apply the new tables to the existing database without deleting menu items:

❌ "ERROR 1215 (HY000): Cannot add foreign key constraint" ▶
The orders table references users.id — so users must exist first. Check that your init.sql creates users before orders. If the order is wrong in the file, the foreign key constraint fails because it can't find the referenced table.

❌ "Cannot find module 'bcrypt'" ▶
bcrypt is not installed inside the container. This happens if you forgot --build when restarting. Run: docker compose up -d --build backend. The rebuild runs npm install inside the Dockerfile, which includes bcrypt.
Part 3
Build the Authentication API
⏱ 20 min
4
Create auth.js — Registration & Login Routes
▶

Create a separate file backend/auth.js for authentication routes. This keeps server.js clean.

javascript · backend/auth.js
const express = require('express');
const bcrypt  = require('bcrypt');
const db      = require('./db');

const router = express.Router();
const SALT_ROUNDS = 10;   // 2^10 = 1024 rounds — never go below 10

// ── POST /api/auth/register ──────────────────────────────────
router.post('/register', async (req, res) => {
  const { email, password, full_name, phone } = req.body;

  // Input validation
  if (!email || !password || !full_name) {
    return res.status(400).json({ error: 'Email, password, and full name are required' });
  }
  if (password.length < 8) {
    return res.status(400).json({ error: 'Password must be at least 8 characters' });
  }

  try {
    // Hash the password — ~100ms intentional delay (SALT_ROUNDS = 10)
    const password_hash = await bcrypt.hash(password, SALT_ROUNDS);

    // Insert into database — plain text password is now discarded
    const [result] = await db.query(
      'INSERT INTO users (email, password_hash, full_name, phone) VALUES (?, ?, ?, ?)',
      [email, password_hash, full_name, phone || null]
    );

    res.status(201).json({
      message: 'Account created successfully',
      userId:  result.insertId
    });

  } catch (err) {
    // ER_DUP_ENTRY: email already registered (UNIQUE constraint)
    if (err.code === 'ER_DUP_ENTRY') {
      return res.status(409).json({ error: 'Email already registered' });
    }
    console.error('Registration error:', err.message);
    res.status(500).json({ error: 'Registration failed' });
  }
});

// ── POST /api/auth/login ─────────────────────────────────────
router.post('/login', async (req, res) => {
  const { email, password } = req.body;

  if (!email || !password) {
    return res.status(400).json({ error: 'Email and password are required' });
  }

  try {
    // Lookup user by email (fast — INDEX on email)
    const [rows] = await db.query(
      'SELECT id, email, password_hash, full_name FROM users WHERE email = ?',
      [email]
    );

    // Use same error message for "not found" and "wrong password"
    // (prevents email enumeration attacks)
    if (rows.length === 0) {
      return res.status(401).json({ error: 'Invalid credentials' });
    }

    const user = rows[0];

    // bcrypt.compare re-hashes the submitted password and compares
    // It does NOT decrypt the stored hash
    const match = await bcrypt.compare(password, user.password_hash);

    if (!match) {
      return res.status(401).json({ error: 'Invalid credentials' });
    }

    // Login successful — Week 8 will return a JWT token here instead
    res.json({
      message:  'Login successful',
      userId:   user.id,
      fullName: user.full_name,
      email:    user.email
    });

  } catch (err) {
    console.error('Login error:', err.message);
    res.status(500).json({ error: 'Login failed' });
  }
});

module.exports = router;
🔐
Security design: Both "user not found" and "wrong password" return the identical message: "Invalid credentials". If you return "Email not found" separately, attackers can enumerate which emails are registered in your system — confirming real user accounts is valuable data for targeted attacks.

MySQL terminal showing SELECT id, email, password_hash FROM users\G output. The password_hash field for each user shows a 60-character string beginning with $2b$10$ — clearly not a human-readable password. The Key Checkpoint — bcrypt Working Correctly The password_hash column shows a 60-character string starting with $2b$10$. This proves: (1) the plain text password was never stored, (2) bcrypt ran with 10 rounds, (3) each user has a unique salt embedded in their hash. This is what secure password storage looks like.

🔵 Average — What does bcrypt.compare() actually do?
The 60-char hash contains the salt embedded inside it (the first 29 characters). bcrypt.compare(submitted, storedHash) extracts the salt from storedHash, re-hashes submitted using that same salt, then compares the result to the original hash. No decryption — pure comparison of two derived values.
🟣 Advanced — Verify the Schema Constraints
Run inside MySQL: SHOW CREATE TABLE orders\G — the output shows the full table definition including FOREIGN KEY and ENUM. Then test the foreign key: INSERT INTO orders (user_id, total_amount) VALUES (999, 50.00); — this should fail with ERROR 1452: Cannot add or update a child row: a foreign key constraint fails. The database rejected an order for a non-existent user. Try the same with user_id = 1 — it succeeds.
