1.1 What is Infrastructure as Code? 20 min

Infrastructure as Code (IaC) means describing your servers, networks, and services in files — the same way you write application code. Those files are committed to Git, reviewed in pull requests, and applied to create real infrastructure. The traditional alternative is ClickOps: a developer logs into a server and manually types commands or clicks through a GUI.

❌ ClickOps — The Old Way
No history — "Who changed that? When? Why?" — unknown forever
Not reproducible — setting up an identical environment requires remembering every step and order
Error-prone — a missed flag or typo affects production with no undo button
Slow onboarding — new team member takes hours or days to replicate the environment
Dev ≠ Production — environments diverge over time; bugs appear only in prod
✔ Infrastructure as Code
Git history — every infrastructure change is a commit with an author, date, and reason
Reproducible — run the same file on any machine, get the same result every time
Reviewable — infrastructure changes go through pull requests like code changes
Fast onboarding — new developer types one command and has a running environment
Dev = Production — same docker-compose.yml runs everywhere; no environment surprises
🌿 Beginner ⚡ Average 🚀 Advanced
🌿 Beginner — The Recipe Analogy
Imagine a chef who memorises every recipe. If the chef is sick, nobody can cook the food. If a customer asks "how was this made?", there's no answer. IaC is like writing the recipe down. Anyone with the recipe gets the same dish, every time, in any kitchen — and the recipe is checked into Git so you always know who last changed the salt quantity.
⚡ Average — The Core Principle
If you need more than one command to reproduce your infrastructure, it belongs in a file. If it's in a file, it belongs in Git. If it's in Git, it can be reviewed, rolled back, and shared. Apply this rule and you've already adopted the IaC mindset — the specific tool (Compose, Terraform, Ansible) comes second.
🚀 Advanced — Immutable Infrastructure
The IaC philosophy taken to its conclusion is immutable infrastructure: servers are never modified in place after deployment. When a change is needed, build a new image with the change, deploy the new image, destroy the old one. Docker containers are naturally immutable (the image defines the state); Kubernetes and AWS ECS enforce this by design. The docker-compose.yml you write in Lab 7.1 is the first step toward this pattern.
1.2 Declarative vs Imperative Infrastructure 15 min

There are two fundamentally different ways to express what you want a computer to do. Modern IaC tools are almost always declarative:

Imperative — “How”
Give step-by-step instructions: "Do step 1, then 2, then 3."
A bash script: install MySQL, create user, create database.
Run it twice → step 2 fails: "User already exists."
You handle every possible state manually. Fragile.
The sleep 30 hack — guess how long MySQL takes.
Declarative — “What”
Describe the desired end state: "I want MySQL with this config."
Docker Compose checks what already exists, applies only the diff.
Run it twice → same result. No errors. Idempotent.
The tool handles state. You describe intent.
condition: service_healthy — waits precisely, not blindly.
Side-by-side: bash script vs docker-compose.yml
# ─── Imperative (bash) ───────────────   # ─── Declarative (Compose) ────────────
apt-get install mysql                      db:
mysql -e "CREATE USER 'app'@'%'..."          image: mysql:8.0
mysql -e "CREATE DATABASE cloudeats"         environment:
mysql -e "GRANT ALL ON cloudeats.* TO..."      MYSQL_DATABASE: cloudeats
# What if user already exists?                MYSQL_USER: app
# Script fails. Fix. Re-run from scratch.   # Run again = no problem ✅
Why this matters for CloudEats Lab 7.1: The docker-compose.yml is declarative. Run docker compose up -d after it's already running and nothing breaks — Docker reads the current state and applies only what's needed. This is why Docker Compose qualifies as a real IaC tool, not just a convenience wrapper around docker run.
1.3 IaC Tools Landscape 10 min

Students should recognise these names — they appear in every DevOps job description. You don't need to know them all deeply; you need to know what layer each one operates at.

ToolManagesStyleThis course?

💡
Why Compose and not Terraform? Terraform requires cloud-provider accounts with billing, IAM setup, and a steeper learning curve that would consume weeks. Docker Compose achieves the same conceptual goal inside the Proxmox lab: infrastructure as a file, committed to Git, applied with one command. Every concept you learn about Compose directly transfers to Terraform when you encounter it in industry.
🚀 Advanced — Pulumi and CDKs
A newer pattern uses general-purpose programming languages (TypeScript, Python, Go) to define infrastructure instead of YAML. AWS CDK and Pulumi let you write new Bucket("my-bucket") in TypeScript and it provisions real AWS resources. The tradeoff: more power and testability, but less readable to non-developers. The declarative vs imperative debate applies here too — most CDK constructs compile down to CloudFormation (declarative) under the hood.
1.4 Docker Compose as IaC — Five Key Concepts 15 min

The docker-compose.yml built in Lab 7.1 uses five structural concepts. Every concept has a purpose — understand the purpose before the syntax.

📦
Services
Each container in the stack. Specifies the image (or Dockerfile path), exposed ports, environment variables, volumes, networks, and startup dependencies. CloudEats has seven: mysql, redis, mongodb, user-service, menu-service, order-service, api-gateway.
Top-level key
👥
Networks
The private bridge network containers share. Services on the same network find each other by service name as hostname — Docker provides internal DNS. http://user-service:3001 resolves because both containers share cloudeats-network. Covered since Week 2.
Internal DNS
💾
Volumes
Named volumes persist data outside the container lifecycle. docker compose down removes containers but not volumes. The MySQL database survives. docker compose down -v removes volumes too — use only when you want a clean slate. Three volumes in CloudEats: mysql-data, redis-data, mongo-data.
Survives down
❤
Health Checks
A command Docker runs periodically inside the container to verify the service is genuinely ready — not just started, but accepting connections. Status: starting → healthy or unhealthy. Services with depends_on condition: service_healthy wait for the green light before launching.
Ready, not just running

Environment variables and secrets — the fifth concept. Passwords are never hardcoded in docker-compose.yml:

Environment variable substitution pattern
# docker-compose.yml ── reference, never hardcode
db:
  image: mysql:8.0
  environment:
    MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD:-secret123}
    #                    └── reads .env  └── fallback if .env missing

# .env file (in .gitignore ── never commit)
MYSQL_ROOT_PASSWORD=MyRealProd!Pass999

# In production: same docker-compose.yml, values from cloud secret manager
# The file is identical; only the source of the value changes (Week 8)
✅
After Lab 7.1 your docker-compose.yml defines: 7 services · 3 named volumes · 1 bridge network · health checks on all 3 databases · depends_on condition: service_healthy so services wait properly. This single file is the infrastructure definition for CloudEats. Check it into Git — every infrastructure change is now a commit with a message.
3.1 The Complete CI/CD Pipeline 25 min

Week 6 built the CI half: tests run automatically on every push. Week 7 adds the CD half: when those tests pass, the code deploys automatically. Together they form a complete pipeline.

CI — Continuous Integration (Lab 6.2)
Developer pushes → tests run automatically
Goal: catch bugs before they reach users
Result: confidence the code builds and tests pass
Already built: npm test in ci.yml
CD — Continuous Deployment (Lab 7.2)
Tests pass → deploy to server automatically
Goal: get working code to users as fast as possible
Result: git push main = live in 2–3 minutes
Adding: a deploy job to the same ci.yml

🚨 Quality Gate: Tests FAIL → pipeline stops. Notification sent. Code is not deployed. Tests PASS → continue to CD. gate

↓

🌿 Beginner ⚡ Average 🚀 Advanced
🌿 Beginner — What “no human needed” really means
After Lab 7.2 works, the only human action needed is git push. Everything after that — running tests, connecting to the server, pulling code, rebuilding containers, restarting services — happens automatically in GitHub's cloud. Your teammate could push code at 3am while you're asleep, and by 3:02am it would be tested and live on your VM. That's what CD means.
⚡ Average — Deployment frequency is a quality metric
Counter-intuitively, deploying more often reduces risk. Each deployment is smaller, easier to reason about, and easier to roll back. Netflix deploys thousands of times per day. Teams that deploy once a month have massive, scary releases with many things changing at once. CI/CD makes small, frequent deployments safe.
🚀 Advanced — GitOps and pull-based CD
The Lab 7.2 approach is “push-based” CD: GitHub Actions pushes changes to the server via SSH. An emerging alternative is GitOps (Argo CD, Flux): an agent running on the server continuously watches the Git repo and pulls changes when it sees a new commit. This eliminates the need for SSH keys and works better at scale. The conceptual model is identical; only the direction of the connection changes.
3.2 SSH Keys for Automated Deployment 20 min

GitHub Actions must SSH into the Proxmox VM to deploy. It cannot type a password — there is no human available. Instead it uses an SSH key pair: a mathematical lock and key derived from the same algorithm.

🤖 GitHub Actions Runner

🔑 Private Key
Stored as an encrypted
GitHub Secret. Never visible
in logs or to anyone.
🥊

💻 Proxmox VM

🔓 Public Key
Stored in
~/.ssh/authorized_keys
on the deployment server

The handshake: when GitHub Actions connects, it presents the private key. The VM checks it against the stored public key. If they are a mathematically matching pair, access is granted — no password typed anywhere.

SSH key setup — run once on your deployment VM
# Generate an ed25519 key pair (modern, compact, secure)
ssh-keygen -t ed25519 -C "github-actions-cloudeats" \
           -f ~/.ssh/github_actions_key -N ""
# -N ""   no passphrase — required for unattended automation
# Creates: github_actions_key  (private — goes to GitHub Secrets)
#          github_actions_key.pub (public — goes to authorized_keys)

# Authorise GitHub Actions to connect
cat ~/.ssh/github_actions_key.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys   # owner read/write only
chmod 700 ~/.ssh                   # owner access only

# CRITICAL: test manually before adding to GitHub
ssh -i ~/.ssh/github_actions_key student@<YOUR_VM_IP>
# If this succeeds from your terminal, GitHub Actions will too
⚠
Instructor note — highest-risk step for diploma students: SSH key setup accounts for >80% of Lab 7.2 failures. Demonstrate the key generation and authorized_keys steps live on the projector before students attempt it. Make every pair do the manual SSH test before adding the key to GitHub. If the manual test works, GitHub Actions will work.
GitHub Actions workflow — using the stored secret
# In .github/workflows/ci.yml — the deploy job
deploy:
  runs-on: ubuntu-latest
  needs: test        # ← only run if test job passes
  if: github.ref == 'refs/heads/main'
  steps:
    - name: Deploy to VM
      uses: appleboy/ssh-action@v1.0.0
      with:
        host:     ${{ secrets.DEPLOY_HOST }}
        username: ${{ secrets.DEPLOY_USER }}
        key:      ${{ secrets.DEPLOY_KEY }}
        script: |
          cd ~/cloudeats-app
          git pull origin main
          docker compose build user-service
          docker compose up -d --no-deps --build user-service
          curl -f http://localhost:8000/health || exit 1
Why GitHub Secrets? Secrets are encrypted at rest and in transit. They appear as *** in all workflow logs — nobody can read them, even repository admins. Anyone who forks your repo does not get your secrets. This is the same principle as AWS Secrets Manager and Azure Key Vault (Week 8). The pattern: never put a real credential in a file. Store it somewhere with access controls. Reference it by name.
3.3 Zero-Downtime Deployment 15 min

A naïve deployment stops all containers, rebuilds everything, then restarts. During the rebuild, the app is unavailable. For CloudEats at lunchtime, even 30 seconds of downtime means lost orders and angry customers.

🔄
Rolling Update — used in Lab 7.2
Build the new image while the old container is still running and serving requests. Swap the container — the old one stops only after the new one is confirmed healthy. Total downtime: milliseconds (the container swap itself).
Command
docker compose up -d \
  --no-deps \
  --build \
  user-service
# --no-deps: don't touch mysql/redis
# --build:   rebuild image first
# -d:        background mode
🔶
Blue-Green Deployment — industry standard
Run two identical environments simultaneously. Blue handles all live traffic. Green receives the new deployment and is tested in isolation. When Green is healthy, the load balancer flips from Blue to Green in one atomic switch. Blue becomes the instant rollback target. Downtime: zero. Used by: Netflix, Spotify, AWS, every major SaaS product.
Blue-green concepts appear in interviews — know the pattern even if the lab uses rolling.
⚡ Average 🚀 Advanced
⚡ Average — Health check in the deploy script
After restarting a service, the deploy script should verify it actually came up healthy before marking the pipeline successful: curl -f http://localhost:8000/health || exit 1. The -f flag tells curl to return a non-zero exit code on HTTP errors. The || exit 1 causes the pipeline step to fail, which triggers a notification — before any user notices the service is down.
🚀 Advanced — Canary releases
Between rolling and blue-green: route 5% of traffic to the new version and monitor error rates and latency in real-time. If metrics stay within bounds, gradually increase to 10%, 25%, 50%, 100%. If anything spikes, instant rollback with no user impact. Tools: Nginx split_clients, AWS CodeDeploy canary hooks, Kubernetes Argo Rollouts. The CloudEats API Gateway (a single nginx proxy) could implement a basic canary with split location blocks.

Quiz Week 7 Knowledge Check — Final Exam Patterns

These question patterns match what typically appears in the CloudEats Academy final. Select an answer to check if you're right.

Q1 — A new developer joins the CloudEats team. With ClickOps, they spend two days setting up a broken local environment. With IaC (docker-compose.yml), setup takes 15 minutes. Which IaC property explains this difference?
  • Containerisation reduces file size
  • Reproducibility — the same file produces the same result on any machine
  • Container networking uses DNS instead of IP addresses
  • Containers start faster than virtual machines
Q2 — A docker-compose.yml contains MYSQL_PASSWORD: ${MYSQL_PASSWORD:-secret123}. The .env file sets MYSQL_PASSWORD=Pr0d!Pass. What value does MySQL receive?
  • secret123 (the fallback)
  • Pr0d!Pass (from .env)
  • Both values concatenated
  • Neither — docker-compose.yml does not read .env automatically
Q3 — A developer pushes a commit to main. Two of the three tests fail. The GitHub Actions workflow has a deploy job with needs: test. What happens?
  • The deploy job runs anyway — tests are informational
  • The deploy job runs because one test passed
  • The test job fails; the deploy job does not run; developer is notified
  • GitHub automatically reverts the push
Q4 — Why is an SSH private key stored as a GitHub Secret rather than written directly into the .github/workflows/ci.yml file?
  • The private key is too large for a YAML value
  • GitHub Actions does not support SSH
  • Anyone with read access to the repo could download a committed key and SSH into the server
  • Git cannot store binary files like SSH keys
Q5 — A rolling deployment uses docker compose up -d --no-deps --build user-service. What does --no-deps do and why is it important?
  • Skips the Docker build cache to force a fresh build
  • Prevents Compose from recreating dependency containers (mysql, redis) that haven't changed
  • Bypasses the network layer for faster startup
  • Disables health checks on dependent services
