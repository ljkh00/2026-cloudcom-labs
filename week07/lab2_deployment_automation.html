Part 2 SSH Key Setup — Passwordless Authentication 15 min
⚠
This is the most critical part of the lab. Take your time. Test each step before moving on. If the SSH connection does not work manually, it will not work in GitHub Actions either — and the error will be harder to debug there.
3
Understand SSH key authentication ▶

SSH key authentication works with a key pair: two mathematically linked files. You never need to type a password — the keys prove identity instead.

text — How the authentication flow works
Private key (id_deploy)          Public key (id_deploy.pub)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Lives in GitHub Secrets          Lives on the VM in
(encrypted, never in logs)       ~/.ssh/authorized_keys

When GitHub Actions connects:
  GitHub presents private key ──→ VM checks against authorized_keys
                                  Match found → Access granted ✅
                                  No match    → Access denied ❌
🌿 Beginner analogy

Think of the public key as a padlock that you put on your door. The private key is the only key that opens it. You can hand out as many padlocks as you want — but only the one matching private key can open them. The private key never leaves the key holder (GitHub, in our case).

4
Generate the SSH deployment key pair on your VM ▶

Run this command on your VM (not your laptop). It creates two files: the private key and the public key.

Terminal — on your VM
ssh-keygen -t ed25519 -C "github-actions-cloudeats" -f ~/.ssh/deploy_key -N ""
# -t ed25519   : key type (modern, secure, small)
# -C "..."     : comment label to identify this key
# -f ~/.ssh/deploy_key : filename for the key pair
# -N ""        : no passphrase (REQUIRED for automation)
Expected output:
Generating public/private ed25519 key pair. Your identification has been saved in /home/student/.ssh/deploy_key Your public key has been saved in /home/student/.ssh/deploy_key.pub The key fingerprint is: SHA256:xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx github-actions-cloudeats
Terminal — confirm both files were created
ls -la ~/.ssh/
# You should see: deploy_key (private) and deploy_key.pub (public)
⚠ ~/.ssh directory does not exist ▶

Create it first: mkdir -p ~/.ssh && chmod 700 ~/.ssh then re-run the ssh-keygen command above.

5
Authorize the public key on the VM ▶

Add the public key to the VM's authorized_keys file. This is what tells the VM to trust connections made with the matching private key.

Terminal — on your VM
# Append the public key to authorized_keys
cat ~/.ssh/deploy_key.pub >> ~/.ssh/authorized_keys

# Set correct permissions (SSH refuses to work if these are wrong)
chmod 600 ~/.ssh/authorized_keys
chmod 700 ~/.ssh

# Verify the key was added
cat ~/.ssh/authorized_keys
Expected — last line of authorized_keys:
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... github-actions-cloudeats
🌿 Beginner — why are the permissions important?

SSH has a security rule: if the authorized_keys file is readable by anyone other than the owner, SSH ignores it entirely. The chmod 600 command sets the file to "readable and writable by owner only". If you skip this step, SSH will silently fail with a confusing "Permission denied" error.

6
Test the SSH connection manually before trusting GitHub Actions ▶

Always test SSH key authentication manually before adding it to a workflow. If it fails here, it will fail in GitHub Actions with a much harder-to-read error message.

Terminal — from your VM to itself (loopback test)
# Test connection using the deploy key
# Replace DEPLOY_USER and DEPLOY_HOST with your actual values
ssh -i ~/.ssh/deploy_key -o StrictHostKeyChecking=no DEPLOY_USER@DEPLOY_HOST "echo 'SSH works!'"
Expected output (no password prompt):
SSH works!
⚠ Permission denied (publickey) ▶

Work through this checklist in order:
1. ls -la ~/.ssh/authorized_keys — permissions must show -rw-------
2. cat ~/.ssh/authorized_keys — the key must be on a single line (no line breaks in the middle)
3. sudo systemctl status sshd — SSH server must be running
4. sudo nano /etc/ssh/sshd_config — confirm PubkeyAuthentication yes is set
5. If you changed sshd_config: sudo systemctl restart sshd

⚠ Connection refused / timeout ▶

Check SSH service status: sudo systemctl status sshd. If not running: sudo systemctl start sshd && sudo systemctl enable sshd. Also check firewall: sudo ufw status — if active, run sudo ufw allow 22.

✅ Part 2 complete: SSH key pair generated. Public key is in authorized_keys. Manual test connection succeeds without a password prompt.
Part 3 Add Secrets to GitHub 10 min
7
Copy the private key content from your VM ▶

You need to copy the entire private key file — including the header and footer lines — into GitHub Secrets.

Terminal — on your VM
# Print the private key — copy EVERYTHING including the BEGIN/END lines
cat ~/.ssh/deploy_key
It starts and ends like this (your key content will differ):
-----BEGIN OPENSSH PRIVATE KEY----- b3BlbnNzaC1rZXktdjEAAAABbm9uZQAAAARub25lAAAAGAAAABBzc2gtZWQyNTUxOQAA ... (many lines of base64 text) ... -----END OPENSSH PRIVATE KEY-----
🔒
Never share or post this key anywhere. It gives whoever has it the ability to SSH into your VM as your user. The only place it goes is GitHub Secrets — which encrypts it immediately.
8
Add all three secrets to GitHub Repository Settings ▶

Open your browser and navigate to your GitHub repository.

  1. Click Settings (top tab of the repo, not your account settings).
  2. In the left sidebar: Secrets and variables → Actions.
  3. Click "New repository secret".

Add these three secrets — one at a time:

Secret nameValue to paste
DEPLOY_KEYThe entire private key content from Step 7 (including BEGIN/END lines)
VM_HOSTYour VM IP address (e.g. 192.168.56.10)
VM_USERYour VM username (e.g. student)
🌿 Beginner — once added, secrets cannot be viewed again

After saving a secret, GitHub shows only its name — not its value. If you pasted the wrong value, delete the secret and create a new one with the correct value. This is intentional security design.

Why not hardcode the IP and username in the workflow file? Workflow files (.github/workflows/) are committed to Git and visible in the repository. If your repo is public (or becomes public later), hardcoded server IPs and usernames are exposed. Secrets keep this information encrypted and separate from the code.
✅ Part 3 complete: Three secrets added to GitHub: DEPLOY_KEY, VM_HOST, VM_USER.
Part 4 Add the Deploy Job to the Workflow 10 min
9
Open and review the existing CI workflow ▶
Terminal — on your VM
cd ~/cloudeats-app
cat .github/workflows/ci.yml

You should see a test-menu-service job (its display name is "Menu Service Tests", but its job id — the key needs: must reference — is test-menu-service). You will add a deploy job after it. The deploy job will have needs: test-menu-service — meaning it only runs if the test job passes.

⚡ Average — why needs: test-menu-service matters

Without needs: test-menu-service, the deploy job would run in parallel with the test job — which means broken code could deploy before tests even finish. The needs key enforces sequential execution AND short-circuits the pipeline: if tests fail, deployment never starts.

needs: must reference the job's id (the YAML key, e.g. test-menu-service:) — not its name: field (the human-readable label shown in the GitHub UI, e.g. "Menu Service Tests"). Using the display name here is a common mistake and causes GitHub Actions to reject the workflow with "depends on unknown job".

10
Add the deploy job to ci.yml ▶

Open the workflow file and add the deploy job at the end. Keep all existing content — do not replace it.

Terminal
nano .github/workflows/ci.yml

Add this block at the end of the file (after your existing test job):

.github/workflows/ci.yml — append this deploy job
  deploy:
    name: Deploy to VM
    runs-on: ubuntu-latest
    needs: test-menu-service     # only run if test job passes
    if: github.ref == 'refs/heads/main'  # only deploy from main branch

    steps:
      - name: Deploy CloudEats to VM
        uses: appleboy/ssh-action@v1.0.0
        with:
          host:     ${{ secrets.VM_HOST }}
          username: ${{ secrets.VM_USER }}
          key:      ${{ secrets.DEPLOY_KEY }}
          port:     22
          script: |
            cd ~/cloudeats-app

            echo "=== Pulling latest code ==="
            git pull origin main

            echo "=== Building updated services ==="
            docker compose build user-service menu-service order-service api-gateway

            echo "=== Deploying with zero downtime ==="
            docker compose up -d --no-deps user-service
            docker compose up -d --no-deps menu-service
            docker compose up -d --no-deps order-service
            docker compose up -d --no-deps api-gateway

            echo "=== Health check ==="
            sleep 10
            curl -f http://localhost:8000/api/menu/health || exit 1

            echo "=== Deployment complete ✅ ==="
            docker compose ps
🌿 Beginner — what does --no-deps do?

--no-deps (no dependencies) tells Docker Compose to update only the named service, without also recreating the databases it depends on. This is critical: without it, docker compose up api-gateway would also restart MySQL, Redis, and MongoDB — causing real downtime while databases reinitialise.

🚀 Advanced — why curl -f exits 1 on failure

The -f (fail) flag tells curl to exit with a non-zero status code if the HTTP response is an error (4xx or 5xx). In a shell script, exit 1 signals failure to the parent process — in this case, GitHub Actions. This transforms a silent bad deployment into a visible pipeline failure. Without -f, curl succeeds even if the app returns a 500 error, and the pipeline would show green when the app is broken.

⚠ GitHub Actions error: "Job 'deploy' depends on unknown job 'test'" ▶
This means the value after needs: does not match any job id in the file. Open ci.yml and check the exact key under jobs: from Lab 6.2 — it is test-menu-service, not test (that is only its name: label shown in the GitHub UI). Make sure your deploy job says needs: test-menu-service exactly, with matching spelling and no extra spaces, then commit and push again.

🚀 Advanced only — not required for the lab submission
15
Deploy only the services that actually changed ▶

Currently the pipeline rebuilds all four microservices on every push, even if only one file changed. This adds unnecessary build time. The challenge: use git diff to detect which service directories changed and rebuild only those.

bash — approach for selective deploy
# In your deploy script on the VM:
CHANGED=$(git diff --name-only HEAD~1 HEAD)

if echo "$CHANGED" | grep -q "services/user-service/"; then
  echo "user-service changed — rebuilding"
  docker compose up -d --no-deps --build user-service
fi

if echo "$CHANGED" | grep -q "services/menu-service/"; then
  echo "menu-service changed — rebuilding"
  docker compose up -d --no-deps --build menu-service
fi
# ... repeat for order-service, api-gateway

Challenge questions:

  • What happens if docker-compose.yml itself changes? Should that trigger a full redeploy?
  • What is a risk of the HEAD~1 approach when multiple commits are pushed at once?
  • How would you handle a change to a shared utils/ library used by all services?
