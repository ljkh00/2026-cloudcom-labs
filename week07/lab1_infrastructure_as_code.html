Part 1 The Deployment Problem — Why IaC? 10 min
1 See what manual deployment actually looks like ▶

Before writing the solution, understand the problem. Read through this — do not run these commands, they are for illustration only.

Manual deployment — illustration only, do not run
# 1. Create network
docker network create cloudeats-network

# 2. Start MySQL — remember all 5 flags
docker run -d --name mysql-db --network cloudeats-network \
  -e MYSQL_ROOT_PASSWORD=secret123 \
  -e MYSQL_DATABASE=cloudeats \
  -p 3306:3306 mysql:8.0

# 3. Wait for MySQL to be ready (guess how long?)
sleep 30

# 4. Start Redis
docker run -d --name redis-cache --network cloudeats-network \
  -p 6379:6379 redis:alpine

# 5. Start MongoDB
docker run -d --name mongodb --network cloudeats-network \
  -e MONGO_INITDB_ROOT_USERNAME=admin \
  -e MONGO_INITDB_ROOT_PASSWORD=secret123 \
  -p 27017:27017 mongo:6.0

# 6-19. Repeat for each of the 4 services...
# TOTAL: 20+ commands, 10–15 minutes, high error rate
Why does this matter? A new team member joining CloudEats needs to run all of this in the correct order with the correct values. If they forget one environment variable, a service silently connects to the wrong database. There is no record of who changed what or when. Each developer's environment is slightly different. IaC solves every one of these problems.
⚡ Average
The core IaC principle: if you need more than one command to reproduce your infrastructure, it should be in a file. If it's in a file, it should be in Git. If it's in Git, it can be reviewed, rolled back, and shared.
🚀 Advanced
Notice the sleep 30 — a hard-coded delay to wait for MySQL. This is the brittleness of imperative scripts: how do you know 30 seconds is enough? Too short = service fails to connect. Too long = wasted time. Docker Compose's healthcheck and condition: service_healthy solves this properly in Part 3.
✅
Check: Can you list three specific problems with the manual approach above? (History, reproducibility, error-prone. If yes, continue.)

services:

      - mysql-data:/var/lib/mysql

      interval: 10s
      timeout:  5s
      retries:  5

  redis:
    image: redis:7-alpine
    container_name: cloudeats-redis
    restart: unless-stopped
    ports:
      - "6379:6379"
    volumes:
      - redis-data:/data
    networks:
      - cloudeats-network
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout:  3s
      retries:  5

    image: mongo:6.0
    container_name: cloudeats-mongodb
    restart: unless-stopped
    environment:
      MONGO_INITDB_ROOT_USERNAME: ${MONGO_USER:-admin}
      MONGO_INITDB_ROOT_PASSWORD: ${MONGO_PASSWORD:-secret123}
    ports:
      - "27017:27017"
    volumes:
      - mongo-data:/data/db
    networks:
      - cloudeats-network

      MYSQL_DATABASE: ${MYSQL_DATABASE:-cloudeats}
      NODE_ENV:       ${NODE_ENV:-production}
    ports:
      - "3002:3002"

        condition: service_healthy

# ── VOLUMES (Data Persistence) ───────────────

⚠️
YAML is indentation-sensitive. Use spaces — never tabs. Each level of nesting is 2 spaces. If you get a parse error, check that lines are aligned correctly.
Why ${VARIABLE:-default} syntax? The :-default part means "use the .env value if it exists, otherwise fall back to the default". This lets the file work even without a .env file — useful for a quick local spin-up. In production, always use the .env (or a cloud secret manager) instead of the default.
3 Validate the YAML syntax before running ▶

Person B — validate the file. This catches YAML errors before you try to start seven containers.

Terminal
docker compose config --quiet
Expected output
(no output = valid YAML ✅)
🔴 yaml: line N: could not find expected ':' ▶

A YAML syntax error at line N. Open the file with nano docker-compose.yml and go to that line number. Common causes: a tab character instead of spaces, a missing colon after a key, or inconsistent indentation. Check that all nested items are indented 2 more spaces than their parent.

⚡ Average
docker compose config without --quiet prints the fully-resolved file, substituting all ${VAR} references. Compare it against your .env values to verify substitution is working correctly before deploying.
Part 3 Understanding Health Checks and Startup Order 10 min
4 Understand the three database health check commands ▶

Each database uses a different tool to check readiness. These are already in the docker-compose.yml from Step 2 — this step explains why each one is different.

DatabaseHealth check commandWhat it tests
MySQLmysqladmin ping -h localhostMySQL daemon is accepting connections
Redisredis-cli pingRedis responds with PONG
MongoDBmongosh --eval "db.adminCommand('ping')"MongoDB admin ping returns { ok: 1 }
🔴 Health check fails: "mysqladmin not found" ▶

The MySQL 8.0 official image includes mysqladmin — it should be available. If you see this error, the image may not have fully pulled. Try docker compose pull mysql and then docker compose up -d again. If using a custom MySQL image, switch to the official mysql:8.0 tag.

🔴 Services never reach "healthy" — circular dependency ▶

Circular dependency: if Service A depends on Service B and B depends on A, Docker Compose will hang indefinitely. The rule: databases never depend on services. Services depend on databases. The API gateway depends on services, not databases. If you see containers stuck in "starting" for more than 2 minutes, run docker compose ps and look for two containers each waiting for the other.

Why condition: service_healthy? depends_on without a condition only waits for the container to start — not for the database to be ready for connections. MySQL takes 15–30 seconds to initialise after starting. Without the health condition, user-service tries to connect immediately, gets "connection refused", and crashes. With the health condition, it waits patiently until MySQL confirms it is ready.
🚀 Advanced
The health check interval: 10s and retries: 5 mean Docker will try every 10 seconds for up to 50 seconds before marking the container as unhealthy. For a slow machine, increase retries to 10. For production where fast startup matters, use start_period: 30s (available in Compose v3.4+) to give the container grace time before health checks start counting failures.

9 Prove data persistence — the volume survives container deletion ▶

This demonstration is important: volumes persist data even after containers are deleted and recreated. This is the difference between docker compose down (safe) and docker compose down -v (deletes data).

Terminal
# Write something to Redis
docker compose exec redis redis-cli SET test_key "IaC_works"
docker compose exec redis redis-cli GET test_key

# Stop and REMOVE the Redis container (not the volume)
docker compose stop redis
docker compose rm -f redis

# Restart Redis — it recreates from the image
docker compose up -d redis

# Check the data survived
docker compose exec redis redis-cli GET test_key
Expected — data survived container deletion
"IaC_works"
✅
Why this matters: A container is disposable — it holds application code and configuration. A volume holds data. Treat containers as cattle, not pets: you can destroy and recreate them freely without losing your database.

Part 6 🚀 Advanced Challenge — Add Resource Limits Optional
★ Add CPU and memory limits to prevent runaway services ▶
🚀 Advanced only

In production, a single service going into a CPU loop can starve other containers. Docker Compose supports resource limits via the deploy key.

docker-compose.yml — add to each service block
user-service:
  build:
    context: ./services/user-service
  deploy:
    resources:
      limits:
        cpus:   '0.5'      # max 50% of one CPU core
        memory: 256M      # max 256 MB RAM
      reservations:
        cpus:   '0.1'      # guaranteed minimum
        memory: 64M

Add this to each microservice. After redeploying, verify with docker stats.

Trade-off question: What happens if a service legitimately needs more than its memory limit during a traffic spike? What is the trade-off between setting limits too tight vs too loose?
