Part 0 Why Automated Testing? A Production Disaster 8 min
0.1 The bug that got to production ▶

Two hours after deploying the ratings feature from Lab 6.1, a real-world scenario plays out:

production incident — what happened
Customer report:
  "I gave my favourite restaurant 6 stars and the app crashed!"

Root cause found:
  validateRating() correctly rejects 6 on the backend.
  But a customer sent a direct HTTP request, bypassing the form.
  The edge case "rating > 5 sent as string via API" was never tested.

Business impact:
  50 customers affected  | 2 hours downtime  | RM 2,000 lost revenue
  4 hours of developer time to find, fix, and redeploy
  1-star review left: "App crashes when I try to rate!"
🌿 Beginner — Why didn't the developer catch this?
When testing manually, developers test the happy path: "enter a valid rating, it works." They rarely test every edge case: what if someone sends a string? A negative number? A rating of 999? Humans forget. Automated tests never forget — you write them once and they run forever, every time, on every change.

Here is the difference between manual and automated testing at a glance:

❌ Manual Testing
Write code → curl test one case → "Looks good!" → deploy

Next sprint: change a function → forget to retest edge cases → break in production
✔ Automated Testing
Write tests once → run npm test in 2 seconds → 12 cases checked → CI runs same 12 tests on every push automatically
⚡ Average — Testing Pyramid
Tests are organised into layers. Unit tests (bottom, most numerous): test one function in isolation, milliseconds each. Integration tests (middle): test multiple parts together, e.g. an API endpoint hitting the database. End-to-end / UI tests (top, fewest): test through a real browser, seconds each. Today focuses on unit tests — the most important layer to master first.
🚀 Advanced — Cost of bugs by stage
IBM Systems Science Institute research (widely cited in software engineering) found that bugs caught in production cost roughly 6× more to fix than those caught in development, and 15× more than those caught in requirements. Automated tests act as a mechanical net at the cheapest stage. The ROI calculation: 1 hour writing tests prevents 6–15 hours of incident response, hotfix, re-QA, and deploy cycles.
✅

Part 1 Install Jest & Export the Function 10 min
1.1 Install Jest as a dev dependency ▶

Jest is the testing framework used by Facebook, Airbnb, and thousands of open-source projects. --save-dev records it under devDependencies in package.json — it is a tool for development only, not shipped to production.

terminal
# Navigate to the menu service
cd ~/cloudeats-app/services/menu-service
pwd
# Expected: .../cloudeats-app/services/menu-service

# Install Jest — saves to devDependencies
npm install --save-dev jest

# Confirm it installed
npm list jest
What you should see
menu-service@1.0.0 └── jest@29.x.x
🌿 Beginner — What is --save-dev?
npm install express adds to dependencies — packages needed when the app runs in production. npm install --save-dev jest adds to devDependencies — packages only needed while developing. When you deploy to a server and run npm install --production, Jest is skipped, keeping the production container lean.
⚡ Average — Jest vs Mocha: why Jest wins for small teams
Jest is "batteries included": zero-config test runner, built-in expect assertions, built-in mocking, and coverage reporting in one package. Mocha requires separate packages (Chai for assertions, Sinon for mocks, Istanbul for coverage). For a team starting with testing, Jest's single install is far less friction. Mocha's composability matters at scale when you need specific assertion libraries or non-standard reporters.
⚠ npm WARN / npm ERR during install ▶
A WARN about peer dependencies is usually harmless — continue. An ERR usually means a network issue. Try: npm cache clean --force then npm install --save-dev jest again. If offline, check your Wi-Fi connection.
1.2 Add test scripts to package.json ▶

Add "test", "test:watch", and "test:coverage" scripts so you can run Jest without typing the full path.

services/menu-service/package.json — scripts section
{
  "name": "menu-service",
  "version": "1.0.0",
  "scripts": {
    "start": "node src/server.js",
    "test": "jest",
    "test:watch": "jest --watch",
    "test:coverage": "jest --coverage"
  },
  "dependencies": {
    "express": "^4.18.0",
    "mysql2": "^3.0.0"

🌿 Beginner — What do these scripts do?
"test": "jest" → npm test runs all test files once and exits.
"test:watch": "jest --watch" → npm run test:watch re-runs tests automatically every time you save a file. Great for rapid development.
"test:coverage": "jest --coverage" → npm run test:coverage shows which lines of code were exercised by tests.
1.3 Add the validateRating function to server.js ▶

This lab tests a validateRating function — but it hasn't existed in your code until now. Open services/menu-service/src/server.js and add this function above the app.listen(...) line at the bottom of the file. It checks that a rating is present, is a number, is a whole number, and falls between 1 and 5.

services/menu-service/src/server.js — add above app.listen()
// ===== RATING VALIDATION (add above app.listen) =====
function validateRating(rating) {
  if (rating === undefined || rating === null) {
    return { valid: false, error: 'Rating is required' };
  }
  if (typeof rating !== 'number') {
    return { valid: false, error: 'Rating must be a number' };
  }
  if (!Number.isInteger(rating)) {
    return { valid: false, error: 'Rating must be a whole number' };
  }
  if (rating < 1 || rating > 5) {
    return { valid: false, error: 'Rating must be between 1 and 5' };
  }
  return { valid: true };
}
🌿 Beginner — Reading the checks top to bottom
Each if block handles one failure reason and returns immediately — this is called an "early return" or "guard clause" pattern. By the time execution reaches the last line, every bad case has already been ruled out, so { valid: true } is safe to return. The order matters: checking typeof before the range comparison stops a string like 'five' from ever reaching rating < 1.
⚡ Average — Why Number.isInteger instead of rating % 1 === 0?
Both work for numbers, but Number.isInteger() is the standard library function built exactly for this check and reads clearly to any developer reviewing the code. It also safely returns false for non-numeric input rather than producing NaN comparisons, though by this point in the function typeof has already filtered those out.
✅
validateRating exists in server.js. Confirm with grep -n "function validateRating" src/server.js before moving on.
1.4 Export validateRating so tests can import it ▶

Jest imports your function to test it. But server.js currently does not export anything — and it also starts a live server unconditionally the moment the file is loaded. Both need a guard. Replace your existing app.listen(...) line at the bottom of the file with the block below, which only starts the server outside of tests, and add the conditional export beneath it.

services/menu-service/src/server.js — replace app.listen(...) at the bottom of the file
// ===== START SERVER (skip during tests) =====
// Jest sets NODE_ENV=test automatically — only start listening otherwise
const PORT = process.env.PORT || 3002;
if (process.env.NODE_ENV !== 'test') {
  app.listen(PORT, () =>
    console.log(`[menu-service] Running on http://localhost:${PORT}`)
  );
}

// ===== EXPORT FOR TESTING (add at bottom of file) =====
// Only exports when Jest sets NODE_ENV=test
// Production server is unaffected
if (process.env.NODE_ENV === 'test') {
  module.exports = { validateRating };
}
🌿 Beginner — Why guard app.listen() too, not just the export?
app.listen() opens a real network port and keeps Node running to accept connections. If it stays unconditional, importing server.js during a test also boots a live server. Locally you can just press Ctrl+C to stop it, so nothing seems wrong. But in Part 4 you will push this file so it runs inside GitHub Actions — a remote machine with nobody watching. There, the open server keeps Jest's process alive forever, and the "Run tests" step hangs indefinitely instead of finishing.
⚡ Average — The better pattern: separate utilities file
In professional codebases, pure logic like validateRating lives in its own file (e.g. utils/validators.js) that exports cleanly without any server startup side-effects. server.js imports from it. Tests import from utils/validators.js directly. The conditional guard here works for a lab but is a smell in production code.
⚠ "Cannot find function validateRating in server.js" ▶
You need to have the validateRating function already in server.js from Step 1.3 above. Search the file: grep -n "function validateRating" server.js. If it is missing, go back to Step 1.3 and add it.

Part 2 Create the Test File & Run It 12 min
2.1 Create the test folder and validation.test.js ▶

Jest discovers test files by looking for files ending in .test.js or .spec.js, or files inside a __tests__ folder. We use both conventions here.

terminal
cd ~/cloudeats-app/services/menu-service

# Create the test directory
mkdir -p __tests__/unit

# Confirm the folder exists
ls __tests__/unit
# Expected: (empty for now)

Now create the test file. This contains 12 tests organised into four groups: valid ratings, invalid ratings, edge cases, and boundary values.

__tests__/unit/validation.test.js — create this file
/**
 * Unit Tests for Rating Validation
 * Tests the validateRating() function from menu-service/src/server.js
 *
 * AAA Pattern used in each test:
 *   Arrange — set up the input
 *   Act     — call the function
 *   Assert  — check the result with expect()
 */

// Import the function we want to test
const { validateRating } = require('../../src/server');

// describe() groups related tests under a heading
describe('validateRating Function', () => {

  // ── Group 1: Valid ratings should pass ─────────────────────
  test('should accept valid rating of 1', () => {
    const result = validateRating(1);
    expect(result.valid).toBe(true);
  });

  test('should accept valid rating of 3', () => {
    const result = validateRating(3);
    expect(result.valid).toBe(true);
  });

  test('should accept valid rating of 5', () => {
    const result = validateRating(5);
    expect(result.valid).toBe(true);
  });

  // ── Group 2: Invalid ratings should fail ───────────────────
  test('should reject rating above 5', () => {
    const result = validateRating(6);
    expect(result.valid).toBe(false);
    expect(result.error).toBe('Rating must be between 1 and 5');
  });

  test('should reject rating of 0', () => {
    const result = validateRating(0);
    expect(result.valid).toBe(false);
    expect(result.error).toBe('Rating must be between 1 and 5');
  });

  test('should reject negative rating', () => {
    const result = validateRating(-1);
    expect(result.valid).toBe(false);
    expect(result.error).toBe('Rating must be between 1 and 5');
  });

  test('should reject decimal rating', () => {
    const result = validateRating(3.5);
    expect(result.valid).toBe(false);
    expect(result.error).toBe('Rating must be a whole number');
  });

  // ── Group 3: Edge cases ────────────────────────────────────
  test('should reject undefined rating', () => {
    const result = validateRating(undefined);
    expect(result.valid).toBe(false);
    expect(result.error).toBe('Rating is required');
  });

  test('should reject null rating', () => {
    const result = validateRating(null);
    expect(result.valid).toBe(false);
    expect(result.error).toBe('Rating is required');
  });

  test('should reject string rating', () => {
    const result = validateRating('five');
    expect(result.valid).toBe(false);
    expect(result.error).toBe('Rating must be a number');
  });

  // ── Group 4: Boundary values ───────────────────────────────
  test('should accept exact lower boundary: 1', () => {
    expect(validateRating(1).valid).toBe(true);
  });

  test('should accept exact upper boundary: 5', () => {
    expect(validateRating(5).valid).toBe(true);
  });

  test('should reject one above upper boundary: 6', () => {
    expect(validateRating(6).valid).toBe(false);
  });

});
🌿 Beginner — Anatomy of one test
test('description', () => { ... }) — the description is what you read when a test fails.
const result = validateRating(6) — call the function with a specific input.
expect(result.valid).toBe(false) — assert what the output should be. If result.valid is true instead, Jest prints a clear "Expected: false, Received: true" failure.
⚡ Average — Why test boundary values?
Boundary Value Analysis (BVA) is a testing technique: bugs cluster at edges. For a range of 1–5, test exactly 0, 1, 5, and 6 — not just 3. The most common off-by-one errors show up as "accepts 6 when it should reject" or "rejects 1 when it should accept". Our test suite covers all four boundaries explicitly.

Part 3 Break a Test on Purpose — Then Fix It 10 min
💡
Why do this? Most students only see tests passing. Seeing a failure — and understanding what the output tells you — is the skill that matters when a real bug sneaks through to CI at 2am.
3.1 Introduce a deliberate bug in validateRating ▶

Open services/menu-service/src/server.js and find the range check inside validateRating. Change the upper bound from 5 to 10.

server.js — find and change this one line
// BEFORE (correct):
if (ratingNum < 1 || ratingNum > 5) {
  return { valid: false, error: 'Rating must be between 1 and 5' };
}

// AFTER (deliberately broken — change 5 to 10):
if (ratingNum < 1 || ratingNum > 10) {  // BUG: should be 5
  return { valid: false, error: 'Rating must be between 1 and 5' };
}
🌿 Beginner — What did this change do?
The function now accepts ratings from 1 to 10 instead of 1 to 5. A customer who submits a rating of 6 or 7 will no longer get an error — the value will be accepted and saved to the database. This is exactly the kind of off-by-one bug that ships to production when there are no automated tests.
3.2 Run the tests and read the failure output ▶
terminal
npm test
What you should see (failures highlighted)
FAIL __tests__/unit/validation.test.js validateRating Function ✓ should accept valid rating of 1 (3ms) ✓ should accept valid rating of 3 (1ms) ✓ should accept valid rating of 5 (1ms) ✗ should reject rating above 5 (4ms) ✓ should reject rating of 0 (1ms) ✓ should reject negative rating (1ms) ... ✗ should reject one above upper boundary: 6 (1ms) ● validateRating Function › should reject rating above 5 expect(received).toBe(expected) Expected: false Received: true 18 | test('should reject rating above 5', () => { 19 | const result = validateRating(6); > 20 | expect(result.valid).toBe(false); | ^ 21 | }); Test Suites: 1 failed, 1 total Tests: 2 failed, 10 passed, 12 total
🌿 Beginner — Reading the failure message
Expected: false — the test said "I expect this to be false"
Received: true — but the function returned true (accepted rating 6)
The > arrow and ^ caret point to the exact line in the test that failed. Jest also shows the test name, so you know instantly which case broke without reading the whole test file.
⚡ Average — Two tests failed, not one — why?
Both "should reject rating above 5" (tests 6) and "should reject one above upper boundary: 6" (also tests 6) failed. This is intentional test duplication at the boundary — the group-2 test checks the general case, while the group-4 test explicitly documents that 6 is the exact boundary violation. Both catch the same bug, which gives you two signals that something is wrong.
🚀 Advanced — Exit codes and CI
When tests fail, Jest exits with code 1 (non-zero). GitHub Actions interprets any non-zero exit code as a step failure, which marks the entire workflow run as failed and blocks the PR from merging. This is the mechanical gate: your CI pipeline is just automation that checks the exit code. npm test && echo "deploy" — echo "deploy" only runs if tests exit 0.
3.3 Fix the bug and verify tests go green ▶

Restore the correct upper bound in server.js and re-run the tests to confirm everything is green again.

server.js — restore the correct value
// Fix: restore 5 as the upper bound
if (ratingNum < 1 || ratingNum > 5) {
  return { valid: false, error: 'Rating must be between 1 and 5' };
}
terminal
npm test
What you should see
PASS __tests__/unit/validation.test.js validateRating Function ✓ should accept valid rating of 1 (3ms) ✓ should accept valid rating of 3 (1ms) ✓ should accept valid rating of 5 (1ms) ✓ should reject rating above 5 (1ms) ... ✓ should reject one above upper boundary: 6 (1ms) Tests: 12 passed, 12 total | Time: 2.1s
✔
You just experienced the Red → Green cycle that defines TDD (Test-Driven Development): write a failing test, write the minimum code to pass it, confirm it passes. You ran it in reverse here (broke then fixed), but the principle is identical.

Part 4 GitHub Actions CI — Tests on Every Push 15 min
4.1 Create the CI workflow file ▶

GitHub Actions reads YAML workflow files from the .github/workflows/ folder in your repo. Any file there with a .yml extension is treated as a workflow definition.

terminal
cd ~/cloudeats-app

# Create the workflows directory
mkdir -p .github/workflows

# Confirm the path
ls .github/workflows
# Expected: (empty for now)

Now create the workflow file. Every line is annotated so you understand what it does before you push it.

.github/workflows/ci.yml — create this file
# Workflow name — appears in the GitHub Actions tab
name: Run Automated Tests

# TRIGGER: when does this workflow run?
on:
  push:
    branches:
      - main          # every push to main
      - 'feature/**'  # every push to any feature/* branch
  pull_request:
    branches:
      - main          # every PR that targets main

# JOBS: what to run
jobs:
  test-menu-service:
    name: Menu Service Tests
    runs-on: ubuntu-latest  # fresh Ubuntu VM, destroyed after job

    steps:

      # Step 1: Download the code from GitHub
      - name: Checkout code
        uses: actions/checkout@v3

      # Step 2: Install Node.js on the runner VM
      - name: Setup Node.js 18
        uses: actions/setup-node@v3
        with:
          node-version: '18'
          cache: 'npm'          # cache node_modules between runs
          cache-dependency-path: services/menu-service/package-lock.json

      # Step 3: Install project dependencies
      - name: Install dependencies
        working-directory: ./services/menu-service
        run: npm install

      # Step 4: Run the test suite
      - name: Run tests
        working-directory: ./services/menu-service
        env:
          NODE_ENV: test    # enables module.exports in server.js
        run: npm test
🌿 Beginner — What is working-directory?
working-directory: ./services/menu-service tells GitHub Actions to run that step from inside the menu-service folder. Without it, npm install would look for package.json in the root of the repo (where it does not exist) and fail.
⚡ Average — Why cache: 'npm'?
Without caching, every CI run downloads all node_modules from the internet (~50MB for a typical Node project). With cache: 'npm' and cache-dependency-path pointing to the lockfile, GitHub stores node_modules after the first run and restores it on subsequent runs if the lockfile has not changed. This cuts the install step from ~30 seconds to ~3 seconds for typical projects.
🚀 Advanced — The on: trigger design
Running CI on feature/** pushes catches failures early, before a PR is even opened. Running on pull_request: branches: [main] is what enables the branch protection rule: "require status checks to pass before merging". These two triggers together mean a developer cannot merge broken code even if they somehow skip the feature-branch check. The CI gate is enforced at the PR boundary where it matters most.

⚠ "Run tests" step is stuck / spinning for many minutes ▶
This almost always means app.listen() in server.js is not guarded, so it starts a live server during the Jest run. That keeps the CI process alive and the step never finishes — unlike your terminal at home, nobody on GitHub's server can press Ctrl+C. Go back to Step 1.4 and confirm app.listen(...) is wrapped in if (process.env.NODE_ENV !== 'test') { ... }. Fix it, commit, and push again — the stuck run can be cancelled from the Actions tab (top-right "Cancel workflow" button) instead of waiting it out.
⚠ "No workflow runs" in Actions tab ▶
Confirm the file is at exactly .github/workflows/ci.yml in your repo (not .github/workflow/ or github/workflows/). Check with git ls-files | grep ci.yml. Also confirm the push to main actually succeeded: git log origin/main --oneline -3.
⚠ CI fails on "Install dependencies" step ▶
Confirm package-lock.json exists in services/menu-service/. Run npm install locally in that folder, which generates the lockfile, then git add services/menu-service/package-lock.json && git commit -m "chore: add package-lock" && git push.
4.4 Prove CI blocks bad code — push a broken test ▶

The real value of CI is that it catches bugs before they reach main. Push a deliberately broken commit on a feature branch and watch CI reject it.

terminal
# Create a test branch
git checkout -b feature/test-ci-gate

# Break the validation again (change 5 to 10)
sed -i 's/ratingNum > 5/ratingNum > 10/' services/menu-service/src/server.js
# macOS: sed -i '' 's/ratingNum > 5/ratingNum > 10/' ...

git add services/menu-service/src/server.js
git commit -m "bug: accidentally changed rating upper bound to 10"
git push -u origin feature/test-ci-gate

Go to GitHub → Actions tab. Watch the workflow run on feature/test-ci-gate. It will fail with a red X. Now open a Pull Request from feature/test-ci-gate into main — GitHub blocks the merge button with the message: "Some checks were not successful."

✅
This is the CI gate working. A PR with failing tests cannot merge into main. The broken code never reaches production. Fix the bug (restore > 5), push again, CI goes green, merge is unblocked.
terminal — restore and push the fix
sed -i 's/ratingNum > 10/ratingNum > 5/' services/menu-service/src/server.js
# macOS: sed -i '' 's/ratingNum > 10/ratingNum > 5/' ...
git add services/menu-service/src/server.js
git commit -m "fix: restore correct rating upper bound to 5"
git push
# CI re-runs, goes green, PR merge is now unblocked

Merge the PR on GitHub, then clean up locally:

terminal

git pull origin main

Part 5 Test Coverage — How Much is Tested? 10 min
5.1 Run the coverage report ▶

Test coverage measures what percentage of your source code was actually executed when the tests ran. A line that is never reached by any test is a potential hiding place for bugs.

terminal
cd ~/cloudeats-app/services/menu-service
export NODE_ENV=test
npm run test:coverage
What you should see
PASS __tests__/unit/validation.test.js ----------|---------|----------|---------|---------|------------------- File | % Stmts | % Branch | % Funcs | % Lines | Uncovered Line #s ----------|---------|----------|---------|---------|------------------- All files | 45.12 | 28.57 | 50.00 | 45.12 | src/server.js| 45.12 | 28.57 | 50.00 | 45.12 | 20-45, 60-120 ----------|---------|----------|---------|---------|-------------------
🌿 Beginner — What do the columns mean?
% Stmts — percentage of individual statements (lines of code) that ran during tests.
% Branch — percentage of decision points (if/else branches) both sides of which were tested.
% Funcs — percentage of functions that were called at all.
Uncovered Lines — the exact line numbers that no test ever reached. Lines 20-45 and 60-120 are the Express route handlers we have not tested yet.
🌿 Beginner — Why is coverage only 45%?
We only wrote tests for validateRating(). The rest of server.js has route handlers (GET /api/menu, POST /api/ratings etc.) that our unit tests never call. That is fine for now — unit tests cover the pure logic, and integration tests would cover the routes. 45% is a starting point, not the goal.
⚡ Average — Industry coverage targets
70–80% is considered "good" at most companies. 80–90% is "very good". Above 90% tends to have diminishing returns — the remaining untested code is often error-handling paths that are hard to trigger automatically. Chasing 100% coverage can lead to writing tests that check implementation details rather than behaviour, making refactoring painful.
🚀 Average+ — Add a coverage threshold to CI
To enforce a minimum standard, add to package.json:
package.json — add jest config block
"jest": {
  "coverageThreshold": {
    "global": {
      "functions": 80,
      "lines": 70
    }
  }
}
Now npm run test:coverage exits with code 1 if coverage drops below the threshold, causing CI to fail. This mechanically enforces the team's coverage contract.
terminal — also generates an HTML coverage report
# After running test:coverage, open the HTML report:
open coverage/lcov-report/index.html   # macOS
xdg-open coverage/lcov-report/index.html  # Linux
# Shows colour-coded source with covered lines in green, uncovered in red
⚠ Coverage report shows 0% for everything ▶
The NODE_ENV=test variable is missing. The module.exports block in server.js is not executing, so the test file's require('../../src/server') returns an empty object and calls nothing. Run export NODE_ENV=test in the current terminal then retry. On Windows PowerShell use $env:NODE_ENV="test" instead.
5.2 Add one more test — write it yourself ▶

Add a test for one edge case that the original suite does not cover: a rating of 2 (a valid mid-range value). This lets you practise the full loop without scaffolding.

__tests__/unit/validation.test.js — add inside the describe block
// Your new test — add after the last existing test
test('should accept valid rating of 2', () => {
  const result = validateRating(2);
  expect(result.valid).toBe(true);
});
terminal
npm test
# Expected: 13 passed, 0 failed
✨
You just wrote your first test from scratch using the AAA pattern (Arrange: input is 2, Act: call validateRating, Assert: valid is true). Commit this new test with git add && git commit && git push and watch CI run 13 tests.

Part 6 🚀 Husky Pre-Commit Hook 10 min · Advanced only
🚀 Advanced Track — Local quality gate

CI catches bugs after you push. Husky catches them before you commit. A pre-commit hook runs npm test automatically whenever you run git commit. If tests fail, the commit is aborted. You never push broken code because broken code can never become a commit.

6.1 Install Husky and configure the pre-commit hook ▶
terminal — run from the repo root
cd ~/cloudeats-app

# Install Husky at the root level (not inside menu-service)
npm install --save-dev husky

# Initialise Husky — creates .husky/ directory
npx husky init

# Replace the default pre-commit hook with our test command
echo 'cd services/menu-service && export NODE_ENV=test && npm test' > .husky/pre-commit
chmod +x .husky/pre-commit

# Confirm the hook file content
cat .husky/pre-commit
What you should see
cd services/menu-service && export NODE_ENV=test && npm test
🚀 Advanced — How Git hooks work
Git hooks are scripts in .git/hooks/ that Git runs at specific lifecycle points. pre-commit runs before the commit is recorded. If the script exits with non-zero, the commit is aborted. Husky makes hooks trackable in version control (unlike raw .git/hooks/ which is not committed). Every developer who clones the repo and runs npm install gets the same hooks automatically via the prepare script Husky adds to package.json.
6.2 Test the hook — try committing broken code ▶
terminal
# Break the validation again
sed -i 's/ratingNum > 5/ratingNum > 10/' services/menu-service/src/server.js

# Try to commit — the hook should block it
git add services/menu-service/src/server.js
git commit -m "this should not work"
What you should see (commit is rejected)
FAIL __tests__/unit/validation.test.js ✗ should reject rating above 5 ✗ should reject one above upper boundary: 6 Tests: 2 failed, 10 passed husky - pre-commit script failed (exit code 1)
✅
The commit was blocked. The broken change is still in your working directory but was never committed. Fix the bug, then try git commit again — this time the tests will pass and the commit will succeed.
terminal — fix and commit properly
# Restore the correct value
sed -i 's/ratingNum > 10/ratingNum > 5/' services/menu-service/src/server.js

# Commit — hook runs tests, all pass, commit succeeds
git add services/menu-service/src/server.js
git commit -m "chore: add Husky pre-commit hook for local test gate"

# Commit the Husky files too
git add .husky/ package.json package-lock.json
git commit -m "chore: configure Husky pre-commit hook"
git push origin main
🚀 Advanced — Two-layer defence
You now have two independent quality gates: (1) Husky pre-commit — catches failures locally before a commit is even recorded, instant feedback in under 3 seconds. (2) GitHub Actions CI — catches failures on any machine, on any branch, regardless of whether the developer has Husky. Together they create defence-in-depth: local developer discipline backed by a server-side mechanical gate. Neither alone is sufficient: Husky can be bypassed with git commit --no-verify; CI cannot.
✅
Part 6 complete. You have a pre-commit hook that blocks broken commits before they leave your machine, backed by GitHub Actions that blocks broken PRs before they reach main. Two-layer CI is industry standard.
