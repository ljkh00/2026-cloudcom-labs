0.2 Configure Git with your identity ▶

Git needs to know who you are before you can commit. This is a one-time setup per machine — it attaches your name and email to every commit you make.

terminal — replace with your real name and email
git config --global user.name "Your Full Name"
git config --global user.email "your.email@example.com"

# Verify it saved
git config --list | grep user
What you should see
user.name=Your Full Name user.email=your.email@example.com
🌿 Beginner — Why does Git need my name?
Every commit is a snapshot with metadata attached: who made it, when, and why. When your teammates look at the project history (using git log), they see your name next to each commit. This is how teams trace "who added this line?" without asking around.
⚡ Average — --global flag
The --global flag writes to ~/.gitconfig — it applies to every repository on this machine. Omit --global to set a name/email for one specific repo only (useful when you contribute to work and personal projects from the same machine with different identities).

1.2 Create a GitHub repository and connect it ▶

Now create an empty repository on GitHub and link your local folder to it. The local folder is called the local repo; the one on GitHub is called the remote repo.

🌿 Beginner — How to create the repo on GitHub
1. Go to github.com/new
2. Repository name: cloudeats-app
3. Set to Public (required for GitHub Pages)
4. Do NOT tick "Add a README" or "Add .gitignore" — we already have them
5. Click Create repository
6. Copy the HTTPS URL shown (looks like https://github.com/YOUR-USERNAME/cloudeats-app.git)
terminal — replace YOUR-USERNAME with your GitHub username
# Link local repo to GitHub remote (origin = the nickname for GitHub)
git remote add origin https://github.com/YOUR-USERNAME/cloudeats-app.git

# Rename default branch to 'main' (if it is still 'master')
git branch -M main

# Push commits to GitHub for the first time
# -u sets 'origin main' as the default for future push/pull
git push -u origin main
What you should see
Enumerating objects: 14, done. Counting objects: 100% (14/14), done. Writing objects: 100% (14/14), 3.21 KiB | 3.21 MiB/s, done. To https://github.com/YOUR-USERNAME/cloudeats-app.git * [new branch] main -> main Branch 'main' set up to track remote branch 'main' from 'origin'.
⚡ Average — What is 'origin'?
origin is just a nickname (alias) for the remote URL. You could call it anything, but origin is the universal convention. git remote -v shows the full URL behind the alias. Having a nickname means you type git push origin main instead of the full HTTPS URL every time.
⚠ Prompted for username and password every time ▶
GitHub no longer accepts your account password for Git over HTTPS. You need a Personal Access Token: Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token. Select repo scope. Use this token as your password when prompted. Or switch to SSH: GitHub SSH docs →
⚠ "remote origin already exists" ▶
A remote called origin was already added. Check it with git remote -v. To change the URL: git remote set-url origin https://github.com/YOUR-USERNAME/cloudeats-app.git
Why push to GitHub at all? A local Git repo protects you from your own mistakes (you can always revert). A remote on GitHub also protects you if your laptop is stolen, breaks, or gets coffee spilled on it. It also lets teammates clone and contribute, and it is where the CI pipeline in Lab 6.2 will watch for pushes.
1.3 Verify on GitHub ▶

Open https://github.com/YOUR-USERNAME/cloudeats-app in your browser. You should see all your files listed. Click the commits link (e.g. "1 commit") to see the commit history.

🌿 Beginner — What should I see?
You should see a file listing that mirrors your local folder: docker-compose.yml, services/, README.md, package.json, .gitignore. If you do NOT see node_modules/ in the file listing, that means .gitignore worked correctly.
terminal — confirm remote is configured correctly

What you should see

Part 2 Create a Feature Branch 10 min
2.1 Create and switch to feature/add-laksa-to-menu ▶

You are going to add a laksa item to the CloudEats menu. Rather than editing main directly, you create a feature branch — an isolated space where your changes cannot affect anything else until you choose to merge.

terminal
cd ~/cloudeats-app
pwd
# Confirm: ~/cloudeats-app

# Make sure main is up to date before branching
git checkout main
git pull origin main

# Create a new branch AND switch to it in one step
git checkout -b feature/add-laksa-to-menu

# Confirm which branch you are on
git branch
What you should see
* feature/add-laksa-to-menu main
🌿 Beginner — What does the * mean?
The asterisk (*) marks your current branch. Any commits you make now will be added to feature/add-laksa-to-menu. The main branch stays exactly as it was — no asterisk, no changes.
⚡ Average — Why pull before branching?
git pull origin main downloads any new commits your teammates pushed since your last sync. Branching from an outdated main means your feature branch will be missing those changes, which makes the eventual merge larger and messier. Always pull before branching.
🚀 Advanced — Branch naming conventions
The feature/ prefix is a Gitflow convention. Other common prefixes: fix/ for bug fixes, chore/ for maintenance tasks with no user-facing change, hotfix/ for urgent production fixes. These prefixes appear in GitHub's PR view, making it instantly clear what a PR is doing before you read the description.
⚠ "error: pathspec 'feature/add-laksa-to-menu' did not match any file(s) known to git" ▶
This happens when you use git checkout without -b and the branch does not exist yet. Use git checkout -b feature/add-laksa-to-menu (note the -b flag) to create and switch in one step.

What you should see

# Stage specifically the file you changed
git add services/menu-service/seed.js

# Confirm it is staged (green = ready to commit)
git status
What you should see

terminal
# Commit with a clear, imperative message
git commit -m "feat(menu): Add Laksa to menu seed data

- Added Laksa item to menuItems array
- Price: RM 9.50, Category: Noodles
- Spicy coconut noodle soup with prawns and tofu puffs"

# View the commit in the log
git log --oneline -5
What you should see
7c14de8 feat(menu): Add Laksa to menu seed data a3f82b1 Initial commit: CloudEats microservices from Lab 5.1
🌿 Beginner — Why stage before committing?
The staging area is a "review room". You can change 10 files but only commit 3 of them in this snapshot. This lets you make one logical commit ("Add Laksa") separately from another ("Fix typo in README"), even if you edited both files at the same time.
⚡ Average — Conventional Commits format
The message feat(menu): Add Laksa to menu seed data follows Conventional Commits: type(scope): description. Common types: feat (new feature), fix (bug fix), docs (docs only), chore (maintenance). This format is machine-readable — tools like semantic-release use it to auto-generate changelogs and bump version numbers.
🚀 Advanced — What breaks if you force-push to main?
git push --force origin main rewrites the remote history. If any teammate pulled main before your force-push, their local history now diverges from the remote. When they try to push, Git refuses. They must git pull --rebase or reset. Force-pushing to a shared branch is considered destructive. Reserve --force-with-lease (safer) for feature branches only, never for main.

Part 4 Open a Pull Request & Merge to Main 10 min
4.1 Open a Pull Request on GitHub ▶

A Pull Request (PR) is a formal request to merge one branch into another. On GitHub it shows the exact diff, creates a space for code review comments, and (once Lab 6.2 is done) will also show the CI result.

🌿 Beginner — Steps to open the PR
1. Go to https://github.com/YOUR-USERNAME/cloudeats-app
2. Click the yellow banner "Compare & pull request", OR click Pull requests tab → New pull request
3. Set base: main (where you want to merge into)
4. Set compare: feature/add-laksa-to-menu (what you are merging from)
5. Title: feat(menu): Add Laksa to menu
6. Description: Explain what you added and why
7. Click Create pull request
⚡ Average — Reading the diff in a PR
The "Files changed" tab in the PR shows exactly what lines were added (green) and removed (red). This is what your reviewer will read. Good PR hygiene: keep PRs small (one feature), link to the task it resolves, and write a description that explains why, not just what (the diff already shows what).
🚀 Advanced — What breaks if you skip the PR and merge directly?
Merging directly from the command line with git merge still works technically. But you lose: the code review record, the CI check gate (Lab 6.2 attaches to PRs), the diff comment thread, and the permanent "why" documentation. In a team of two or more, a direct merge to main is a code review bypass. At companies with compliance requirements, bypassing PR review can trigger policy violations.
4.2 Merge the PR and pull locally ▶

Once the PR is open (and in a real team, once a reviewer approves it), click Merge pull request on GitHub. Then update your local main branch to match.

terminal — after merging on GitHub
# Switch back to main
git checkout main

# Pull the merge commit from GitHub
git pull origin main

# Confirm laksa is in the history on main
git log --oneline --graph -6
What you should see
* 2b88cc4 Merge pull request #1 from feature/add-laksa-to-menu |\ | * f901aa5 feat(menu): Add initial rating to Laksa item | * 7c14de8 feat(menu): Add Laksa to menu seed data |/ * a3f82b1 Initial commit: CloudEats microservices from Lab 5.1
🌿 Beginner — What is the branching graph telling me?
The * is a commit. The |\ and |/ lines show the branch splitting off and rejoining. Reading from bottom to top: initial commit → feature branch splits off (two feature commits) → feature merges back into main (merge commit at top). This is your complete feature history, preserved forever.
terminal — clean up the feature branch
# Delete the local feature branch (already merged, safe to delete)
git branch -d feature/add-laksa-to-menu

# Delete the remote branch on GitHub
git push origin --delete feature/add-laksa-to-menu

# Confirm only main remains
git branch
What you should see
* main
Why delete the feature branch after merging? Stale branches pile up and confuse the team. If main has the merged code, the branch has served its purpose. Deleting it keeps the repo clean. GitHub even offers a "Delete branch" button on the closed PR page. The history is still in the commit graph — nothing is lost.
✅
Part 4 complete. You have opened a PR, merged it, and cleaned up the branch. This is the core feature branch workflow used in industry every single day.
Part 5 Trigger & Resolve a Merge Conflict 15 min
💡
What you are doing: You will deliberately create a conflict by editing the same line on two different branches. Then you will resolve it the same way a real team does. Merge conflicts look scary the first time — this exercise makes them routine.
5.1 Set up the conflict — two branches, same line ▶

You will create two branches that both edit the same line in services/menu-service/server.js. When you try to merge, Git cannot auto-decide which version to keep.

terminal — create branch A and commit a change
git checkout main

# Branch A — person sets port to 3002
git checkout -b conflict/branch-a

# Edit the first line of server.js that sets the port
# On macOS/Linux: sed replaces in-place
sed -i 's/const PORT = .*/const PORT = 3002;/' services/menu-service/server.js

# On macOS you may need: sed -i '' 's/const PORT = .*/const PORT = 3002;/' ...

# Verify the change
grep "const PORT" services/menu-service/server.js
What you should see
const PORT = 3002;
terminal
git add services/menu-service/server.js
git commit -m "chore(menu): Set port to 3002 for menu service"

# Now go back to main and create a SECOND branch
git checkout main
git checkout -b conflict/branch-b

# Branch B — different person sets port to 3003
sed -i 's/const PORT = .*/const PORT = 3003;/' services/menu-service/server.js
# macOS: sed -i '' 's/const PORT = .*/const PORT = 3003;/' ...

git add services/menu-service/server.js
git commit -m "chore(menu): Set port to 3003 for testing environment"
🌿 Beginner — What just happened?
You now have two branches that both started from the same main and both changed the same line (const PORT = ...) to different values. When you try to merge one into the other, Git will not know which value is correct — so it marks the conflict and waits for you to decide.
5.2 Trigger the conflict by merging branch-a into branch-b ▶
terminal
# You are on conflict/branch-b
git branch
# Expected: * conflict/branch-b

# Try to merge branch-a INTO branch-b
git merge conflict/branch-a
What you should see
Auto-merging services/menu-service/server.js CONFLICT (content): Merge conflict in services/menu-service/server.js Automatic merge failed; fix conflicts and then commit the result.
✅
This is expected. Git has paused and is waiting for you. Your repo is in a special "merging" state. Nothing is broken — Git just needs your decision.
terminal — confirm what git status shows during a conflict
git status
What you should see
On branch conflict/branch-b You have unmerged paths. (fix conflicts and run "git commit") (use "git merge --abort" to abort the merge) Unmerged paths: (use "git add <file>..." to mark resolution) both modified: services/menu-service/server.js
🌿 Beginner — "both modified" means conflict
both modified is Git saying "both branches changed this file in the same area and I cannot auto-merge them." You need to open the file and decide what to keep. We do that in Step 5.3.
⚡ Average — Escape hatch
If you ever want to cancel a merge that has gone wrong: git merge --abort. This returns your branch to exactly where it was before you ran git merge. Nothing is lost. Use it to start over if you make a mistake during conflict resolution.
5.3 Read the conflict markers and resolve ▶

Open services/menu-service/server.js in your editor. Find the conflict markers. They look like this:

what you will see inside server.js
<<<<<<< HEAD
const PORT = 3003;
=======
const PORT = 3002;
>>>>>>> conflict/branch-a
🌿 Beginner — Decoding the markers
Between <<< HEAD and ======= is YOUR branch's version (branch-b, port 3003)

Between ======= and >>> is the INCOMING version (branch-a, port 3002)

You need to: (1) decide which port is correct, (2) delete the three marker lines, (3) leave only the final correct code.

For this exercise, port 3002 is correct for the menu service. Edit the file so it reads exactly:

services/menu-service/server.js — after resolving
const PORT = 3002;
// All three conflict marker lines deleted — file is clean
⚠
Make sure you delete all three marker lines: the <<<<<<<, the =======, and the >>>>>>>. Leaving any marker in the file will cause your app to crash with a syntax error.
⚡ Average — VS Code makes conflicts visual
VS Code highlights conflict markers with green/blue colour coding and shows buttons: Accept Current Change, Accept Incoming Change, Accept Both Changes, Compare Changes. Clicking "Accept Incoming Change" does the same as manually deleting the markers and keeping the incoming version. For complex conflicts with many files, VS Code's merge editor is much easier than using nano.
5.4 Stage the resolved file and complete the merge ▶

Once the file is clean (no conflict markers), you tell Git "I have resolved this" by staging the file. Then you complete the merge with a commit.

terminal
# Confirm the file no longer has conflict markers
grep -n "<<<\|===\|>>>" services/menu-service/server.js
# Expected: no output (empty = no markers found)

# Stage the resolved file
git add services/menu-service/server.js

# Check status — "all conflicts fixed"
git status
What you should see
On branch conflict/branch-b All conflicts fixed but you are still merging. (use "git commit" to conclude merge)
terminal
# Complete the merge with a descriptive commit
git commit -m "Merge conflict/branch-a: resolve PORT conflict, keep 3002 for menu service"

# View the final graph
git log --oneline --graph -6
What you should see
* 9e51ff2 Merge conflict/branch-a: resolve PORT conflict, keep 3002 for menu service |\ | * 2b88cc4 chore(menu): Set port to 3002 for menu service * | f901aa5 chore(menu): Set port to 3003 for testing environment |/ * 7c14de8 Merge pull request #1 from feature/add-laksa-to-menu ...
🌿 Beginner — You just did what senior devs do
Merge conflicts look terrifying in tutorials but in practice they are just text editing. The key steps are always the same: find the markers, decide what to keep, delete the markers, git add, git commit. After you do this five times, it takes under two minutes.
🚀 Advanced — Preventing conflicts at scale
Teams reduce conflict frequency by: (1) trunk-based development with feature flags (branches live less than 24 hours), (2) git pull --rebase instead of merge pulls (keeps history linear), (3) file ownership policies (CODEOWNERS file in GitHub assigns specific files to specific people, reducing simultaneous edits), (4) breaking large files into smaller modules. The nuclear option is git rerere (reuse recorded resolution) — Git memorises how you resolved a conflict and replays it automatically next time.
terminal — clean up both conflict branches
git checkout main
git branch -d conflict/branch-a
git branch -d conflict/branch-b
git branch
# Expected: * main
✅
Part 5 complete. You deliberately caused a merge conflict and resolved it. This is a milestone — most students are afraid of conflicts until they do it hands-on once.

6.2 Enable GitHub Pages in the repo settings ▶
🌎 Enable GitHub Pages — 4 steps
  1. Go to your repo on GitHub → click Settings tab (top row)
  2. In the left sidebar click Pages
  3. Under Branch, select main and folder /docs → click Save
  4. Wait 60–90 seconds, then refresh the Settings → Pages page. You will see: "Your site is live at https://YOUR-USERNAME.github.io/cloudeats-app"
🚀 Advanced — What GitHub Pages actually does
GitHub Pages runs a static site server that serves files from the branch and folder you specified. Every time you push to main, GitHub rebuilds the site automatically within ~60 seconds. It uses the same CDN infrastructure as GitHub itself, so your site loads fast globally for free. The docs/ folder approach keeps your app code and public site in the same repo — a clean pattern for portfolio projects.
