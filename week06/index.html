1.1 The Problem DevOps Solves 15 min

Before DevOps, software companies had two separate teams that rarely talked to each other — and that silence caused constant crises.

🚧 Dev Team — wants speed
Writes new features every week
Wants to deploy on Friday afternoon
"It works on my machine!"
Blames Ops when deployment fails
📝 Ops Team — wants stability
Runs the servers, fears downtime
Reluctant to deploy on Fridays
"This worked fine last quarter!"
Blames Dev when servers crash
🌿 Beginner ⚡ Average 🚀 Advanced
🌿 Beginner — Think of a Restaurant
Imagine the kitchen (Dev team) cooks food however they like. The waiter (Ops team) then has to serve it — but the chef never warned the waiter what was on the menu. Every service is a surprise and customers keep getting the wrong food. DevOps is like having a shared kitchen screen: everyone sees what is cooking, and the recipe is always the same no matter which chef made it.
⚡ Average — The Wall of Confusion
Developers throw code "over the wall" to operations. Ops scrambles to deploy code they did not write, on servers the developer never tested on. When something breaks, there is a blame game instead of a fix. DevOps breaks down the wall — same people, same tools, shared responsibility for the full lifecycle: code → test → deploy → monitor.
🚀 Advanced — DORA Metrics
The DevOps Research and Assessment (DORA) team identified four key metrics for high-performing engineering organisations: Deployment Frequency, Lead Time for Changes, Change Failure Rate, and Mean Time to Recovery. Elite performers deploy multiple times per day with a change failure rate below 1%. Week 6 gives you the Git and CI foundation that makes this possible at any scale.
🔗
CloudEats connection: Every lab from Week 6 onwards is a DevOps practice. Git = version control; automated tests = quality gate; GitHub Actions = the pipeline that takes code from your laptop to a running container automatically.
1.2 Git — Core Concepts 25 min

Git is a distributed version control system — a tool that tracks every change to every file, who made it, and when. Without it, teams manage code like this:

without git — file naming chaos
server-v1.js
server-v2-ali-changes.js
server-FINAL.js
server-FINAL-FINAL-USE-THIS-ONE.js
server-FINAL-FINAL-v2-with-bugfix.js
# Which one is production? Nobody knows.

With Git there is one file. The complete history is stored in a hidden .git folder. You can return to any previous version at any time.

🌿 Beginner ⚡ Average 🚀 Advanced
🌿 Beginner — Key Terms Explained Simply
  • Repository (repo): A folder that Git is watching and remembering. Think of it as a project box that keeps every version of every file you ever saved.
  • Commit: A saved snapshot of your project at a moment in time — like hitting "Save Game" in a video game. You can reload any old save.
  • Staging area: A waiting room before you commit. You choose exactly which changed files go into the next snapshot using git add.
  • Remote: A copy of your repo on GitHub's servers. push uploads your snapshots there; pull downloads new ones from there.
⚡ Average — The Three-State Model
Git tracks files in three states: Working directory (your actual files on disk), Staging area / index (changes chosen for the next commit via git add), and Repository (committed snapshots in .git/). Run git status before every commit — it shows exactly which state each changed file is in.
🚀 Advanced — Content-Addressable Storage
Every commit hash (e.g. a3f82b1) is a SHA-1 checksum of the commit's content including the parent commit hash. This makes Git a Merkle tree — tamper-proof by design. Changing one byte in any historical file produces a completely different hash chain, immediately detectable. This is also why git rebase creates new commits (new hashes) rather than moving old ones.
essential git commands
# Start tracking a folder ────────────────────────────────
git init                          # Start tracking this folder with Git

# See what has changed ───────────────────────────────────
git status                        # See all changed / staged / untracked files
git diff                          # See exact line-by-line changes (unstaged only)

# Stage and commit ───────────────────────────────────────
git add server.js                 # Stage one specific file
git add .                         # Stage ALL changed files in this folder
git commit -m "Add menu endpoint" # Save a snapshot with a description

# View history ───────────────────────────────────────────
git log --oneline                 # Compact one-line history
git log --oneline --graph         # History with branch lines drawn in ASCII

# Sync with GitHub ───────────────────────────────────────
git push origin main              # Upload your commits to GitHub
git pull origin main              # Download new commits from GitHub

Writing good commit messages — this matters for teamwork:

❌ Bad messages
"fix stuff"
"changes"
"update"
"asdfgh"
✔ Good messages
"Fix null error in order endpoint"
"Add bcrypt to registration route"
"Update docker-compose healthcheck"
💡
A commit message should complete this sentence: "If applied, this commit will: [your message]." Try it with "fix stuff" and you will immediately see why it fails.
1.3 .gitignore — What Not to Track 10 min

Not everything in your project folder should be committed to Git. The .gitignore file (note the dot at the start) tells Git which files to silently skip.

🚫
Never commit these
node_modules/ — hundreds of megabytes; npm install recreates it every time

.env — contains real passwords and API keys. If this reaches GitHub, rotate credentials immediately

*.log — runtime log files, different on every machine

.DS_Store — macOS metadata, meaningless to teammates on Windows/Linux
✅
Always commit these
All source code (.js, .py, .html, .css)

Config files (docker-compose.yml, package.json, Dockerfile)

Documentation (README.md)

.env.example — shows shape of .env without real values
.gitignore — paste at project root
# Dependencies (recreated by npm install)
node_modules/

# Environment secrets — NEVER commit real values
.env

# Runtime logs
*.log
npm-debug.log*

# OS metadata
.DS_Store
Thumbs.db
.env.example — commit this instead of .env
# Copy this to .env and fill in your real values
DB_HOST=your_database_host
DB_USER=your_username
DB_PASSWORD=your_password_here
JWT_SECRET=your_secret_here
REDIS_URL=redis://localhost:6379
🌿 Beginner ⚡ Average 🚀 Advanced
🌿 Beginner — Why .env is so dangerous
Your .env file contains database passwords and secret keys. GitHub is public by default. If you push .env to GitHub, automated bots scan for it within seconds, extract your credentials, and use them to attack your database or run up cloud charges under your account. This happens to real students every semester. The rule is simple: .env goes in .gitignore, always, forever.
⚡ Average — Why .env.example matters
.env.example communicates required environment variables to new contributors without exposing real values. When a new developer clones the repo, they run cp .env.example .env and fill in their own values. This is a professional convention used in every serious Node.js project. See: dotenv docs →
🚀 Advanced — Git history remembers deleted files
Deleting .env from a later commit does NOT remove it from history. git log --all -- .env will still find it. Anyone who clones and checks out an old commit will see the file with real credentials. Correct remediation is git filter-branch or BFG Repo Cleaner, followed by rotating all exposed credentials. Prevention is the only real solution — always gitignore before first commit.
2.1 What is a Branch? 20 min

A branch is a separate, parallel line of development inside the same repository. Changes on a branch do not affect anyone else until you choose to merge them back.

🌿 Beginner ⚡ Average 🚀 Advanced
🌿 Beginner — Branching is Like a Draft
You are writing an essay. You have your main essay saved. You want to try a new introduction but you are not sure it is good. You make a copy, edit the copy, and if you like it, you paste it back into the main essay. A Git branch is exactly that — a safe draft space. The main essay (the main branch) is never touched until you are confident.
⚡ Average — Why branches matter for teams
Without branches, all developers push directly to main. Ali pushes broken code at 3pm. By 3:01pm the entire team is blocked. Branches give Ali a sandbox — his broken code only affects feature/ali-profile. The team carries on. When Ali fixes it and tests pass, the branch merges cleanly into main.
🚀 Advanced — A branch is just a pointer
Under the hood, a branch is a text file in .git/refs/heads/ containing one commit hash (41 bytes). Creating a branch is O(1) — it costs nothing. This is why Git branching is so cheap compared to older systems like SVN that physically copied files. HEAD is a special pointer that always tracks your current branch.

🌿 Interactive Branch Visualizer — step through a feature branch workflow

You are on main. Three commits exist: init, menu API, user auth.
branch commands
git branch                           # List all branches (* = current branch)
git branch feature/add-laksa          # Create a new branch (stays on current)
git checkout feature/add-laksa        # Switch to that branch
git checkout -b feature/add-laksa     # Create AND switch in one step
git push origin feature/add-laksa     # Upload this branch to GitHub
git merge feature/add-laksa           # Merge branch into current branch
git branch -d feature/add-laksa       # Delete branch after merging (safe)

The complete pull request workflow:

Why open a Pull Request instead of merging directly? A PR creates a permanent record of what changed, why, and who approved it. It shows the code diff for review, surfaces automated test results, and blocks merge until all checks pass. Six months later when something breaks, the PR history tells you exactly which change caused it.
🚀 Advanced — Trunk-Based vs Gitflow
CloudEats uses simplified Gitflow (main + develop + feature branches). For large teams, trunk-based development is often preferable — everyone commits to main using very short-lived branches (<24 hours), relying on feature flags to hide incomplete work. Gitflow suits products with versioned releases (mobile apps, packaged software). Trunk-based suits continuous deployment (web services). Since CloudEats deploys continuously, trunk-based would be the industry choice — but Gitflow is easier to learn first.
2.3 Resolving Merge Conflicts 20 min

A merge conflict occurs when two branches change the exact same lines of the same file. Git pauses and asks you to decide. This looks scary but is just a text editing task.

⚡ Interactive Conflict Resolver — click the version you want to keep

<<<<<<< HEAD (your branch)
const PORT = 3000;
======= (divider)
const PORT = 3001;
>>>>>>> feature/user-service
✔ RESOLVED
Click a version above to resolve the conflict.
next steps after resolving
# After editing the file to keep the right version:
git add server.js
git commit -m "Resolve conflict: use port 3001 for user-service"
🛡
Prevention is better than cure: Pull from main frequently (git pull origin main before starting work). Keep feature branches short-lived — merge within a day or two. Communicate with teammates about which files you are editing.
⚡ Average — Reading the conflict markers
Between <<<<<<< HEAD and ======= is your version (current branch). Between ======= and >>>>>>> is the incoming version (branch being merged). Edit the file, remove all three marker lines, keep whichever code is correct. Then git add and git commit.
🚀 Advanced — 3-way merge vs rebase
git merge creates a merge commit (non-linear history). git rebase replays commits on top of the target — linear history, but rewrites commit hashes. Rebase is cleaner for feature branches before opening a PR. Never rebase a branch that has been pushed and shared — you rewrite history others already have. GitHub's "Squash and merge" button handles this safely.
3.1 What is CI/CD? 20 min

CI/CD stands for Continuous Integration / Continuous Deployment. It automates every step between writing code and running that code in production — removing manual SSH sessions, manual docker compose up, and manual "hope it works" deployments.

🔗
Continuous Integration (CI)
Every time a developer pushes code, an automated process:

1. Downloads the code
2. Installs dependencies
3. Runs all tests
4. Reports: pass ✔ or fail ✖

Broken code is caught immediately. A PR cannot merge until CI passes.
runs on every push
🚀
Continuous Deployment (CD)
If CI passes, the code is automatically deployed to a server. No manual steps required.

Push to main → tests pass → app is live.

CD builds on top of CI. You build a full CD pipeline in Week 7 Lab 7.2.
covered in Week 7
📱
Why this matters: Manual deployment is a Friday afternoon nightmare. Automated deployment is a Tuesday morning routine. Every serious software company uses CI/CD — it is table stakes, not optional.

This simulates what GitHub Actions does when you run git push origin main.

⚫Workflow triggered by git push origin main
⚫Checkout code (actions/checkout@v3)
⚫Setup Node.js 18
⚫Install dependencies (npm install)
⚫Run tests (npm test)
⚫Report result — update commit status on GitHub
.github/workflows/ci.yml — the workflow students build in Lab 6.2
name: Run Tests

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      # Step 1 — get the code
      - uses: actions/checkout@v3

      # Step 2 — install Node.js
      - name: Setup Node.js
        uses: actions/setup-node@v3
        with:
          node-version: '18'

      # Step 3 — install packages
      - name: Install dependencies
        run: npm install

      # Step 4 — run the tests
      - name: Run tests
        run: npm test
🌿 Beginner ⚡ Average 🚀 Advanced
🌿 Beginner — What is YAML?
YAML (pronounced "yam-ul") is a file format for writing configuration in a human-readable way. It uses indentation (spaces, not tabs!) to show structure. Think of it like a form: name: is the label, Run Tests is your answer. GitHub reads this file and knows exactly what to do when you push code.
⚡ Average — The on: trigger block
The on: block defines when the workflow fires. push: branches: [main, develop] means "run CI whenever anyone pushes to main or develop". pull_request: branches: [main] means "also run CI when a PR targeting main is opened or updated". This is the gate — a PR must show a green checkmark before it can be merged. See GitHub Actions trigger docs →
🚀 Advanced — GitHub Actions architecture
When CI triggers, GitHub allocates a fresh ephemeral ubuntu-latest runner VM. Each step runs in sequence on this VM. uses: references a reusable action from the Actions Marketplace. run: executes a shell command. The VM is destroyed after the job — nothing persists between runs unless you use actions/cache explicitly. This immutability is a feature: every run starts clean, eliminating "works on my runner" bugs.
3.2 Unit Tests vs Integration Tests 20 min

Automated tests verify that code works correctly without a human clicking buttons. Two types matter for CloudEats right now:

🔬
Unit Test
Tests one isolated function — no database, no network, no other services. Fast (milliseconds). Run hundreds per second.

External dependencies are replaced with fake versions called "mocks". Only the logic of the function is tested.
fast · isolated
📈
Integration Test
Tests multiple parts working together — usually an API endpoint hitting a real database. Slower (seconds). Tests actual user-facing behaviour.

Catches "wiring errors" — wrong SQL, missing middleware, incorrect response shape — that unit tests miss entirely.
real dependencies
unit test — pure function, no database needed
// Function to test (orders/utils.js)
function calculateTotal(items) {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}

// Test (tests/utils.test.js)
test('calculateTotal returns correct sum', () => {
  const items = [
    { price: 12.90, quantity: 2 },   // Nasi Lemak x 2 = 25.80
    { price: 8.50,  quantity: 1 }    // Laksa x 1    =  8.50
  ];
  expect(calculateTotal(items)).toBe(34.30);
});
reading test output — what pass and fail look like
PASS  tests/utils.test.js
  calculateTotal
    ✓ returns correct sum (3ms)
    ✓ returns 0 for empty cart (1ms)
    ✓ handles decimal prices correctly (2ms)

Test Suites: 1 passed, 1 total  |  Tests: 3 passed, 3 total  |  Time: 0.847s

--- If a test fails: --------------------------------------------------
FAIL  tests/utils.test.js
  calculateTotal
    ✗ returns correct sum (4ms)
      Expected: 34.30
      Received: 21.40
# The received value tells you exactly what went wrong
🌿 Beginner ⚡ Average 🚀 Advanced
🌿 Beginner — Tests are just IF statements
A test says "I expect the function to return X when given Y. If it does not, something broke." expect(calculateTotal(items)).toBe(34.30) reads as "I expect calculateTotal called with these items to equal 34.30." If it returns 21.40 instead, the test fails and gives you the exact numbers — no detective work needed.
⚡ Average — Both types are needed
Unit tests are fast and catch logic errors (the multiplication formula is wrong). Integration tests are slower but catch wiring errors (the SQL query inserts to the wrong column). Industry practice: many unit tests that run in under 30 seconds, plus fewer integration tests. A 10:1 unit-to-integration ratio is common. See Jest documentation →
🚀 Advanced — Test pyramid and Jest vs Mocha
The test pyramid prescribes: many unit tests at the base, fewer integration tests in the middle, minimal end-to-end (browser) tests at the top. CloudEats uses Jest over Mocha because: zero-config setup, built-in expect assertions, built-in mocking, and coverage reports. Mocha is more modular but requires separate packages (Chai for assertions, Sinon for mocks). For a small team, Jest's batteries-included approach wins. For a large team with specific tooling needs, Mocha's composability is valuable.

Eight questions covering Hours 1–3. Click any answer to check it instantly. An explanation appears below each question after you answer.

1. A developer pushes broken code directly to main at 4pm on a Friday. Which DevOps practice most directly prevents this?
  • Having two separate teams — one Dev, one Ops
  • Writing more comments in the code
  • Branch protection rules requiring CI to pass before merging to main
  • Deploying on Mondays only
💡
Branch protection rules on GitHub block any merge to main unless all required CI checks pass and a reviewer has approved. Even if a developer tries to push directly, the rule enforces the gate. This is the DevOps practice that replaces "hope nothing breaks on Friday" with a repeatable, automated safety net.
2. You run git status and see a file listed under "Changes not staged for commit". What is the correct next command to include it in your next commit?
  • git commit -m "save it"
  • git add filename.js
  • git push origin main
  • git pull origin main
💡
"Not staged for commit" means the file is in your working directory but has not been moved to the staging area yet. git add filename.js moves it to staging. Only then can git commit include it in the snapshot. Think of staging as a shopping basket — you choose what goes in before you check out.
3. Which of these files should never be committed to a public GitHub repository?
  • package.json
  • .env
  • README.md
  • docker-compose.yml
💡
.env contains real database passwords and API keys. Automated bots scan GitHub for exposed credentials within seconds of a push and use them to attack databases or generate cloud charges. Always add .env to .gitignore before your very first commit. Use .env.example instead to document which variables teammates need to fill in.
4. After running git merge feature/user-service, you see this in your file:

<<<<<<< HEAD
const PORT = 3000;
=======
const PORT = 3001;
>>>>>>> feature/user-service What does the section between <<< and === represent?
  • The incoming branch’s version
  • Your current branch’s version (HEAD)
  • The original version before either branch changed it
  • A Git error message that you cannot edit
💡
HEAD points to your current branch. The section between <<< and === is your version. The section between === and >>> is the incoming version from feature/user-service. To resolve: edit the file, delete all three marker lines, keep whichever code is correct, then git add and git commit.
5. In the GitHub Actions workflow file, what does the on: push: branches: [main] block control?
  • Which Node.js version to install
  • Which test files to run
  • When the workflow is triggered
  • Where to deploy the application after tests pass
💡
The on: block defines triggers — events that cause the workflow to run. push: branches: [main] means "run this workflow whenever someone pushes commits to the main branch". The jobs: block below it defines what to do when triggered. Separating trigger from action is what makes GitHub Actions reusable across different events.
6. A unit test for calculateTotal() passes successfully. But when the app runs, orders are saved with the wrong total in the database. Which type of test would have caught this bug?
  • More unit tests on calculateTotal()
  • An integration test for the POST /api/orders endpoint
  • Adding the file to .gitignore
  • A better commit message on the broken commit
💡
The calculation function works correctly in isolation (the unit test passes). The bug is in the "wiring" — how the total is passed and saved to the database. Unit tests only test one function in isolation. An integration test for POST /api/orders would exercise the full path: HTTP request → middleware → database write → response, and would catch a wiring error that unit tests miss by design.
7. Which single command creates a new branch called feature/add-laksa AND immediately switches to it?
  • git branch feature/add-laksa
  • git checkout feature/add-laksa
  • git checkout -b feature/add-laksa
  • git merge feature/add-laksa
💡
The -b flag tells git checkout to create the branch and switch to it in one step. Without -b, git checkout feature/add-laksa tries to switch to a branch that does not exist yet and gives an error. The modern equivalent (Git 2.23+) is git switch -c feature/add-laksa, which is more readable.
8. Describe step by step what happens from the moment a developer types git push origin main to when GitHub shows a green ✔ on the commit. (Choose the most complete answer.)
  • Nothing automatic — the green tick appears after 5 minutes
  • GitHub emails the team to ask if the code is safe to deploy
  • GitHub detects the push, allocates a fresh Ubuntu runner VM, checks out the code, installs npm packages, runs npm test, and marks the commit pass or fail based on the exit code
  • The code is deployed to production immediately without any checks
💡
The push triggers the on: push workflow. GitHub allocates an ephemeral Ubuntu VM (the "runner") and executes each step in sequence: checkout code → setup Node.js → npm install → npm test. If every step exits with code 0 (success), the commit receives a green checkmark. If any step fails (non-zero exit), it receives a red cross and the developer is notified. The runner VM is then destroyed.
